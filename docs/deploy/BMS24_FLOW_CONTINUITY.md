# Непрерывная разработка BMS24: реестр, состояние в PR, синхронизация с main

Документ утверждён владельцем 27.11.2026. Он дополняет [решение #160](https://github.com/rimanfatykhov-arch/bms24/issues/160) (одна ветка — один исполнитель, квитанция передачи; PR #161), [стандарт выпуска](BMS24_RELEASE_CONVEYOR_V1.md) и [политику #63](https://github.com/rimanfatykhov-arch/bms24/issues/63). Где они расходятся, действуют #160 и стандарт выпуска. Этот документ ни одну проверку не ослабляет.

Цель — устранить разрывы, которые были в работе до 27.11. Первый: одну линию вели два исполнителя, потому что указания пришли в разные чаты. Второй: состояние терялось вместе с сессией. Третий: длинные цепочки PR расходились с main. Четвёртый: работа стояла, пока ждали решения или вердикта.

## 1. Реестр исполнителей

- Единственный источник истины — закреплённый [Issue #198 «Реестр исполнителей BMS24»](https://github.com/rimanfatykhov-arch/bms24/issues/198). Для каждой линии в нём записаны PR, ветки, исполнитель (Claude, Codex или DeepSeek, а для Claude — название сессии) и состояние.
- Перед каждым push исполнитель сверяется с реестром. Если линии нет или там записан другой исполнитель, он не пушит. Он оставляет комментарий в #198 и ждёт решения владельца.
- Назначает исполнителя только владелец. Указание, данное прямо в одном из чатов, сначала заносят в реестр, и только потом по нему пушат. Координатор фиксирует решение в #198 в тот же день.
- Передача линии идёт по #160. Старый исполнитель оставляет квитанцию в PR, новый подтверждает её получение, и после этого координатор меняет строку реестра.

## 2. Состояние хранится в PR

У каждого открытого PR в описании, сразу после строки `Исполнитель:`, есть блок «Состояние». Его обновляют при каждом push и при каждом вердикте:

```text
Состояние (дата, время UTC)
head: <полный SHA>  tree: <полный SHA>  base: <SHA main>
CI: <ссылка на запуск> — PASS/FAIL/RUNNING
Кандидат: <имя артефакта>, ZIP SHA256 <…>, manifest <…> (если собран)
Следующий шаг: <одно действие> — кто: <исполнитель/Codex/владелец>
Блокер: <нет | что именно>
```

Продолжить работу должен уметь любой исполнитель, у которого есть только этот блок и `git`. Переписку чатов для этого читать не нужно. Передачу Codex публикуют комментарием в PR по одному шаблону: head и tree, один ZIP из CI, SHA256 ZIP и manifest, обязательные проверки с результатами, проверки NOT RUN и короткий сценарий приёмки.

## 3. Синхронизация с main

- После каждого merge в main исполнитель каждой открытой линии в течение рабочего дня вливает main в свои ветки, прогоняет CI и обновляет блок «Состояние». Сначала main вливают в нижний PR цепочки, затем каждый следующий вливают поверх предыдущего.
- Опубликованную историю не переписывают: только merge, без force-push в чужие или уже переданные Codex ветки.
- Цепочка держит не больше трёх PR, ещё не принятых Codex. Следующий PR открывают, когда нижний получил PASS.
- Порядок merge задаёт владелец. Его записывают в раздел «Очередь merge» в #198.

## 4. Работа не стоит в ожидании

- Если исполнителю нужно решение владельца, он ставит метку `ждёт-владельца`, формулирует вопрос в PR и переходит к следующей задаче своей линии, которая от этого решения не зависит.
- Координатор собирает открытые вопросы в один опросник с вариантами ответа, примерно дважды в день. Владельцу не нужно отвечать в каждом чате отдельно.
- У вопроса о решении внутри исходного кода может быть вариант по умолчанию со сроком. Если владелец до срока не возразил, вариант считается принятым, и это записывают в PR. Для TEST, staging, production, merge, схемы БД, прав доступа и внешних интеграций вариантов по умолчанию нет.

## 5. Вердикты Codex и метки

- Мяч на PR показывают метки, на PR одновременно стоит одна из них: `ждёт-codex`, `codex-fail`, `codex-pass`, `ждёт-владельца`.
- Метку ставит тот, кто передаёт мяч. Исполнитель ставит `ждёт-codex`, когда публикует передачу. Codex или координатор ставит `codex-fail` или `codex-pass` по вердикту.
- Координатор следит за комментариями во всех PR и Issue. Вердикт Codex он передаёт исполнителю нужной линии, а не начинает исправления сам, если линия за ним не закреплена.

## Что не меняется

TEST устанавливает только Codex, в порядке очереди #145. Production — только через Codex, после просмотра владельцем и его команды «публикуй» для конкретного ZIP и среды. Staging и merge — вне задач исполнителей. Обязательные проверки, FULL, release gates и отрицательные контроли не ослабляются. Недоступные проверки отмечаются `NOT RUN`.
