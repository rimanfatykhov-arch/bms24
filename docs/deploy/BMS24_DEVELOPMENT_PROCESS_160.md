# Решение по процессу разработки BMS24, #160

Владелец утвердил [решение #160](https://github.com/rimanfatykhov-arch/bms24/issues/160). Оно дополняет [стандарт выпуска](BMS24_RELEASE_CONVEYOR_V1.md) и [политику #63](https://github.com/rimanfatykhov-arch/bms24/issues/63). Быстрая проверка нужна до пуша. Приёмка выпуска по-прежнему опирается на обязательные CI, FULL, release gates и отрицательные контроли.

## Задача и исполнитель

Один PR отвечает на один проверяемый вопрос. Для продуктового PR в описании есть короткий сценарий, по которому владелец увидит результат. Решения и независимые аудиты оформляются отдельно от реализации.

Первая строка описания PR — `Исполнитель: Claude`, `Исполнитель: Codex` или `Исполнитель: DeepSeek`. Только указанный исполнитель пушит в ветку. При передаче он оставляет в PR квитанцию: полный head SHA, результат `git status`, завершённые изменения, фактически выполненные проверки и остаток работы. Принимающий подтверждает получение в PR. После этого обновляется исполнитель в описании и возобновляются пуши. Если обнаружилась вторая работа над той же целью, зафиксируйте пересечение в PR или задаче до следующего пуша.

## Проверка до пуша и приёмка

Правку оформления сначала открывают на локальном стенде с реальными шаблонами `bms24_*`, CSS плагина и синтетическими данными. Проверяют затронутые экраны на ширинах 320, 375, 768 и 1440 px. В отчёте отдельно отмечают локальный результат и результат обязательного CI. Недоступную проверку отмечают `NOT RUN`.

Перед сборкой сверяют исходную ветку и публикуемый состав с фактически установленным production. Пакет должен сохранять ранее выпущенные функции. Проверки и квитанция привязываются к head, base, tree, ZIP и manifest. При изменении дерева заново проверяют затронутое поведение на новом кандидате.

Codex ведёт очередь установок на test в [#145](https://github.com/rimanfatykhov-arch/bms24/issues/145). До завершения задачи E из #160 установки на test выполняются последовательно, одним оператором. Для production и staging требуется независимая приёмка, просмотр владельца и отдельная команда «публикуй» для принятого ZIP и указанной среды.

## Учёт известных падений

Задача C из #160 оформляется отдельно. Запись о падении должна иметь точный ID теста и проверяемую причину, владельца и срок. Неожиданное падение и просроченная запись блокируют решение о готовности. Кандидат и отрицательные контроли по-прежнему обязаны проходить действующие проверки. Отсутствие отчёта, сбой подготовки среды и отмена запуска учитываются своим фактическим статусом.
