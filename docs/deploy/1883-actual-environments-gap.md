## Вывод

Оба сервера используют существенно разные версии Moodle. Даже совпадающие номера плагинов не доказывают одинаковое поведение; для production-релизов сначала нужен релевантный staging на той же Moodle 4.1.22, с PHP 8.1 и Custom Certificate.

`mod/customcert` на production требует Core >= `2022112820`, поэтому перенос этого кода в текущий staging Moodle 4.0.12 **заблокирован**.

По официальной документации Moodle ветка 4.1 уже не поддерживается: после краткосрочного выравнивания staging требуется отдельный план перехода на поддерживаемый LTS.

## Решение для этапа 1884

1. Снять версии PHP и БД внутри staging Docker; определить набор томов и Docker Compose окружения (read-only).
2. Проверить резервные копии текущего staging и доступную ёмкость VDS.
3. Поднять **отдельный** staging-контур Moodle 4.1.22 + совместимые плагины и Custom Certificate с изолированной тестовой БД; сохранить рабочий 4.0.12 без изменения.
4. Провести миграционную и пользовательскую приёмку, включая ACL, курсы и сертификаты.
5. После parity подготовить production release package с независимым rollback и обязательным ручным подтверждением.
6. Не копировать `config.php`, `moodledata`, тестовую БД или секреты на production.
