# Быстрый маршрут модуля — предложение к согласованию

Продолжение [стандарта QA](../05_RELEASE_QA_STANDARD.md) и действующих runbooks
[публикации](RC30_DEPLOYMENT_RUNBOOK.md) / [восстановления](RC30_BACKUP_RESTORE_PLAN.md).
Это дополнение, не второй стандарт backup. #105 не является зависимостью.
**Действующие CI, FULL и release gates не изменяются этим PR.**

## Минимальная последовательность

1. Готовая правка фиксируется commit/tree. Действующий основной классификатор
   определяет обязательные проверки; shadow остаётся benchmark. Неизвестное,
   SQL, ACL, миграции, интеграции, потенциальная несовместимость — расширенная
   приёмка, даже при небольшом diff. Первый read model #106 требует FULL.
2. Один раз собрать ZIP существующим `tools/build_install.py`. Manifest привязать
   к commit/tree и точным зависимостям; записать SHA256 ZIP и manifest.
   `tools/dev/verify_preview_package.py` проверяет только идентичность пакета,
   состав и CRC/SHA, не заменяет CI/ACL/restore и не разрешает deployment.
3. Установить только этот local_kbacompany на постоянный синтетический dev.
   Corporate/Core не менять. Отдельные credentials/data/DB/internal network;
   cron/queues, email и реальные интеграции выключены. Доказать outbound deny.
   Рабочие stage41/test не использовать как dev и не перезапускать.
4. Адресные тесты + короткий реальный browser smoke + просмотр владельца.
   Сохранить просмотренный ZIP/manifest неизменными. Любое изменение пакета
   аннулирует относящиеся к нему проверки/согласование; повторять затронутое.
5. Только отдельное «публикуй» для точного пакета и актуальное окно. Перед паузой
   проверить baseline/Core/Corporate, gates, квоту/inodes и применимость точки
   восстановления по действующему регламенту. Постоянного разрешения нет.
6. Один оператор применяет проверенную процедуру #102/#103: guards/writer drain,
   сохранить прежний код, атомарная замена модуля, purge, smoke, возврат cron и
   maintenance. При FAIL — прежний код/кеши; новые данные не затирать. Опасные
   изменения требуют отдельного плана совместимости и rollback данных.

Не копировать всю систему для каждой UI-правки. Но отмена свежего capture по
утверждённому регламенту backup пока не согласована: отсутствие такой политики
означает HOLD быстрого production-маршрута, а не молчаливое исключение из gates.
Retentions, RPO, допустимая свежесть и разрешения удаления требуют решения
владельца; здесь не придумываются. Третье хранилище не требуется автоматически.

## Измерение и границы ускорения

Отдельные timestamps: разработка; тесты; очередь/исполнение CI; ожидание просмотра;
установка; smoke. Полное elapsed и elapsed без ожидания владельца показываются
вместе. Цель 3–5 минут для готовой небольшой правки — не достигнутый SLA и не
срок создания функции. Первый замер — только на согласованном небольшом пакете.
Если действующие обязательные gates дольше цели, фиксировать эту причину и
предлагать минимальное изменение отдельным PR с отрицательными тестами. Не
объявлять ожидание FULL необязательным из-за желания ускорить публикацию.

## Что ещё требует решения

- Точный список допустимых presentation-only правок и их обязательных gates.
- Свежесть/состав backup и проверки восстановления для совместимого code-only
  выпуска. Прежние проверенные restore не переносить на несовместимый baseline.
- Новое правило вводится только после независимой приёмки и решения владельца.
  Этот PR не меняет workflow, required checks, rulesets или branch protection.

Приватные адреса, пути, credentials и команды конкретного сервера хранятся в
приватном operator runbook. В Git — обезличенная процедура и тесты пакета.

## Реализованный небольшой инструмент dev

`tools/dev/apply_preview.py` применяет только local_kbacompany на явно помеченный
синтетический dev: проверяет ZIP/manifest, место/inodes, неизменность DB/version,
не допускает второго оператора, сохраняет прежний код и выполняет purge.
Сбой переключения или purge возвращает код без восстановления пользовательских
данных. Затем всё равно обязателен настоящий browser smoke. Инструмент не имеет
режима production и не заменяет проверенный production-оператор #102/#103.
Это dev-only прототип: обработка SIGKILL/host crash требует ручного восстановления
по сохранённым директориям; готовность production-watchdog этим не объявляется.
Отрицательные тесты проверяют повреждение пакета, посторонний компонент, path
traversal, параллельный запуск, drift схемы, сбой stop/rename/purge и сохранность данных.
