## План

1. Отдельный draft PR реализации от того же main. Разрешённый путь `tools/dev_observer/**`. Python stdlib, версионный контракт JSON. Вход по умолчанию offline. Явный GitHub GET только для BMS24, ограниченный набор REST-маршрутов, страницы/лимиты/повторы, без загрузки артефактов.
2. Проекция только типизированных полей. Регистру #198 принадлежит назначение. Текст обсуждений, метки и общий success workflow не служат подтверждением. Подтверждённые зависимости, решения, receipts и Drive revision metadata подаются отдельным курируемым источником. Неизвестная связь блокирует только затронутую задачу.
3. Пять локальных отчётов, проверка точного head/tree/base/main, актуальности, обязательных jobs и независимой приёмки. Блокер, источник и одно следующее действие на запись.
4. Проверки D01/D02/D07/D08/D17/D18, пограничные API-ответы, секреты, ZIP/manifest и receipts. Сверить exit codes, diff, check_reconcile и qa_local, зарегистрировать результаты и передать на отдельное назначение reviewer.

Главный риск — ложный READY из stale/partial, текстового вердикта или самопроверки. При недостатке подтверждённых данных результаты fail closed. DB/ACL/Moodle/privacy продукта и deployment вне путей. Контроль безопасности проекта — минимизация экспортируемых GitHub полей. В BDO-2 можно предложить машиночитаемый реестр и согласованный формат аттестаций.
