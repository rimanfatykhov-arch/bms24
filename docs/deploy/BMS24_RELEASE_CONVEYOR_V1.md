# BMS24 — стандарт конвейера разработки и выпуска (v1, 20.11.2026)

**Статус: принят в PR #144.** Процедура применяется к новым релизам. Для каждой публикации нужно отдельное решение владельца. Требования `docs/05_RELEASE_QA_STANDARD.md` действуют с учётом риска конкретного выпуска.

## 1. Цель

Делать небольшие предсказуемые релизы по цепочке **одна задача → один PR → один immutable install ZIP → постоянный test → приёмка → ТОТ ЖЕ ZIP на production → smoke/receipt**. Не смешивать разработку фичи и бесконечные исследования релизного оператора. Не создавать новый PR/модель только ради повторения уже подтверждённого CI, если новый тест не закрывает наблюдаемый блокер.

**Build once, deploy many:** не собирать пакет повторно между тестом и production. Не копировать живые PHP-файлы вручную и не устанавливать случайный checkout рабочей ветки.

## 2. Роли

- **Claude — разработка:** получает задачу и точный исходный коммит, работает в облачной Git-ветке, возвращает PR и короткий сценарий проверки. Если работа началась с ZIP, Codex переносит изменения в ветку от того же коммита перед запуском CI.
- **Codex — координатор и оператор:** проверяет изменения и CI, берёт подтверждённый ZIP из Actions, ставит его по SSH на `test.bms24.online` и передаёт владельцу на приёмку. По отдельному решению владельца ставит принятый ZIP на production.
- **GitHub — source of truth:** исходные файлы, PR, CI, immutable artifact + SHA256; никакого production config.php, ключей, SQL дампов, moodledata и пользовательских данных.
- **Владелец:** задаёт приоритеты, принимает видимый результат на test, определяет окно и допустимый перерыв для production. Никакого неявного разрешения на потерю данных, включение нового feature flag или destructive restore.

Один назначенный оператор на один production release; любые параллельные deployment процессы блокируются.

## 3. Минимальная единица выпуска

На PR указывается: ID задачи, baseline SHA, только необходимые изменённые файлы, plugin version, DB migration (yes/no), затронутые роли/права/интеграции, тесты PASS/FAIL/NOT RUN. Каждая самостоятельная продуктовая правка идёт отдельным PR; инфраструктурные эксперименты не блокируют продукт без установленной зависимости.

**Режим A — UI/код, без изменений БД:** PHP/JS/CSS lint, целевые тесты, tenant/ACL/CSRF если затронуты, browser smoke в обеих оболочках если требуется; неизменность схемы и версии кода проверить. Предотвратить regression в затронутых страницах.

**Режим B — изменение БД/прав/интеграций:** плюсом real Moodle fresh+upgrade на точной baseline, обе поддерживаемые СУБД по матрице, сохранность данных, компания/ACL, idempotency, rollback/recovery rehearsal. SQL DDL не гарантирует транзакционный откат. При миграции после DDL **запрещён code-only downgrade**. Объём проверки выбирается до начала разработки, расширяется при обнаружении фактического риска, а не ради бесконечного дополнительного стенда.

## 4. Одна сборка и одна идентичность

Когда PR готов:
1. CI проверяет исходный SHA, выполняет обязательные проверки и единожды собирает **install ZIP** с корнем `kbacompany/` (для `local_kbacompany`). ZIP включает только разрешённые файлы этого плагина, без исходного `config.php`, секретов и `moodledata`.
2. Генерирует `manifest.json` с `commit_sha`, plugin version, file list и SHA256 каждого файла; `SHA256SUMS` с SHA256 самого ZIP и manifest. После сборки артефакт НЕ модифицируется.
3. Установочный ZIP берётся из `Release disposable Moodle acceptance → package` в PR задачи. Артефакт `release-install-<run>-a<attempt>` включает `candidate-install.zip`, `manifest.json` и `SHA256SUMS`. Манифест фиксирует точный head, base и попытку сборки.
4. CI artifacts из Actions временны. **Принятый** ZIP/manifest/SHA256 сохранять как неизменяемые release assets в GitHub Releases со ссылкой на commit и приёмку; не копировать бинарные ZIP в каждую ветку Git. Draft/падающий CI не публиковать как «готовый релиз».
5. Установка на test/prod сверяет **тот же ZIP hash**, не только одинаковые названия или plugin version. Если исходный код меняется — это новый SHA, новый пакет, новая приёмка. Никаких «мелких правок прямо в установленном ZIP».

Для установки использовать пакет `release-install-*` из workflow **Release disposable Moodle acceptance** того же PR. В его манифесте `source.pr_head` и `source.checkout_sha` должны совпадать с проверенным коммитом PR, а базовая версия должна соответствовать установленному релизу. Сквозную репетицию установки на двух СУБД запускает этот же workflow для веток `release/*`. Выпуски с миграциями продолжают проходить эту репетицию и проверки восстановления.

Форма квитанции: `release-id | source-sha | zip-sha256 | plugin-version | test-install-time | test-result | production-install-time | production-result`.

Для обычного PR FAST проверяет исходники, а STANDARD добавляет целевые PHPUnit и проверки безопасности. Изменения БД, прав, файлов, интеграций, CI и неопознанные изменения получают FULL с двумя браузерными прогонами и историческими обновлениями БД. Ветки `release/*` продолжают репетицию установки и восстановления. Публикация идёт через приёмку TEST с тем же ZIP.

## 5. Постоянный test (обязательная приёмка)

Сервер для test должен быть изолирован от реальных пользователй и исходящих интеграций; собственные DB, config, moodledata, URL. **Тестировать пакет, а не разрозненные файлы**:
- установить точный ZIP тем же методом, что будет применён на prod; Moodle CLI upgrade, если plugin version требует изменения БД;
- открыть затронутые страницы, проверить вход/доступы ролей и разных компаний, формы и данные;
- проверить новые сценарии, console/network ошибки и журналы;
- для DB-релиза проверить upgrade с точной предыдущей версии и сохранение старых строк, а также восстановление;
- владелец подтверждает пользовательский результат на test в PR/issue, либо явно фиксируется НЕ ПРИНЯТО.

Тестовый сервер сам по себе не доказывает безопасность реального production backup. Для DB-релиза нужен отдельный подтверждённый пробный restore полного DB+code+config+moodledata и безопасный план остановки writes.

## 6. Короткий production gate

Только назначенный серверный оператор после приёмки test проверяет:
- точное совпадение source SHA, ZIP SHA256, версии, состава пакета и миграционного baseline prod;
- существующие версии Moodle/PHP/СУБД/Corporate, актуальную квоту bytes/inodes, отсутствие другого оператора;
- **свежий проверенный backup** всех компонентов, с проверкой независимого восстановления там, где затронуты БД/файлы;
- возможность остановить новые записи web/API/cron/queues и обеспечить непрерывную паузу на время установки; при остановке нескольких workers не полагаться на один PID;
- заранее известный cutover/rollback план, проверенный smoke и назначенного ответственного.

**GO** — все обязательные проверки для конкретного риска PASS, владелец принял test и подтвердил окно, серверный оператор подтвердил выполнение preflight. **HOLD** — любой обязательный FAIL/NOT RUN, drift, недостаток места, неработающий backup/restore, невозможность quiesce writers, неавторизованный feature flag. CI PASS ≠ production GO.

При DB DDL прерывании — maintenance HOLD и phase-aware recovery; не восстанавливать старый backup поверх новых записей без отдельного решения с учётом возможной потери данных.

## 7. Production install и подтверждение

- Снять/задействовать заранее согласованное окно обслуживания, гарантированно остановить записи, сохранить свежий backup.
- Проверить SHA256 загруженного ZIP на production, установить **ТОТ ЖЕ** файл, штатно запустить Moodle CLI upgrade от надлежащего пользователя и выполнить smoke.
- Проверить installed plugin version, схему и отсутствие потерь старых данных, ключевые ACL, корректность cron и интерфейсов; возобновить только проверенные writers по протоколу.
- Зафиксировать фактическую квитанцию с серверными результатами. После этого релиз получает статус **PUBLISHED**; до этого только READY/HOLD. Не утверждать успех на основании GitHub Actions или скриншота PR.

## 8. WIP и скорость конвейера

- **Не более одного активного production-кандидата** на компонент и одного оператора на target. Следующую фичу разрабатывать параллельно, но не смешивать в уже собранный ZIP.
- Работать короткими инкрементами; QA запускается сразу после готовности PR, а не после серии накопленных релизов.
- Отчёт по релизу — один компактный `Release Card` с 4 разделами: `Artifact`, `CI/Test`, `Prod readiness`, `Receipt`. У каждой блокировки одна формулировка, ответственный и проверяемое действие; никаких новых цепочек «подготовительных» PR без конкретного отсутствующего контрольного результата.
- Для правок UI без DB не требовать повторно многодневную миграционную репетицию, если в том же релизе нет новых schema/ACL изменений. Для DB-релиза **не снижать** обязательный restore/quiesce gate ради скорости.
- Старые RC29/RC30 и синтетические V1a–V1j — справочные материалы, не разрешение/запрет на каждый будущий UI-патч.

## 9. База следующей задачи

Перед передачей задачи Claude сверить исходный SHA и версию плагина с квитанцией последней публикации. Если `main` отстаёт, разработку можно начать с опубликованного SHA. До приёмки и выпуска проверьте, что новый PR сохранит весь установленный код после объединения с актуальным `main`.
