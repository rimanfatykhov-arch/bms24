# Issue #106: первая личная сводка дня

Источник требований и нерешённых вопросов — [Issue #106](https://github.com/rimanfatykhov-arch/bms24/issues/106).
План RC34 в [#75](https://github.com/rimanfatykhov-arch/bms24/issues/75) имеет статус PLANNED:
его полный workflow не считается автоматически принятым для этой итерации.

Первый законченный сценарий: сотрудник выбирает день, читает свои задачи со сроком
на эту дату и собственные события отправки результата, открывает исходную задачу.
Это read-only проекция, не сохранённый/отправленный отчёт. Новых таблиц, записей
отчётов, вычисленного дневного времени, уведомлений и прав руководителя нет.

Канонические источники: `task`, `tasklog` (`action=submit`, `actorid`, `details.result`).
Обе стороны соединения ограничены company UUID. Текущий own-scope Task Center,
включая разрешённое position coverage, применяется до загрузки записей.
Отозванное членство закрывает всю проекцию; смена назначения может скрыть старое
событие. Это явно объясняется на экране: исторический снимок распределения задач
не выдумывается. Отправка и приёмка результата не смешиваются.

Дата — гражданский день в Moodle timezone текущего пользователя, интервал
`[local midnight, next local midnight)`, включая 23/25-часовые дни. `factminutes`
показывается только как время задачи целиком; ноль не объявляется подтверждённым
нулём рабочего времени. Раздельная пагинация задач и результатов — по 25 записей.

Будущие черновик, итог дня, препятствия, план следующего рабочего дня и явная
отправка потребуют отдельной канонической сущности/миграции и расширенной приёмки.
Хранить их в task.result, комментариях календаря или localStorage нельзя.

Первая версия содержит серверный read model и SQL: по действующей политике **FULL**,
не FAST. Dev-preview не заменяет CI, матрицу СУБД или разрешение публикации.
Основа выпуска — опубликованный #110 (`43c528d`), сохраняющий #103. Кандидат
объединяет его с read-only сводкой из #107 (`8e503f5`): task_open endpoint/JS/service,
дедупликация, отдельный лимит истории и все 56 BROWSER checks сохранены.
Исторические source-preservation JSON неизменны: новая цепочка продолжает
точные RU/EN hashes опубликованного #110, а сводка добавляет 18 новых ключей.
Новая функциональность определяется сравнением с production head #110.

Ветка `release/day-summary-after110` нужна для действующей package/rehearsal
политики: workflow запускает эти jobs только для `release/*`. Политику не меняем
и неожиданный skip не называем PASS. Новый кандидат требует собственного
ZIP/manifest, CI и затронутого dev-smoke/просмотра. Старый preview ZIP #107
не устанавливается поверх #110. Merge и deployment требуют решения владельца.

Проверки: PHPUnit `daily_report_service_test` (канонический payload, чужая компания,
отзыв, DST, ошибочная дата), реальные адресные проверки на синтетическом Moodle,
браузерные 320/390/1440px, собственные/чужие данные, пустой день и исходная задача.
Статический PASS не является runtime PASS. Актуальные результаты — в PR и Issue.
