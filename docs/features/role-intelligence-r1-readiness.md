# BMS Role Intelligence — R1: карта готовности должностей

**Статус:** первый серверный инкремент, read-only, не развёрнут.
**Ветка:** `feature/role-intelligence-readiness-01`.
**Кодовая база:** `local/kbacompany/version.php` → `1.1.0-rc29`,
`2026101645` в ветке `main`. Устаревшая запись `1642` в
`AGENTS.md` не является фактической версией исходников.

## Архитектурное решение

Не создавать новый независимый справочник должностей.
Использовать существующие canonical объекты:

- `local_kbacompany_position` — активные должности;
- `local_kbacompany_function` — версионируемые функции с опубликованным
  состоянием и привязкой к должности;
- `local_kbacompany_roledna` — версионируемые профили Role DNA.

Новые сервисы: `local_kbacompany\local\role_intelligence_service`.

Уже существующие границы сохраняются: управление и роли — BMS,
компетенции и требования — BMS + Moodle; обучение и аттестация —
Moodle/KBA Corporate; CRM/ERP — внешние адаптеры.

## R1: что реализовано

`role_intelligence_service::snapshot($companyuuid, $userid)`:

1. Нормализует UUID компании, проверяет принадлежность/контекст
   и право `local/kbacompany:managepeople` через текущую политику.
2. **До выборок** накладывает `companyuuid` на Position, Function и
   Role DNA. Запросов вне компании нет.
3. Учитывает только активные должности.
4. Для функции и Role DNA считает только опубликованную ревизию на UUID:
   новый черновик не скрывает предыдущую публикацию; последняя
   архивная ревизия исключает объект.
5. Для каждой должности возвращает признаки:
   - заполнено ли назначение/цель должности (`purpose`);
   - число опубликованных функций;
   - число опубликованных профилей Role DNA;
   - коды недостающих связей.
6. Суммарно подсчитывает `positions`, `basic_links_present`,
   `needs_description` и причины неполноты.

**Важно:** `basic_links_present` означает только присутствие трёх
базовых элементов и **не является доказательством качества должностной
карты**, полноты бизнес-функций или достижения компетенций сотрудником.
Пустая должность не означает плохую работу сотрудника.

Новые таблицы, роли, маршруты, формы, SQL миграции, cron,
интеграции и права доступа **не добавлялись**. Это серверное ядро R1;
страница UI/CRUD будет отдельным инкрементом после тестов.

## Проверки и критерии приёмки

Тест: `local/kbacompany/tests/role_intelligence_service_test.php`

- contract: read-only, company scoped, без дублирующего каталога;
- публикация → черновик: опубликованный объект остаётся;
- публикация → архив: объект исключается;
- одна функция/профиль с разными ревизиями считается однократно;
- чужая компания не попадает в выборку;
- пользователь вне компании не может прочитать данные.

На рабочем окружении с Moodle PHPUnit выполнить:

```bash
php admin/tool/phpunit/cli/init.php
vendor/bin/phpunit --testsuite local_kbacompany_testsuite \
  --filter role_intelligence_service_test
```

И статическую проверку из корня репозитория:

```bash
php -l local/kbacompany/classes/local/role_intelligence_service.php
php -l local/kbacompany/tests/role_intelligence_service_test.php
python3 scripts/qa_local.py
git diff --check
```

Точный тестовый runner Moodle нужно сверить с
версией и конфигурацией целевого тестового стенда; команды выше —
ориентир, **в этом PR они пока не выполнены**.

## Критерии безопасности

- Не изменять production `edu.kzn.mba` или старый
  `test.bms24.online`.
- На втором тестовом `stage41.bms24.online` сначала принять
  HTTPS, Core, плагины и права; не выдавать стадию
  «принято», пока Moodle PHPUnit и ACL не проверены.
- Новая функция не читает имена сотрудников и не меняет
  назначения, компетенции, задачи, метрики или финансовые данные.
- Любые будущие ИИ-предложения должностных карт: только черновики
  и подтверждение уполномоченного человека перед записью.
