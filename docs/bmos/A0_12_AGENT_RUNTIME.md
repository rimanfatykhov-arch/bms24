# BMOS-A0. Agent Runtime (`local_bmosruntime`)

**Статус: PROPOSED.** Решения Q-02, Q-03, Q-14; замечание REV-10. Код не написан.

## 1. Назначение и размещение

- Отдельный Moodle-плагин **`local_bmosruntime`**, выключаемый целиком (настройка + отсутствие плагина = нет
  агентов). Решение Q-02.
- Делает: планирование и исполнение `AgentRun`, сборку контекста через команды R0, вызов моделей через
  `local_kbaai` ModelRouter, разбор ответа в команды, отправку команд в Command Gateway, kill-проверки, учёт шагов
  и лимитов.
- Не делает: не хранит канонические данные домена, не проверяет права (это Gateway), не вызывает провайдеров
  напрямую, не принимает внешних запросов (решение Q-03: до A4 только внутренний Runtime).

## 2. Связи

| Кто вызывает | Что | Через |
|---|---|---|
| Runtime → `local_kbacompany` | Команды API v2 | `agent_command_gateway::execute` (публичный PHP-контракт с версией, как `bms_ai_bridge_service::contract()`) |
| Runtime → `local_kbaai` | Вызов модели | Версионный контракт ModelRouter (`contract()/status()`), без доступа к ключам |
| `local_kbacompany` → Runtime | Нет прямых вызовов | Только статус и kill switch через собственные таблицы BMOS |

## 3. Граница доверия: это не sandbox (REV-10)

Runtime работает в том же PHP-процессе, с теми же правами файловой системы и учётными данными БД, что и весь
Moodle. **Физической изоляции нет.** Изоляция модульная и держится на правилах ниже.

**Разрешено:**
- Только доверенный код из репозитория, прошедший ревью и CI. Никаких загружаемых плагинов агентов, скриптов,
  шаблонов кода в БД.
- Инструменты агента — только PHP-классы, зарегистрированные **в коде** Runtime (allowlist); ревизия определения
  может лишь выбрать подмножество из этого списка. Каждый инструмент = одна команда API v2.
- Сеть — только через адаптер `local_kbaai` к хосту из списка разрешённых (сейчас `api.timeweb.ai`), и только в
  среде, где сеть разрешена владельцем.

**Запрещено (проверяется статически в CI, задача A1-13):**
- `eval`, `exec`, `shell_exec`, `proc_open`, `system`, `passthru`, `unserialize` недоверенных данных,
  динамический `include`/`require`, создание классов или вызов методов по имени из ответа модели.
- `$DB` к таблицам домена `local_kbacompany_*` и `local_kbaai_*` (Runtime пишет только свои таблицы запусков, если
  они у него будут; иначе — ни одной).
- `curl`, `download_file_content`, `file_get_contents('http…')` и любой HTTP помимо адаптера `local_kbaai`.
- Доступ к файлам Moodle (`get_file_storage`) — только через команды Gateway.
- Интерпретация ответа модели как кода, пути, SQL, имени класса или URL. Ответ модели — данные: только JSON по
  схеме команды, разбор fail closed.

**Следствие.** Ошибка в коде Runtime равна компрометации Moodle. Поэтому Runtime минимален, классифицируется CI как
FULL, а физическая изоляция (отдельный процесс/сервис без доступа к БД) — тема отдельного ADR вместе с внешними
агентами (Q-03, A4).

## 4. Kill switch и in-flight вызовы (решение Q-14)

| Момент | Поведение |
|---|---|
| До старта запуска | Запуск не стартует (`cancelled`) |
| Перед каждой защищённой операцией (команда Gateway) | Проверка; выключено → `killed`, команда не выполняется |
| Перед каждым вызовом модели | Проверка; выключено → `killed`, вызова нет, резерв `released` |
| Вызов модели уже отправлен (in-flight) | Прервать HTTP нельзя. Ответ, когда придёт, помечается `discarded_by_kill`; ни одна команда по нему не выполняется; расход регистрируется как `charged`/`unknown`; резерв — по A0_06 §6.1 |
| Очередь | Не исполняется; поставленные команды проверяются заново при любой попытке |

Таймаут вызова модели в профиле ограничивает худшее время срабатывания: оно не больше длительности одного шага
плюс таймаута in-flight вызова. Измеряется в A3.

## 5. Расписание

A1–A2: только ручной запуск человеком. A3: расписание, утверждённое человеком, с лимитом запусков в день.
Самоперезапуск агента и запуск агентом другого агента запрещены до отдельного ADR (A4).
