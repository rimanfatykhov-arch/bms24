# BMOS-A0. Work Principal и Position Occupancy

**Статус: PROPOSED.** Таблицы ниже — проект, а не DDL. Имена таблиц предварительные (ограничение Moodle на длину имени
учтено: префикс `local_kbacompany_` + ≤ 12 символов). Утверждение — после gate A0, реализация — A1.

## 1. WorkPrincipal

Действующее лицо в BMS: тот, от чьего имени выполняется команда и кто записывается в аудит.

| Поле | Тип | Правило |
|---|---|---|
| `uuid` | char(36) | Неизменяемый. Никогда не переиспользуется |
| `companyuuid` | char(36) | Ровно одна компания. Принципал одной компании не действует в другой. Для холдинга — отдельные принципалы |
| `principaltype` | enum | `human` · `ai_agent` · `service_integration`. Не меняется после создания |
| `userid` | int | Только для `human`: Moodle `user.id`. Для остальных — 0 |
| `memberuuid` | char(36) | Только для `human`: `member.uuid` действующего членства |
| `transportuserid` | int | Только для `service_integration`: выделенный транспортный Moodle-аккаунт (ADR-0012). Не автор, не держатель прав. Для `ai_agent` всегда 0 |
| `displayname` | char | Видимое имя с меткой типа («ИИ-агент», «Интеграция») |
| `sponsoruserid` | int | Обязателен для `ai_agent` и `service_integration`: ответственный человек с действующим членством в той же компании |
| `status` | enum | `draft` → `active` ⇄ `suspended` → `revoked` (терминальный); `archived` — только из `revoked` |
| `credentialref` | char | Ссылка на секрет (алиас), никогда не сам секрет. См. §5 |
| `revision` | int | Оптимистичная блокировка |
| `createdby`, `approvedby`, `approvedat`, `revokedby`, `revokedat`, `revokereason`, `timecreated`, `timemodified` | | Аудит жизненного цикла |

**Правила.**
- `human`-принципал не обязан существовать для обычной работы людей. Он создаётся лениво, только когда человеку нужна
  атрибуция в агентной цепочке (спонсор, утверждающий, «от имени»). Права человека по-прежнему считает
  `permission_service`, а не гранты принципала.
- `ai_agent` никогда не связан с Moodle user. Нет логина, пароля, сессии, токена Moodle, ролей компании, capability.
- Смена спонсора — отдельное действие с ревизией и аудитом. Спонсор потерял членство или отозван (ADR-0006) → агент
  автоматически `suspended` при следующей проверке (fail closed), пока не назначен новый спонсор.
- `revoked` необратим. Повторная активация — новый принципал с новым UUID; история старого сохраняется.

**Журнал:** `wpaudit` — неизменяемый (`principaluuid`, `revision`, `event`, `actorprincipaluuid`, `actoruserid`, `details` без секретов, `timecreated`), уникально `principaluuid+revision`.

## 2. Identity и аутентификация по типам

| Тип | Как доказывает себя | Где проверяется |
|---|---|---|
| `human` | Сессия Moodle или токен Moodle этого пользователя | `require_login` / web service + `company_context_service` |
| `ai_agent` | Не аутентифицируется извне в A1–A3. Runtime внутри Moodle создаёт `PrincipalContext` из записи принципала и запуска (`AgentRun`) | Command Gateway: статус принципала, определения, запуска, kill switch |
| `service_integration` | Токен Moodle транспортного аккаунта на выделенном выключенном сервисе + `credentialref` для подписи/секрета канала | Внешняя функция сервиса, затем Command Gateway |

Внешний агентный runtime (вне Moodle) **не предусмотрен до отдельного ADR** (Q-03).

## 3. Position Occupancy

Кто занимает пост и в каком режиме. Второго реестра должностей нет: `positionuuid` → существующий `position.uuid`.

**Люди** остаются в `posassign`. Для чтения строится производное представление `OccupancyView`:
`posassign(active, даты)` → `{principaltype: human, userid, mode: human, source: posassign}`. Новых строк для людей нет.

**Нечеловеческие исполнители** — новая таблица `posoccup`:

| Поле | Правило |
|---|---|
| `uuid`, `companyuuid`, `revision` | Неизменяемый UUID; та же компания, что у поста и принципала |
| `positionuuid` | Активная позиция компании |
| `principaluuid` | Принципал `ai_agent`. `service_integration` пост не занимает |
| `mode` | `agent` — агент исполняет функции поста под надзором; `hybrid` — агент помогает человеку, который в `posassign` того же поста |
| `allowedfunctions` | Явный список `function.uuid+revision` / `poswork.uuid+revision`. Пусто = ничего не разрешено |
| `workloadlimits` | JSON: макс. открытых рабочих элементов, запусков в день, команд в час. Нет значения — нет запуска |
| `supervisoruserid` | Человек-руководитель поста, проверяет результат. Может совпадать со спонсором агента |
| `effectivefrom`, `effectiveto` | UTC; `effectiveto=0` — бессрочно |
| `status` | `proposed` → `approved` → `active` ⇄ `suspended` → `ended` / `revoked` |
| `approvedby`, `approvedat` | Человек с `can_manage_organization`. Для `mode=agent` (самостоятельный пост) утверждающий ≠ создателю и ≠ спонсору агента — принцип двух лиц (решение Q-09) |
| `createdby`, `timecreated`, `timemodified` | |

Журнал `posoccuplog` (неизменяемый, уникально `occupancyuuid+revision`).

**Инварианты.**
1. Занятость агентом не трогает `posassign`, `plannedcount`, штатное расписание и вакантность людей (REV-06).
   Это **два разных показателя**, и они не смешиваются ни в данных, ни в UI:
   - **Вакантность (люди)** — как сейчас: `plannedcount` против активных `posassign`. Агент её не уменьшает.
   - **Функциональное покрытие (агенты)** — сколько функций поста (`function`/`poswork` в `allowedfunctions`) выполняет
     активная занятость агента, например «2 из 5 функций — ИИ-агент». Считается только по `posoccup`.
   - Термин «функциональное покрытие» не равен Position Coverage (замещение людей, `poscover`) и не хранится в `poscover`.
   Вакантная должность с агентом показывается как «Вакантно (людей нет) · функции 2/5 — ИИ-агент», а не «Занято».
2. В `mode=agent` у поста **должен** быть `supervisoruserid`; без него `approved` невозможен.
3. Агент не может быть `primaryid` или `delegateid` в `poscover`. Coverage не переносит работу человека на агента.
4. Занятость не даёт прав. Права — только гранты (§4), и они проверяются вместе с занятостью.
5. Конец занятости (`ended`/`revoked`, `effectiveto` в прошлом) немедленно останавливает команды, привязанные к посту:
   проверка в каждой команде, не только при запуске.
6. Нет ретроактивной миграции: старые задачи, отчёты и назначения не переписываются.

## 4. Grants

Грант описывается в терминах RBAC 2.0 (REV-08): право = `(companyuuid, object_type, action, scope, constraint)`,
**deny by default**. Сверка с RBAC 2.0 — §4.2.

Таблица `wpgrant`: `uuid`, `companyuuid`, `principaluuid`, `command` (имя из A0_04; команда однозначно отображается в
пару `object_type` + `action` RBAC 2.0), `objecttype`, `action`, `scope` (§4.1), `constraint` (JSON, только сужает),
`occupancyuuid` (обязательно для `ai_agent` при scope `position`), `delegationuuid` (только при scope
`delegated_team`), `risklimit` (максимальный класс R0–R3), `ratelimit`, `expiresat` (обязателен, ≤ 90 дней —
решение Q-10), `status` (`active`/`revoked`/`expired`/`superseded`), `grantedby`, `revision`.

**Продление (Q-10)** — только человеком, как новая ревизия гранта с новым `expiresat` ≤ 90 дней от момента
продления. Автопродления нет. Истёкший грант продлить нельзя — выдаётся новый.

### 4.1 Scopes для принципалов

| Scope агента | Объекты | Соответствие RBAC 2.0 | Этап |
|---|---|---|---|
| `own` | Собственные объекты принципала: свои рабочие элементы, свои предложения, свой отчёт, свои запуски | `own` | A1 |
| `position` | Объекты поста занятости: задачи с `dutypositionuuid` = пост, метрики поста | `assigned` (объект назначен посту) | A1 |
| `explicit_object` | Явный список UUID, выданный человеком | `explicit_object` | A1 |
| `delegated_team` | Объекты команды руководителя, делегированные помощнику (REV-07, Q-11) | `team` (ограниченно, см. ниже) | A3 |
| `department`, `subtree`, `company` | — | В RBAC 2.0 не активны (fail closed) | Агенту не выдаются до отдельного ADR |

**Делегированный scope команды (`delegated_team`, REV-07, решение Q-11).** Нужен помощнику руководителя
(первый агент, MR3-D57), чтобы читать задачи и отчёты команды.
- Отдельная запись `wpdeleg`: `uuid`, `companyuuid`, `delegatoruserid` (руководитель), `principaluuid` (агент),
  `positions` (явный список `position.uuid` подчинённых постов, не «всё поддерево»), `objecttypes` (`task`,
  `daily_report`, `indicator`), `actions` (только `view` в A3), `expiresat` ≤ 90 дней, `status`, `revision`.
- **ACL на каждый объект, на каждый вызов:** объект доступен, только если одновременно (1) пост объекта есть в
  `positions`; (2) **делегирующий руководитель сейчас сам имеет** право `view` на этот объект по `permission_service`;
  (3) у агента активный грант с `delegationuuid`; (4) объект не личный (личные задачи, личные сообщения, защищённые
  вложения, приватные кадровые и owner-данные исключены всегда).
- Это пересечение, а не наследование: агент никогда не получает больше, чем руководитель, и не получает права
  спонсора как таковые. Потеря права руководителем, его членства или отзыв (ADR-0006) немедленно лишает агента доступа.
- Делегирует только сам руководитель; утверждает второй человек с `can_manage_organization` (Q-09).

### 4.2 Сверка с RBAC 2.0

Источник: Drive «BMS24 — RBAC 2.0 — роли доступа, матрица объектов и границы разрешений — RC28» и код
(`aclrole`, `aclgrant`, `aclassign`, `aclaudit`, `permission_service`).

| Правило RBAC 2.0 | Как соблюдается для принципалов |
|---|---|
| Deny by default; неопределённая операция запрещена | Нет гранта — нет команды; команда без пары `object_type/action` не регистрируется |
| Право = companyuuid + object_type + action + scope + constraint | Та же форма в `wpgrant`; словарь `object_type`/`action` RBAC 2.0 переиспользуется (`task`, `indicator`, `communication`, `position`, …; `view`, `create`, `edit`, `comment`, `approve`, …) |
| Scopes не равны друг другу без формального owner resolver; department/subtree не активны | Агенту доступны только `own`, `assigned` (`position`), `explicit_object` и ограниченный `team` (`delegated_team`) |
| Персональные документы, кадровые сведения, private owner contour не наследуют broad grants | Исключены из любого гранта агента (A0_03 T07) |
| Явные запреты безопасности и системные способности не преодолеваются грантами | Отзыв (ADR-0006), kill switch, статус принципала проверяются до гранта; грант их не отменяет |
| Назначение ролей — по стабильному Moodle ID, без автоматического назначения | Роли доступа BMS (`aclassign.userid`) агенту **не назначаются**. Гранты принципалов — отдельный реестр |
| Защита от самоэскалации; управление грантами отдельно от `manageorganization` | Принципал не выдаёт гранты; выдача — человек; для `delegated_team` — двумя людьми |
| Аудит изменений ролей и грантов | `wpaudit` + `aclaudit`-подобная запись по каждому гранту и делегированию |
| Методы `permission_service::can(company, userid, object_type, action, resource)` | Для принципалов — параллельный `principal_permission::can(PrincipalContext, object_type, action, resource)`; human-метод не меняется |
| Роль «Бизнес-инженер BMS» (интегратор) — Moodle user | Не путать с `service_integration`: интегратор — человек с ролью доступа, а не принципал-интеграция |

Расхождение, которое нужно держать в уме: в RBAC 2.0 включено end-to-end только семейство «Управленческие циклы»;
по задачам и остальным объектам действуют прежние политики `permission_service`. Поэтому проверка объекта для
агента опирается на существующие сервисные проверки (`task_service::can_view_task` и т. п.) плюс грант, а не на
ещё не включённые scopes RBAC 2.0.

**Правила.**
- Гранта по умолчанию нет. Набор шаблонов (например «агент-аналитик») — просто удобство UI; каждый грант — отдельная строка.
- Грант не может превышать риск-класс команды (A0_04 §4) и никогда не включает R4.
- Выдаёт только человек с `can_manage_organization` (для `service_integration` — также организационный менеджер,
  как в ADR-0012). Принципал не выдаёт гранты, в том числе себе.
- Отзыв гранта, занятости, принципала, членства спонсора или kill switch проверяется **в каждой команде**, включая
  уже поставленные в очередь (A0_03 T09).

## 5. Credentials reference

- В БД — только `credentialref` (алиас) и `credfingerprint` (первые 12 символов SHA-256 секрета) + `rotatedat`.
- Сам секрет — у оператора (Codex) в `config.php` вне Git или во внешнем vault (Q-05). Секрет не попадает в промпт,
  контекст, шаблон, ответ API, журнал, бэкап-манифест, stdout CI.
- Ротация: новый секрет под тем же алиасом, отпечаток меняется, событие в `wpaudit`. Отзыв: удалить секрет и перевести
  принципала в `suspended`/`revoked`; запросы с отозванным секретом — отказ.
- Один ключ провайдера на всё — запрещено (#76). Решение Q-06: отдельный ключ Timeweb на компанию + квоты BMS.
- Решение Q-05: сначала защищённая серверная конфигурация вне Git (у оператора), затем vault; в БД — только алиас и
  отпечаток.

## 6. Семантика задач и назначений (сохраняется)

| Поле / механизм | Значение | Что меняется с агентами |
|---|---|---|
| `task.assigneeid` | Исходный Moodle user-исполнитель | Ничего. Агент сюда не пишется никогда |
| `task.dutypositionuuid` | Задача поста. Пусто = личная задача | Ничего. Личная задача агенту недоступна (A0_03 T07) |
| `effective_executor` | Approved coverage между людьми | Ничего |
| Работа агента над задачей | — | Отдельный рабочий элемент `work` (A0_04 §5): задача поста + агент + поручивший человек. Результат — **предложение** (в том числе предложенный комментарий), принимает человек. Собственный результат агента не меняет каноническую задачу (REV-05). Прямой комментарий агента — только после ворот атрибуции W1 (A0_06 §5.1) |
| История назначений | `posassign`, `poscovaudit`, `tasklog` | Не переписывается. Действия агента — в отдельной атрибуции (A0_06 §5) |

## 7. Атрибуция в аудите (общее правило)

Каждое действие нечеловеческого принципала записывает: `actorprincipaluuid`, `actorprincipaltype`, `onbehalfofuserid`
(для `service_integration` — сопоставленный человек, как в ADR-0012; для `ai_agent` — 0, агент действует сам от себя),
`sponsoruserid` на момент действия, `occupancyuuid`, `grantuuid`, `agentrunuuid`, `approvaluuid` (если было),
`correlationid`. В UI действие агента всегда видно как действие ИИ, а не человека (#76 §D).

Пока совместимость атрибуции не доказана (ворота W1, A0_06 §5.1), агент не пишет в существующие канонические
объекты и журналы вообще: только в собственные новые таблицы (предложения, рабочие элементы, запуски).
