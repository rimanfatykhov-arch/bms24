# BMOS-A0. Модель безопасности агентов и модель угроз

**Статус: PROPOSED, ревизия 3** (27.11.2026: блокеры 1 и 3 проверки Codex). Принцип — **fail closed**: при сомнении команда отклоняется до любого побочного эффекта, отказ
записывается в аудит отдельной транзакцией (как deny-audit в ADR-0012).

## 1. Активы и границы доверия

- **Активы:** данные компаний (задачи, отчёты, сообщения, метрики, персональные данные сотрудников), права людей,
  история и аудит, бюджет ИИ компании, секреты провайдеров, доверие к атрибуции («кто это сделал»).
- **Доверенные:** серверный код BMS, проверки в Command Gateway, решения уполномоченных людей.
- **Недоверенные:** любой текст модели; любые данные из MAX, email, документов, вложений, комментариев, отчётов, внешних
  сайтов; параметры внешних вызовов; содержимое контекста, даже если оно из BMS.
- **Граница:** между Runtime/моделью и доменом стоит только Command Gateway. У Runtime нет SQL-доступа к таблицам
  домена и нет пользовательской сессии.
- **Это не sandbox (REV-10).** Runtime (`local_bmosruntime`) работает в том же PHP-процессе и с теми же учётными
  данными БД, что и Moodle. Изоляция модульная: она держится на том, что весь код Runtime — доверенный, проверенный
  и статически ограниченный. Ошибка в коде Runtime равна компрометации Moodle. Границы и запреты — A0_12 §3.

## 2. Обязательная цепочка проверок команды

Цепочка применяется к нечеловеческим принципалам (`ai_agent`, `service_integration`). Команды людей идут
существующим человеческим путём (`permission_service`, capability, предикаты сервисов) и этой цепочкой не
ограничиваются; в частности, класс R4 для людей означает «только человек», а не запрет.

Порядок фиксирован. Первая неудача — отказ, дальше не проверяется. Ревизия 3 (по FAIL Codex 27.11.2026): шаг риска
только классифицирует и отказывает; запрос на подтверждение создаётся после текущего ACL объекта и проверки
повтора; повтор распознаётся **после** проверки текущих прав и отзыва, но **до** lifecycle и revision — исходная
команда сама изменила состояние и ревизию объекта.

1. **Identity:** принципал существует, `active`, тип допускает команду (команда есть в реестре этого типа).
2. **Kill switch:** глобальный → компания → определение агента → принципал → запуск. Любой выключен — отказ.
3. **Company:** `companyuuid` команды = компания принципала = компания каждого объекта. Компания не отозвана для спонсора.
4. **Sponsor:** у `ai_agent`/`service_integration` действующий спонсор с членством без отзыва (ADR-0006).
5. **Occupancy:** для scope `position` — активная занятость на дату, пост активен, функция в `allowedfunctions`.
6. **Grant:** активный, не истёкший грант на команду и scope (для `delegated_team` — ещё и активное делегирование).
7. **Risk (только классификация и отказ, без побочных эффектов):** риск команды ≤ `risklimit` гранта, иначе
   `risk_forbidden`. R4 у нечеловеческого принципала → `risk_forbidden` (такие команды и так отсутствуют в реестре
   типа). R3 в A1 → `approval_unavailable` без исполнения (REV-01). R3 с A2 → помечается «нужно подтверждение»;
   запрос на этом шаге **не создаётся**.
8. **Object ACL (текущий, по scope гранта)** — principal-aware проверка `principal_object_acl` (A0_02 §4.3):
   - всегда: объект принадлежит компании; объект не личный и не защищённый (личные задачи с пустым
     `dutypositionuuid`, личные сообщения, защищённые вложения, приватный календарь, кадровые и owner-данные);
   - `own`: объект создан этим принципалом (`work`, `proposal`, свой отчёт, свои запуски);
   - `position`: пост объекта = пост **текущей** занятости принципала (для `task.*` — `dutypositionuuid`);
   - `explicit_object`: UUID объекта в списке гранта;
   - `delegated_team` (A3): пост объекта в `wpdeleg.positions` **и** делегирующий руководитель сейчас сам имеет
     право на это действие с объектом; права спонсора и `userid=0` в пользовательские проверки не передаются.
9. **Idempotency / replay** по `cmdidem` (принципал + ключ). Состояния записи и ответ на повтор — §2.1. Тот же ключ
   с другим digest payload → `idempotency_conflict` в любом состоянии. Отклонённая на шагах 1–8 команда записи не
   создаёт — повтор проверяется заново.
10. **Approval (только R3, с A2):** записи нет → в одной транзакции создаются `approvalreq` (`pending`) и `cmdidem`
    (`pending_approval`, ссылка на запрос); ответ `pending_approval`. Исполнение после решения — §2.2.
11. **Lifecycle:** состояние объекта допускает переход.
12. **Revision:** `expectedrevision` = текущая ревизия; иначе `stale_revision`, без повтора.
13. **Rate:** лимиты гранта, занятости, агента, компании (повтор из шага 9 лимит не расходует).
14. **Budget:** для команд, вызывающих модель, — резерв бюджета (A0_06 §6).
15. **Execute + record:** мутация, запись `cmdidem` (`executed`, digest, результат), атрибуция `wpattr`, outbox —
    **в одной транзакции БД**. Отказ любой части — откат всего, ключ не сохраняется. Отказ пишется в audit
    отдельной транзакцией после отката.

Шаги 1–15 выполняются под одним lock (принципал + ключ, по образцу `communication_write_gate` из #178), чтобы
отзыв не проскочил между проверкой и записью, и чтобы два параллельных запроса с одним ключом не выполнили мутацию
и не создали два запроса на подтверждение: второй ждёт lock и на шаге 9 получает сохранённое состояние.

### 2.1 Состояния ключа и ответ на повтор

| Состояние `cmdidem` | Повтор с тем же digest (после шагов 1–8) | Повтор с другим digest |
|---|---|---|
| нет записи | Обычное выполнение (шаги 10–15) | — |
| `pending_approval` (A2) | Тот же `approval_uuid`, статус `pending_approval`; второй запрос не создаётся | `idempotency_conflict` |
| `executed` | Сохранённый результат, `idempotent_replay=true`; lifecycle и revision не проверяются | `idempotency_conflict` |
| `failed` (исполнение после подтверждения не удалось) / `rejected` / `expired` / `cancelled` | Сохранённый итог без исполнения; новая попытка — только с новым ключом | `idempotency_conflict` |

Повтор после отзыва гранта, занятости, делегирования, принципала или kill switch падает на шагах 1–8 — сохранённый
результат не раскрывается.

### 2.2 Исполнение после подтверждения (A2)

1. Решение человека (`approve`) пишется отдельной транзакцией: `approvalreq.status` `pending → approved` условным
   обновлением с `expectedrevision`; второе решение получает `stale_revision`.
2. Исполнение — отдельная транзакция под тем же lock (принципал + ключ): повторно шаги 1–8 (текущие права, отзыв,
   kill switch, ACL), затем проверка статуса запроса, шаги 11–15. Шаг 10 не выполняется: запрос уже есть и
   повторно не создаётся.
3. **Защита от второго исполнения:** условный переход `approved → executed` (`WHERE status='approved'`) в той же
   транзакции, что мутация и `cmdidem → executed`; уникальность `executionaudituuid`. Второй исполнитель
   (повтор задания, параллельный вызов) видит `executed` и возвращает сохранённый результат.
4. Неудача на шагах 1–8 или 11–12 → `approvalreq` и `cmdidem` получают `failed` с кодом; автоповтора нет; агент
   может создать новый запрос с новым ключом.
5. Сбой между решением и исполнением оставляет `approved`; идемпотентный исполнитель доводит его по тем же
   правилам, пока не истёк срок запроса.

**Негативные тесты атомарности (обязательны, S30, S31, S16b):** падение после мутации до записи ключа → откат
мутации; параллельные запросы с одним ключом → одна мутация и не более одного запроса на подтверждение; повтор
после отзыва гранта → отказ, а не сохранённый результат; повтор с иным payload → `idempotency_conflict`; повтор после
изменения объекта другим человеком → сохранённый результат, без перезаписи; R3 вне ACL → отказ до создания запроса;
повторное утверждение → одно исполнение; отзыв между утверждением и исполнением → `failed`, без мутации.

## 4. Что всегда требует человека (A1–A4)

Платежи и финансовые проводки; изменение прав, ролей, членства, грантов, занятости; внешняя публикация; удаление и
архивирование; утверждение отчётов, задач, планов и решений; назначение и переназначение людей; отправка сообщений
людям от имени человека; любые действия в другой компании. Это класс **R4**: для нечеловеческих принципалов —
запрещён, даже с подтверждением, пока отдельный ADR не разрешит узкую политику; для людей — команды «только
human», которые проверяются существующими человеческими правами (A0_04 §4).

## 5. Kill switch и восстановление

- Уровни: глобальная настройка платформы, компания, определение агента (все ревизии), принципал, отдельный запуск.
- Действие (решение Q-14): новые запуски не стартуют; идущий запуск останавливается **до следующей защищённой
  операции или вызова модели** (проверка перед каждой командой и каждым вызовом модели); очередь не исполняется.
- **In-flight вызов модели** (HTTP-запрос уже отправлен) прервать нельзя. Его ответ помечается `discarded_by_kill`,
  ни одна команда по нему не выполняется, расход регистрируется (провайдер мог списать), резерв обрабатывается по
  правилам неопределённого исхода (A0_06 §6.1). Подробно — A0_12 §4.
- Время срабатывания измеряется в A3 (длительность одного шага + таймаут in-flight вызова).
- Включение обратно — только человеком, с причиной в аудите.

## 6. Логи и хранение

Хранить: метаданные запусков, команд, решений, расхода; хеши входа и выхода; ссылки на объекты. Не хранить по
умолчанию: секреты, заголовки авторизации, полные промпты, полные ответы модели с ПДн, скрытые рассуждения.
Журнал провайдера (Timeweb, 90 дней, без текстов) не заменяет аудит BMS.
