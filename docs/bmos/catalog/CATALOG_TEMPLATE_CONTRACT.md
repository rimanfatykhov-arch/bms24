# CAT-0. Логический контракт шаблона каталога

**Статус: PROPOSED.** Это логический контракт, **не утверждённый DDL**. Имена полей — рабочие; физическая схема
определяется в CAT-1/CAT-2 после решения OD-01/OD-02.

## 1. Catalog Template (стабильная запись)

| Поле | Тип | Правило |
|---|---|---|
| `catalog_id` | UUID | Глобальный, не меняется; не является UUID компании или принципала |
| `code` | Строка `BMS-AGENT-NNN` | Стабильный код; не переиспользуется после вывода из каталога |
| `title` | RU/EN | Человекочитаемое название роли («ИИ-помощник руководителя») |
| `category` | Перечень | `management` · `owner` · `analytics` · `architecture` · `audit` · `economics` · `office` · `sales` · `hr` · `methodology` · `mentoring` · `process` (OD-04) |
| `purpose` | Текст | Назначение роли |
| `template_owner` | Роль методологии | Владелец шаблона (не Moodle user ID в глобальном шаблоне; ведущий назначается при утверждении) |
| `current_revision` | Целое | Последняя опубликованная редакция; черновик не считается текущей |
| `status` | Производное | Статус зрелости текущей редакции (§3) |

## 2. Catalog Template Revision (неизменяемая после публикации)

| Поле | Содержание | Правило |
|---|---|---|
| `catalog_id`, `revision` | Ключ | Пара уникальна; опубликованная редакция не редактируется — только новая |
| `editorial_state` | `draft` → `published` → `superseded` / `withdrawn` | `withdrawn` — опубликованная редакция отозвана из-за дефекта; история сохраняется |
| `maturity` | `CONCEPT` / `DESIGNED` / `VALIDATED` / `COMPATIBLE` / `DEPRECATED` | §3; не подменяет статусы AgentDefinition, Occupancy, Grants и AgentRun |
| `ckp` | Текст | ЦКП: результат, получатель, критерий (DNA-001 §3.2) |
| `results` | Р1…Рn | Объект, готовое состояние, получатель, критерий, контрольная точка |
| `role_dna_ref` | Код и версия проекта Role DNA в пакете | Переносимый проект; не запись `roledna` компании |
| `aep_ref` | Код и версия требований AEP в пакете | 11 блоков AEP-001; без конкретных модели, ключа, UUID и лимитов |
| `recognition_pack_ref` | Код и версия набора кейсов | Кейсы C/B, рубрики, трассировка к A0_09 |
| `required_tools` | Список команд A0_04 | Имя команды, риск-класс, scope, этап; только команды контракта A0_04 (без выдуманных API) |
| `context_requirements` | По каждому Р | Источник (команда), поля DTO (минимизация), период, свежесть; запрещённые классы данных |
| `grant_requirements` | Список | Запрашиваемые пары `object_type/action` + scope + `risklimit`; **запрос**, не выдача |
| `risk_classes` | Множество | Разрешённые классы для allowlist (например R0, R1, R2-own); R3/R4 — явно перечислены как исключённые |
| `required_modules` | Список | Плагин и минимальная версия контракта (`local_kbacompany`, `local_bmosruntime`, `local_kbaai`, версии контрактов A0) |
| `min_bmos_stage` | `A1`…`A4` | Минимальный этап, начиная с которого шаблон можно адаптировать; по каждой функции может быть свой этап |
| `model_requirements` | Возможности | Структурированный ответ, размер контекста, локаль, класс профиля; не имя модели |
| `constraints` | Текст и флаги | Ручной запуск, синтетика, без внешней сети, без записи в существующие объекты и т. п. |
| `admission_criteria` | Ссылки на кейсы и ворота | Что должно быть PASS до допуска; автоматического проходного балла нет |
| `compatibility` | Список проверок | Версия платформы, exact SHA, набор проверок, результат PASS/FAIL/NOT RUN, дата, проверяющий |
| `adaptation_rules` | Правила | Что компания обязана заполнить, что может сузить, что не может расширить (§4) |
| `change_log` | История | Причина, автор, дата, затронутые блоки, анализ влияния |
| `package_digest` | SHA-256 | Хеш канонического пакета редакции; провенанс экземпляров ссылается на него |
| `source_docs` | Ссылки | Документы методологии (Drive/GitHub) с версиями |

**Запрещено в шаблоне:** UUID компаний, сотрудников, постов, принципалов и занятостей; Moodle user ID; имена
реальных людей; клиентские данные и примеры из реальных компаний; ключи, токены, `credentialref`; конкретные лимиты
бюджета; действующие гранты; расписания запусков.

## 3. Статусы зрелости

| Статус | Значение | Условие перехода |
|---|---|---|
| `CONCEPT` | Идея роли | Есть код, название, назначение, категория |
| `DESIGNED` | Подготовлен паспорт | Есть ЦКП, Р1…Рn, проекты Role DNA, AEP и Recognition Pack, команды сверены с A0_04 |
| `VALIDATED` | Подтверждён конкретный набор проверок шаблона | Перечисленные кейсы Recognition Pack прогнаны на синтетике на указанной редакции, результаты и проверяющий зафиксированы |
| `COMPATIBLE` | Подтверждена совместимость с конкретной версией платформы | Для пары «редакция шаблона × версия платформы (exact SHA)» команды доступны, ворота этапа PASS; статус привязан к этой паре |
| `DEPRECATED` | Редакция больше не рекомендуется | Решение владельца шаблона; новые адаптации запрещены, действующие экземпляры не меняются автоматически |

`VALIDATED` и `COMPATIBLE` — свидетельства, а не разрешения: они не дают права адаптировать или запускать агента
без всех шагов мастера (CATALOG_LIFECYCLE §3).

## 4. Правила адаптации

- Компания **обязана** выбрать существующий пост, сопоставить Р/Д с функциями поста, назначить людей (спонсор,
  руководитель, утверждающий), выбрать профиль модели из своего реестра, задать лимиты бюджета, выдать гранты.
- Компания **может сузить**: исключить результаты, сократить контекст, ограничить инструменты, снизить риск-класс,
  уменьшить лимиты, сократить сроки.
- Компания **не может расширить** через адаптацию: добавить команду вне `required_tools`, повысить риск-класс,
  расширить scope, включить R3/R4, если их нет в шаблоне. Расширение — только новой редакцией шаблона или
  отдельным решением владельца с новым анализом безопасности.
- Адаптация создаёт **черновики** компанейских сущностей. Ни один шаг адаптации не выдаёт права и не запускает агента.

## 5. Формат пакета (проект для CAT-1)

Пакет редакции — каталог файлов: `template.json` (manifest), `role_dna.md`, `aep.md`, `recognition/` (кейсы и
рубрики), `CHANGELOG.md`. Пример manifest — [AGENT-001/template.json](AGENT-001/template.json). Канонизация, подпись и
место хранения — решения OD-01/OD-02.
