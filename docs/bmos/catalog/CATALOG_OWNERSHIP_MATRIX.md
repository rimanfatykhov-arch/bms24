## 2. Обоснование физического владения

1. **Почему источник — Git.** Шаблон глобален и одинаков для всех компаний. Его изменения должны проходить ревью,
   иметь неизменяемую историю и точный хеш. Git и PR дают это без новой административной формы. Это также
   соответствует MR3-D81/D82: GitHub — технический источник истины, Drive — методологический.
2. **Почему копия на сайте — в `local_bmosruntime`.** Каталог — часть платформы агентов и выключается вместе с ней
   (Q-02). `local_kbacompany` остаётся владельцем компанейских доменных сущностей и не получает глобальный реестр.
   Альтернатива — хранить каталог только в коде пакета без таблиц (CAT-1/CAT-2 так и начинаются; таблица нужна
   только если понадобится импорт без выпуска плагина). Решение — OD-01.
3. **Почему экземпляры — в существующих таблицах.** Role DNA, функции, посты и компетенции уже имеют
   компанейских владельцев и права. Новая копия создала бы второй реестр должностей и требований. Поэтому мастер
   создаёт черновики в существующих сущностях и ссылается на шаблон полями провенанса.
4. **Почему результаты Recognition не в каталоге.** Это компанейские доказательства о конкретном исполнителе, с
   доступом по ACL и сроками хранения. Каталог хранит только переносимые кейсы и рубрики.
5. **Почему Marketplace — BMS Cloud.** Коммерческое распространение, лицензии и тарифы — контур BMS Cloud
   (`bms_tariff_catalog_service`: «нет второго локального реестра подписок»).

## 3. Что каталог не дублирует

Второй реестр должностей, функций, компетенций, процессов, метрик, провайдеров, моделей; поля `AgentDefinition`;
гранты; занятости; запуски; результаты Recognition; человеческие назначения (`posassign`), замещения (`poscover`),
`task.assigneeid`, `dutypositionuuid` и историю людей.
