# BMOS-A0. Roadmap A0–A4, backlog A1–A4 и план миграций

**Статус: PROPOSED.** Порядок этапов — по MASTER ROADMAP 3.0 (BMS-09): A0 архитектура → A1 ограниченный
API/identity → A2 отчётность → A3 помощник руководителя → A4 смешанная команда. Сроки и номера RC не назначаю.
Оценки — относительные (S/M/L), без дат.

## 3. План миграций (без DDL «утверждён»)

1. **Ничего не мигрируется в A0.** `install.xml`, `upgrade.php`, `version.php`, `access.php`, `services.php` не меняются.
2. **A1 — только добавление.** Новые таблицы, без изменения существующих колонок и ключей. Нет backfill: людям не
   создаются принципалы и занятости заранее. Всё выключено настройкой `local_kbacompany/bmos_enabled=0`.
3. **Номер версии** — по чеклисту версии на момент A1 (сейчас `main` = 2026112301; #179 занимает 2026112500). Номер
   RC не назначаю.
4. **MAX (#179).** Если #179 принят раньше A1: шаг upgrade создаёт `wprincipal(service_integration)` для каждой
   существующей строки `inbconn` и записывает ссылку; `principaluserid` остаётся (совместимость), чтение переходит на
   принципала. Если #179 не принят — его схема сразу ссылается на `wprincipal` (согласовать с исполнителем #179).
5. **A2 — отчёты.** По решению Q-08: вариант «отдельная сущность» не трогает `dreport*`; вариант «общая таблица»
   требует смены уникального ключа на production-таблице — режим B, репетиция upgrade и отката на копии.
6. **Откат.** После DDL code-only downgrade запрещён (конвейер §3). Откат функциональности — выключателем; таблицы
   остаются пустыми или неиспользуемыми.
7. **Удаление/приватность.** Privacy provider: принципалы не являются субъектами ПДн, но `sponsoruserid`,
   `approvedby`, `onbehalfofuserid` и т. п. — данные пользователей; экспорт и удаление по существующим правилам.
