# BMOS-A0. Human Approval Contract

**Статус: PROPOSED.** Ревизия 2 (25.11.2026): REV-01, решение Q-09. Ревизия 3 (27.11.2026): блокер 1 проверки
Codex — порядок создания запроса, повтор, исполнение после подтверждения.

**Этап.** Approval-поток (`ApprovalRequest`) реализуется в **A2**. В A1 любая команда R3 отклоняется
`approval_unavailable` без исполнения и без побочных эффектов (сценарий S16a). Сценарий утверждения S16b
обязателен только для A2 (REV-01).

## 1. Когда нужно подтверждение человека

- Всегда для класса **R3** (изменение чужой работы: статус, срок, описание задачи поста, черновик задачи → каноническая
  задача и т. п.).
- Для **R2** — по `riskpolicy` ревизии определения. Решение Q-09: сначала разрешены только собственный результат и
  предложения агента; прямые комментарии — только после ворот атрибуции W1 и отдельного решения владельца.
- **R4** не подтверждается — запрещён агенту (A0_03 §4).

## 2. ApprovalRequest

`approvalreq`:

| Поле | Содержание |
|---|---|
| `uuid`, `companyuuid`, `revision` | |
| `requesterprincipaluuid`, `agentrunuuid`, `correlationid`, `idempotencykey` | Кто и в каком запуске просит |
| `command`, `targettype`, `targetuuid`, `targetrevision` | Что будет сделано и над чем |
| `payloaddigest`, `payload` | Точный payload; хранится в домене, без секретов; изменение = новый запрос |
| `summary`, `rationale`, `provenance` | Что предлагается, краткое обоснование, источники (недоверенные помечены) |

| `approverrule` | `post_supervisor` · `task_reviewer` · `capability:<name>` · `named_user` |
| `approveruserid` | Назначенный человек (если правило даёт одного) |

## 3. Правила

1. **Утверждает только человек** с действующим членством и правом по `approverrule`. Принципал не утверждает свой
   запрос; `service_integration` и `ai_agent` не утверждают никакие.
2. **Два лица (решение Q-09).** Для R3 и для самостоятельного поста (`mode=agent`) утверждающий ≠ тот, кто поручил
   работу (`work.assignedby`) и ≠ спонсор, если спонсор поручил эту работу. Спонсор-поручивший не утверждает
   собственное R3. Нет второго уполномоченного человека — запрос истекает, а не исполняется.
3. **Когда создаётся запрос.** Только после шагов 1–9 цепочки A0_03 §2: текущие права, отзыв, kill switch, ACL
   объекта и проверка повтора. R3 вне ACL отклоняется без создания запроса. Запрос и ключ `cmdidem`
   (`pending_approval`) пишутся в одной транзакции под lock.
4. **Перепроверка при исполнении.** После `approved` исполнение идёт по A0_03 §2.2: повторно шаги 1–8, проверка
   статуса запроса, шаги 11–15; новый запрос не создаётся. Изменилась ревизия объекта — `failed: stale_revision`,
   автоповтора нет; агент может создать новый запрос с новым ключом.
5. **Отзыв во время ожидания.** Отзыв принципала, гранта, занятости, делегирования или kill switch переводит все
   `pending` в `cancelled`; отзыв между `approved` и исполнением даёт `failed` на повторных шагах 1–8.
6. **Идемпотентность.** Один `idempotencykey` команды — один запрос. Повтор того же ключа при `pending` возвращает
   тот же `approval_uuid`; при `executed` — сохранённый результат; при `failed`/`rejected`/`expired`/`cancelled` —
   итог без исполнения (A0_03 §2.1). Повторное утверждение не исполняет команду второй раз.
7. **Конкуренция.** `approve`/`reject` с `expectedrevision`; второе решение — `stale_revision`.
8. **Видимость.** Утверждающий видит payload, источник, обоснование, риск и метку «ИИ». Недоверенный текст
   отображается как цитата, а не как инструкция.
9. **Аудит.** Решение пишет `wpattr` (actor = человек) и outbox `bmos.approval.decided`; исполнение — `wpattr`
   (actor = агент, `approvaluuid` заполнен).

## 4. Приёмка результата и отчётов

- Рабочий элемент агента (`work`) принимает или возвращает человек (`work.accept`/`work.return`, A1). Принятие
  результата не меняет каноническую задачу; если нужна правка задачи — это отдельная R3-команда (A2) или действие
  человека.
- Предложенный комментарий агент не публикует сам: человек публикует его от своего имени или отклоняет (A1).
- Отчёт агента (A2) принимает или возвращает только уполномоченный человек; принятая версия не переписывается.
- Принятие результата не означает внешнюю публикацию, оплату или закрытие процесса (PR #77 §4).
