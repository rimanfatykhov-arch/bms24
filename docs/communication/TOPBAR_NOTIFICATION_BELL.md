# Колокольчик уведомлений в верхнем меню и звук (owned shell)

Статус: кандидат, связан с #145. Не принят, не опубликован. База: `main` 36cc7dd.
Ветка `release/comm-ux-fixes-20261122` (#152) не затронута.

## 1. Аудит: что переиспользуем

| Что | Где | Решение |
|---|---|---|
| Реестр уведомлений | таблица `local_kbacompany_commnotif` | единственный источник; второй реестр не создаётся |
| Генерация | `communication_service::create_notification` (сообщения, упоминания, приглашения, задачи), `ensure_system_notification` (calendar_*, bp_decision, dailyreport_*; cron) | без изменений |
| Прочтение | `mark_notification_read` (форма «Отметить прочитанным» в центре); открытие разговора — `mark_read` треда | без изменений; колокольчик ничего не отмечает |
| Видимость | `communication_service::context()`: контекст компании → активный участник треда → текущий доступ к объекту (`communication_object_service::describe`) | вынесено в `notification_source_visible()`; тем же правилом пользуются центр, счётчики shell и колокольчик |
| Счётчик | раньше три копии цикла: `context()`, `communication_center_service::shell_counters`, live | одна функция `visible_unread_notification_count()`: SQL по тредам, проверка доступа один раз на тред |
| Тип, ссылки | `communication_center_ui_service::notification_type`, `daily_report_target` | ссылки вынесены в `notification_links()` и общие для центра и колокольчика |
| Транспорт | образец `communication_live_poll.php` (GET, require_login, capability, JSON, `no-store`) | новый `communication_notifications_feed.php` по тому же образцу |
| Верхнее меню | слот `topbar.notificationshtml` в `bms24_app_shell.mustache`; `bms_page_shell_service::finish`, `bms_workspace.php`, `bms_architecture.php` | колокольчик только в owned shell |
| Moodle-колокольчик | в owned shell (layout `embedded`) его нет; в legacy/KBA theme есть, и туда же через `message_send` приходят calendar/dailyreport | в legacy BMS-колокольчик не выводится, чтобы не было двух одинаковых |

В `bms_workspace.php` у «Требует внимания» была иконка `i/notifications`, то есть второй колокольчик с другим счётом. В owned shell у неё теперь флажок `i/flagged`; в legacy ничего не меняется.

## 2. Что добавлено

- `communication_service::notification_feed()` и `visible_unread_notification_count()`: только чтение.
- `communication_notifications_feed.php`:
  - GET — лента до 8 последних видимых уведомлений и точный счётчик;
  - POST `action=sound` с `sesskey` — настройка звука;
  - POST `action=claim&ids=…` с `sesskey` — запрос права на сигнал (см. раздел 3, п. 5).
  Любой отказ, включая чужую компанию и отзыв доступа, отвечает одинаково: `{"ok":false,"state":"unavailable"}` с HTTP 200. Строк, счётчиков и ссылок в таком ответе нет, а в консоли открытой страницы не появляется ошибка 4xx.
- Шаблон `bms24_notification_bell.mustache` (только разметка), модуль `amd/src/notification_bell.js`, стили `bms_ui/notification_bell.css` в области `.bms24-app`.
- Настройка пользователя Moodle `local_kbacompany_notification_sound`: `1` или `0`, по умолчанию выключено.
- Служебная настройка `local_kbacompany_notification_sound_mark`: id последнего уведомления, по которому уже был сигнал.
- Обе отражены в privacy provider: metadata и `export_user_preferences`.
- `classes/local/notification_bell_service.php` — серверное решение «звучать или нет» (`claim_signal`).
- 18 строк RU/EN, добавлены в конец языковых файлов.
- В скрытой панели нет заголовков h1–h6 (там `<p>`), чтобы поиск заголовка страницы не находил текст панели.

## 3. Правила сигнала

1. Звук только при включённой настройке аккаунта (значение приходит с сервера в каждом ответе ленты).
2. Первый успешный ответ после загрузки страницы — точка начала наблюдения. Всё, что было видно в этот момент, не звучит; это касается и первичной загрузки, и reload.
3. Новое = id уведомления (uuid) не встречался в этой вкладке, оно не прочитано, создано не раньше начала наблюдения (по часам сервера) и не старше 10 минут. Счётчик для решения о звуке не используется.
4. Пачка новых — один сигнал.
5. Несколько вкладок и браузеров одного аккаунта согласуются через сервер, хранилище браузера не используется:
   - вкладка с новыми id отправляет `action=claim` (POST, `sesskey`);
   - сервер под блокировкой Moodle (`local_kbacompany_bell`, ключ — пользователь) берёт из присланных id только свои, непрочитанные, видимые (то же правило доступа, что у ленты) и не старше 10 минут;
   - сигнал разрешается, если самый новый из них больше сохранённой метки; метка тут же сдвигается;
   - вторая вкладка с тем же событием получает `play:false`. Нет блокировки или нет ответа — тишина, а не повтор.
   Так работает и в приватном режиме, и при заблокированном `localStorage`. Генерация уведомлений, реестр и cron не меняются, ничего не отмечается прочитанным.
6. После «недоступно» (отзыв доступа к компании) наблюдение начинается заново: при восстановлении звука нет.
7. Если ответ пришёл для другого пользователя или компании (в браузере вошёл другой аккаунт), вкладка останавливается и очищает колокольчик.
8. Отказ `play()` (autoplay) перехватывается. Показывается состояние «Браузер заблокировал звук» и кнопка «Проверить звук»; ошибки JS нет.

Вызов `play()` не доказывает, что звук был слышен. Для этого нужна ручная проверка владельца (раздел 6).

## 4. Опрос и нагрузка

- Интервал 30 с, только при видимой вкладке. Это ближе всего к живому опросу центра (25 с) и достаточно для сигнала человеку.
- Скрытая вкладка не опрашивает. При возврате запрос уходит сразу, если прошло 30 с.
- Офлайн (`navigator.onLine === false`) — пауза. Событие `online` запускает один запрос.
- Ошибки: backoff 60 → 120 → 240 → 300 с.
- Одновременно не больше одного запроса. При открытии панели лента обновляется, если с прошлого запроса прошло больше 2 с.
- Стоимость запроса:
  - выборка до 200 последних строк пользователя порциями по 40;
  - один `GROUP BY` по непрочитанным;
  - проверка доступа к объекту один раз на тред.
  Обычная отрисовка страницы ACL уведомлений не выполняет: колокольчик загружается из JS.

## 5. Минимальный срез и схема

- Срез: owned shell, колокольчик, панель, звук. Схема БД не меняется, миграционная приёмка не нужна.
- Новая настройка — штатная `user_preferences` Moodle.
- Версия плагина остаётся `2026111601`, как в `main` и #152: её закрепляют семь CI-гейтов.
- После установки ZIP нужна очистка кэшей Moodle, чтобы подтянулись новые строки, шаблон и AMD. Шаг upgrade не запускается.
- Web Push и Service Worker в срез не входят.

## 6. Ручная проверка владельца (test, после установки Codex)

1. Owned shell, любая страница BMS24 компании A: в верхнем меню один колокольчик.
2. Открыть колокольчик → «Включить звук»: должен прозвучать короткий двойной сигнал.
3. Не закрывая вкладку, получить синтетическое уведомление (Codex создаёт его тем же генератором, что в CI). В течение 30 с должен прозвучать один сигнал, бейдж увеличиться на 1.
4. Открыть уведомление из колокольчика: открывается его объект. Пока не нажато «Отметить прочитанным» в центре или не открыт разговор, уведомление остаётся непрочитанным.
5. «Выключить звук» → следующее уведомление приходит без сигнала.

## 7. Проверки

- PHPUnit: `tests/notification_bell_test.php`:
  - ACL ленты, равенство счётчиков центра, shell и колокольчика, отсутствие отметки прочтения;
  - отзыв участия: точный состав фикстуры (thread_invite + message), после отзыва 0 непрочитанных, тред и его id не раскрыты, история не тронута;
  - чужая компания, настройка по аккаунту;
  - `claim_signal`: один сигнал на пачку, повтор, выключенный звук, прочитанное, старое, чужое, отозванный тред.
- BROWSER: `tools/ci/browser/notification_bell.py`, вердикт `contract.notification_bell_checks()` (8 проверок), ложные PASS отсекаются в `test_contract.py`. Две вкладки проверяются дважды: с обычным `localStorage` и с недоступным (каждое обращение бросает `SecurityError`); событие приходит обеим вкладкам на одном такте часов, сигналов в сумме ровно один.
