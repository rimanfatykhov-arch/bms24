# ADR-0001 — BMS24: управление решениями, задачами и выпуском релизов

- **Статус решения:** Accepted by Product Owner (2026-11-08, в чате BMS)
- **Статус внедрения:** Proposed in GitHub PR, **не действует как репозиторный стандарт до merge в main**
- **Архитектурное ревью:** требуется; архитектор может уточнить реализацию, но не изменить утверждённый принцип без нового ADR
- **Область:** BMS Role Intelligence, BMS AI Core, AI Studio, BMS24.online; все релизы и среды
- **Контекст:** `docs/22_BMS24_PRODUCT_VISION_FOUR_STREAMS.md`

## Проблема

Решения об архитектуре и целях BMS24 принимаются в переписке, а Codex не видит
всей истории. Разработка идёт в нескольких ветках: `main` — build2026101645
(зафиксировано проверкой 2026-11-08), отдельный draft `import/build2026101879`,
а Role Intelligence R1/R2 находятся в PR #38/#39. Это не позволяет считать
один ZIP или статический CI автоматической готовностью продукта к выпуску.

## Утверждённое решение: где хранится источник истины

| Артефакт | Место хранения | Кто принимает |
| --- | --- | --- |
| Гипотезы, идеи, предложения, обсуждения | Чат BMS с владельцем продукта | Не являются командой на deployment |
| **Продуктовая стратегия / направления** | `docs/22_BMS24_PRODUCT_VISION_FOUR_STREAMS.md` в GitHub | Владелец продукта |
| **Архитектурные решения** | `docs/adr/ADR-NNNN-*.md` + индекс `docs/DECISIONS.md` | Владелец продукта после ревью архитектора |
| **Задачи и критерии приёмки** | GitHub Issues, ссылки на ADR и PR | Продуктовый владелец согласует приоритеты |
| **Реализация** | Feature-ветка и GitHub Pull Request | Codex/разработчик; ревью архитектуры и безопасности |
| **Результаты тестов** | GitHub Actions, тестовые протоколы и артефакты с SHA | Тестировщик и ответственный за релиз |
| **Установленная версия** | Фактический Git SHA / plugin version / DB migration state каждой среды, deployment record | Ответственный за инфраструктуру |
| **Решение о production** | Отдельное явное согласование конкретного артефакта и целевой среды; запись в release ticket | Владелец продукта |

**Чат — место утверждения, GitHub — долговременная проверяемая запись.**
До слияния документа в `main` он считается утверждённым намерением,
но ещё не доступен Codex как стандарт из основной ветки.

Разрешённые статусы ADR: `Proposed`, `Accepted`, `Superseded`, `Rejected`.
Изменять Accepted ADR нельзя «тихой» правкой: создать новый ADR,
сослаться на прежний и описать миграцию. Не ссылаться на незакреплённые
чат-формулировки как на релизный контракт.

## Обязанности участников

- **Владелец продукта:** цели, бюджет/приоритеты, бизнес-приёмка, согласование
  ADR, отдельное одобрение каждого production deployment.
- **ChatGPT / продуктовый архитектор:** помогает оформить решение, выявляет
  противоречия, пишет архитектурное ТЗ и критерии приёмки; не является
  автономным исполнителем в чужом приложении без явного запуска.
- **Ведущий архитектор (Codex / отдельное ревью):** ownership, данные, контракты,
  угрозы, миграции, влияние на четыре продукта; пишет/проверяет ADR.
- **Codex (исполнитель):** проверяет реальный checkout и связанные ADR,
  реализует строго ограниченный PR, привлекает субагентов *только если*
  они доступны/сконфигурированы. Не обещать параллельных агентов без проверки.
- **QA / security reviewer:** выполняет тесты и фиксирует непроверенное.
- **Release manager / CI/CD:** запускает pipeline и оформляет deployment evidence.
  Нет права самостоятельно выбирать production-артефакт или обходить approval.

## Сквозной процесс

```text
ОБСУЖДЕНИЕ (ChatGPT) -> РЕШЕНИЕ владельца -> ADR/Issue (GitHub)
                    -> Архитектурное ревью / Impact / Risks
                    -> Codex: feature branch + PR + тесты
                    -> CI: static + security + focused tests
                    -> Staging: backup, upgrade, PHPUnit, cross-company ACL, UI, smoke
                    -> QA-приёмка владельцем (release candidate)
                    -> Отдельное разрешение на PROD
                    -> GitHub protected deployment + post-deploy smoke + журнал
```

### Gates

**G0 Design:** определены продуктовый поток, назначение, границы владения
системами, компания/доступ, миграции и риск. Для изменения доменной схемы,
RBAC, API, AI, SaaS или ролей нужен ADR до реализации.

**G1 Code:** `git status`, SHA, версия, точные изменённые файлы, code review;
секретов нет; PHP lint, RU/EN, JS, XML, статические проверки и `git diff --check`.
Статический PASS не заменяет тесты Moodle.

**G2 Staging:** установлен **тот же** хешированный артефакт; backup/restore,
миграции и лог ошибок, реальные Moodle PHPUnit, проверки двух компаний
(в том числе прямые GET/POST), role/ACL, business workflows, UI в
`legacy` и `owned`, KBA/Boost если поддерживается, smoke после установки.
Недоступные проверки фиксируются как блокирующий `NOT RUN`, если они
обязательны для затронутого риска.

**G3 RC acceptance:** релиз-менеджер фиксирует evidence: версию,
Git SHA, хеш ZIP, версии Moodle/PHP/DB, результаты тестов,
известные ошибки, маршрут обновления и испытанный путь восстановления.
QA и владелец продукта принимают релиз. Сборка в CI ≠ успешная установка.

**G4 Production:** **отдельная явная команда** владельца для
**конкретной версии + сервера + окна + плана rollback**. Должны быть
защищённая environment, минимум прав для деплоя, подтверждённые резервные
копии, post-deploy health check, запись об установке. Слова
«делай следующий шаг/релиз» разрешают работу в GitHub/тестовом
контуре, но **не** production. Не включать auto-deploy на `edu.kzn.mba`
или `bms24.online` без отдельного ADR и закрытых gates.

## Политика окружений

- `edu.kzn.mba` — действующая образовательная платформа. Production
  меняется только по отдельному разрешению.
- `test.bms24.online` — существующий staging; не переписывать его ради
  новой проверки среды.
- `stage41.bms24.online` — параллельный parity staging; готовность
  HTTPS и авторизации проверять по реальным evidence, не по PR.
- `bms24.online` — цель коммерческого SaaS, не объявлять пилот работающим
  до тестов подписок, company isolation, backup/restore, оплаты.

**Важно:** технология БД/PHP — фактически установленная версия каждой среды.
Исторический target PHP 8.1 + MySQL 5.7 и parity MariaDB 10.11 — разные
профили. Проверка на одном не означает проверку другого. Снятая с
поддержки версия Moodle требует ограниченного тестового доступа и
отдельного плана модернизации.

## Следующие действия (не являются разрешением на PROD)

1. После ревью объединить продуктовый контекст PR #41 и данный governance PR.
2. Провести baseline reconciliation: `main`/1645, импорт 1879 в PR #8,
   последовательность upgrade, R1/R2 PR #38/#39, реальная установленная версия.
3. Определить единую ветку RC30 и матрицу поддерживаемых окружений; добавить
   в CI актуальные проверки и Moodle интеграционные тесты.
4. Завершить независимую staging-приёмку и автоматизировать безопасный
   test deployment; ограничить production deployment ручным approval.
5. Только затем планировать разрешение на эксплуатационный релиз.

## Исключения и последствия

Модель добавляет review и немного документации, но исключает накопление
несовместимых ZIP, скрытый деплой и потерю архитектуры между чатами.
Ручная операция на staging допускается при документированной проверке,
если автоматический pipeline ещё не настроен. Важен результат, а не
декларация наличия CI/CD.
