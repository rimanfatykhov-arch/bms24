# ADR-0010. Проверяющий дневного отчёта по оргсхеме, самопроверка на вершине, видимость для руководителя, копия

- Статус: **ПРИНЯТО** владельцем 21.11.2026 (два решения ниже); реализация — этот PR, версия `2026112301`.
- Изменяет: ADR-0009 «Ежедневные отчёты сотрудников» (`docs/adr/ADR-0009-daily-employee-reports.md`, PR #115),
  решение D6 «Самопроверка запрещена» и права доступа D6/В6. Остальные решения ADR-0009 (В1 — боевой план недели
  первым, неизменяемые версии, идемпотентная отправка, снимок задач, откат выключателем) действуют без изменений.
- Заменяет частичную правку PR #147 (уже стоит на production под версией 2026111601): та правка ввела `self_top`,
  но без пометки в интерфейсе, без настройки компании, без копии и с неверным чтением `orgreport`.

## Решения владельца 21.11.2026

1. **Видимость для руководителя — вся компания.** Руководитель видит отчёты всех сотрудников компании.
2. **Самопроверка — только когда выше никого нет.** Во всех остальных случаях она запрещена.

## Контекст

На production директор отправил отчёт, а проверяющий не нашёлся: выше по оргсхеме никого, отчёт ушёл в «Без
проверяющего» и застрял. Администратор-автор не мог открыть собственный отчёт из этой очереди: карточка падала с
`dailyreports_notavailable`. Руководитель без назначения не видел ничего. Копии отчёта не было совсем.

## Решение

### D1. Две сущности оргсхемы

- **Подразделение** — `local_kbacompany_orgnode.uuid`. Следующее подразделение вверх — применённый родитель по линии
  подчинения `local_kbacompany_orgreport.manageruuid`, если строка есть. Пустое значение означает вершину. Иначе
  берётся `orgnode.parentuuid`.
- **Руководитель подразделения** — человек: держатель действующего назначения на должность с `ismanager = 1` этого
  подразделения, а также роль `manager` в отделе компании на Corporate.

Уточнение к постановке задачи. `orgreport.manageruuid` — это **UUID подразделения**, а не пользователь. Так его пишет
`design_service::apply_payload`, так же его читают `live_reporting_parent` и доска оргсхемы. Поэтому таблица остаётся
в обходе как линия подчинения «узел → узел». Человек из неё не берётся никогда. Значение, которое не является
действующим подразделением этой компании, останавливает обход. Таблица не заполняется и не меняется.

### D2. Ближайший руководитель, детерминированно

Обход идёт от подразделений автора: сначала основное назначение, затем остальные по id назначения. Подъём —
не выше 10 уровней, с защитой от циклов. В подразделении берётся первый подходящий руководитель: сначала основной
(`assignmenttype = primary`), иначе с минимальным id пользователя. Подходящий — действующий участник этой компании,
не удалён, не заблокирован, не отозван, не автор. Подразделение, которым руководит сам автор, пропускается:
соруководители — коллеги, а не начальники. Затем подъём продолжается.

Порядок источников, записанный в `dreportver.reviewersource`:

`battleplan` (В1, без изменений) → `orgstructure` → `top_reviewer` → `self_top` → `none`.

### D3. Вершина

Если по оргсхеме выше никого нет:

- если в правилах компании задан постоянный проверяющий верхнего уровня, отчёт уходит ему (`top_reviewer`);
- иначе, если автор **находится на вершине**, он проверяет отчёт сам: `reviewerid = автор`,
  `reviewersource = 'self_top'`. На вершине — значит руководит подразделением или отмечен `member.ismanager`;
- иначе `none`: «Без проверяющего», назначает администратор.

`self_top` — сохранённый признак самопроверки версии. Он виден в карточке, в истории автора, в очереди, в решениях
версии и в журнале: детали `submitted` и `decided` содержат `"selfreview": true`. В интерфейсе написано, что отчёт
проверяет автор, потому что руководителя выше нет. Решение автора принимается только по версии `self_top`. Любая
другая версия, где `reviewerid` совпал с автором, по-прежнему даёт отказ `dailyreports_notreviewer`. Уведомлений
самому себе нет.

Почему сотрудник без подразделения не проверяет себя сам. Иначе любой не размещённый в оргсхеме человек принимал бы
свои отчёты. Это не вершина, а пробел в данных, и такой отчёт ждёт назначения администратором.

Выключатель сайта `local_kbacompany/dailyreports_selftop` (по умолчанию 1, по решению владельца) позволяет вернуть
прежнее поведение `none` без смены кода.

### D4. Руководитель видит всю компанию

Руководитель — действующий участник с `member.ismanager = 1` или руководитель хотя бы одного подразделения. Он и
администратор компании читают все отправленные версии всех отчётов компании, включая свои: очередь «Все отчёты
компании». Право решения есть только у сохранённого проверяющего версии. Администратор дополнительно переназначает
проверяющего (В2). Черновики никто, кроме автора, не читает.

### D5. Копия отчёта

- Вручную: автор выбирает получателей при сохранении или отправке. Это другие действующие участники компании, не
  больше `local_kbacompany/dailyreports_cc_max` (по умолчанию 5).
- По правилу компании `ccpolicy = upper`: руководитель уровнем выше проверяющего по той же цепочке.
- Копия хранится в `local_kbacompany_dreportcc` на версии. При отправке она фиксируется и позже не меняется.
  Проверяющий копию не получает. Доработка переносит ручные копии в новый черновик, а старая версия остаётся как была.
- Получатель получает одно уведомление `dailyreport_copy` на версию. Он видит отчёт в очереди «Копии мне» и не может
  принять, оценить или вернуть его.

### D6. Правила компании

Таблица `local_kbacompany_dreportset`, одна строка на компанию:

- `toppolicy`: `self` или `reviewer`, плюс `topreviewerid`;
- `ccpolicy`: `none` или `upper`.

Меняет только администратор компании: optimistic revision, блокировка, запись `settings_changed` в журнале.
Без строки действуют безопасные значения `self` и `none`.

### D7. Проверяющий виден до отправки

Форма отчёта показывает, кто проверит отчёт, и источник этого выбора. Отдельно указаны самопроверка, «не найден» и
автоматическая копия. Значение вычисляется, не сохраняется и фиксируется только при отправке.

## Последствия

- Схема только аддитивная: шаг `2026112301` создаёт `dreportcc` и `dreportset` из `install.xml`. Существующие таблицы
  и строки не меняются. У созданных версий `reviewerid` и `reviewersource` остаются прежними.
- Версии из PR #147 с `self_top` уже несут признак самопроверки и сразу показываются с пометкой.
- Privacy: копии и правила входят в metadata, контексты, экспорт и удаление. При удалении пользователя его копии
  удаляются, а правило, где он был проверяющим верхнего уровня, возвращается к `self`.
- Шире стал круг чтения: руководители и получатели копии. Это прямое решение владельца. Решения по-прежнему
  принимает только проверяющий.
- Откат: выключатель `dailyreports_enabled` или `dailyreports_selftop`. Понизить версию кодом нельзя (ADR-0009 D8).
