## Context

Продукт требует функциональных постов, которые занимает человек, ИИ-агент или гибрид (MR3-D54), с отдельной
идентичностью и узкими правами агента (MR3-D55) и ответственным человеком (MR3-D56). Код `main` устроен вокруг
Moodle user: граница компании (`company_context_service::context(company, int userid)`), права
(`permission_service`, `aclassign.userid`), задачи (`assigneeid`, `tasklog.actorid`), отчёты (`dreport` уникален по
`userid`), сообщения (`authorid`). Ни одна из этих точек не может принять агента без подмены человека.

ADR-0012 ввёл временный `service_integration` для фейкового MAX как выделенный Moodle-аккаунт и прямо запретил
считать это прецедентом.

## Decision (proposed)

1. **WorkPrincipal** — отдельная идентичность действующего лица: `human` (ссылка на Moodle user и членство),
   `ai_agent` (без Moodle user, логина, сессии, токена, ролей и capability), `service_integration` (транспорт канала;
   может иметь транспортный Moodle-аккаунт, но не автор и не держатель прав). Один принципал — одна компания.
   У нечеловеческих — обязательный спонсор-человек. Lifecycle `draft → active ⇄ suspended → revoked`.
   Подробно: `docs/bmos/A0_02`.
2. **Position Occupancy** без второго реестра должностей: люди остаются в `posassign`; нечеловеческие исполнители —
   в отдельной занятости `posoccup` по `position.uuid` с режимом `agent`/`hybrid`, функциями, лимитами нагрузки,
   руководителем, утверждением и историей. Занятость прав не даёт. Агент не участвует в Position Coverage.
   `task.assigneeid`, `dutypositionuuid`, история назначений, coverage — без изменений.
3. **Grants** — в форме RBAC 2.0 `(company, object_type, action, scope, constraint)`, deny by default, срок ≤ 90 дней,
   продление только человеком. Scopes агента: `own`, `position` (= `assigned`), `explicit_object`, с A3 —
   `delegated_team` (явный список постов, пересечение с текущими правами руководителя на каждый объект; права
   спонсора не используются). Роли доступа BMS (`aclassign`) агентам не назначаются.
4. **Один provider engine — `local_kbaai`** (MR3-D50). В нём добавляется модельный слой:
   `model_provider_interface` (`list_capabilities`, `generate`, `generate_structured`, `embed`, `health_check`,
   `usage`, `estimate_cost`), `ModelRouter`, версионный реестр моделей, `FakeModelProvider`, позже
   `TimewebAIGatewayAdapter`. Сценарные интерфейсы Assessor и BMS Assistant не переписываются. **Agent Runtime —
   отдельный выключаемый плагин `local_bmosruntime`** (MR3-D51), вызывает модели только через `local_kbaai`.
   Это модульная, а не физическая изоляция: только доверенный код, инструменты из allowlist в коде, без
   произвольного исполнения, SQL к таблицам домена и HTTP вне адаптера (`docs/bmos/A0_12`). Внешние агенты — не
   раньше A4, отдельным ADR.
5. **Agent Command Gateway (API v2)** в `local_kbacompany` — единственный вход для действий нечеловеческих
   принципалов. Каждая команда проверяет identity, kill switch, company, sponsor, occupancy, grant, object ACL,
   idempotency/replay, lifecycle, revision, rate, budget и пишет audit; replay распознаётся после проверки текущих
   прав и отзыва, но до lifecycle/revision; мутация, ключ идемпотентности и атрибуция — в одной транзакции.
   Риск-классы R0–R4. В A1 агент пишет только собственный результат и предложения; R3 в A1 отклоняется без
   исполнения, с A2 — через подтверждение второго человека; прямые комментарии — после ворот атрибуции W1; R4
   агенту запрещено. Человек, сервис и агент не получают одинаковых прав автоматически:
   команды «только для людей» не зарегистрированы для других типов. Контракт: `docs/bmos/A0_04`.
6. **ADR-0012 поглощается отдельным совместимым срезом A1-12** после приёмки существующего контура MAX, без
   изменения поведения. Каждая запись `inbconn` получает `wprincipal(service_integration)`; транспортный аккаунт →
   `transportuserid`; dual-actor audit обобщается до `actor_principal_uuid + on_behalf_of_user_id`. До A1-12
   ADR-0012 действует как есть и только для фейкового MAX.
7. **AgentDefinition (ревизии) и AgentRun** — по контракту `docs/bmos/A0_06`: provider, профиль модели, ревизия
   конфигурации, инструменты, источники контекста, действия, риск-политика, лимиты токенов/стоимости/времени/действий,
   `credentialref`, kill switch; у запуска — idempotency, correlation, usage, оценённая и подтверждённая стоимость,
   evidence, ошибка, эскалация, аудит. Секреты, скрытые рассуждения и полные промпты по умолчанию не хранятся.
8. **AI Billing** — бюджеты на компанию/агента/пост/модель/запуск, резерв до вызова, освобождение, идемпотентная
   регистрация расхода. Оценка ≠ списание: `confirmed` только сверкой с данными провайдера. Неопределённый исход
   (таймаут после отправки) удерживает консервативный резерв до сверки и не повторяется автоматически. В A1 — только
   внутренние лимиты и учёт; клиентский биллинг — SaaS/A4.
9. **Fail closed** везде; отказ — без побочных эффектов, с отдельным аудитом.
10. **Атрибуция** — отдельная неизменяемая таблица; существующие журналы не меняются; envelope outbox 1.2 с полями
    актора (добавочно к 1.1). Запись агента в существующие объекты (`actorid=0` + `wpattr`) разрешается только
    после ворот W1: доказанная совместимость всех потребителей и атомарная связь с мутацией.
11. **Вакантность и функциональное покрытие** — разные показатели. Агент не уменьшает вакантность людей; его
    вклад показывается как «функции N/M — ИИ-агент». Position Coverage (`poscover`) не используется.
12. **Отчёт агента** хранится отдельно от `dreport*`, общий UI; отчёты людей не мигрируют.

## Alternatives considered

| Альтернатива | Почему нет |
|---|---|
| Агент как Moodle user (фиктивный сотрудник) | Наследует сессии, роли, членство, отчёты, `assigneeid`; impersonation; запрещено MR3-D55 и #76 |
| Агент в `posassign` / как delegate в `poscover` | Ломает штатное расписание, `effective_executor`, отчёты и инвариант Position Coverage |
| Агент действует под userid спонсора | Impersonation, невозможно отличить действия, права спонсора шире нужных |
| Второй provider engine в Runtime | Запрещено MR3-D50/BMS-ARC-AI-001; дублирование ключей, профилей и защиты |
| Переписать `provider_interface` `local_kbaai` | Риск регрессии Assessor и BMS Assistant без пользы для агентов |
| Сразу внешний агентный сервис с токенами | Требует интеграционного прокси и отдельной модели угроз; до A4 запрещено (Q-03) |

## Consequences

- Плюс: права агента отделены и проверяемы; история людей не переписывается; провайдер заменяем.
- Минус: каждая команда агента требует отдельной principal-aware точки входа в домене (нельзя «просто вызвать
  существующий метод с userid»). Это объём A1–A2.
- Минус: места, где журналы рендерят `actorid`, нужно научить показывать ИИ-актора (A1-08).
- Минус: до ворот W1 агент не может писать в существующие объекты даже низкорисковые записи — сознательное ограничение.
