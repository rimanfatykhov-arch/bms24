# ADR-0008 — Коммуникационный центр: каноническая история, участники-ИИ и внешние каналы

- Статус: **ПРЕДЛОЖЕНО**. Продуктовая цель — **ПРИНЯТО** владельцем 15.11.2026; модель данных, права, порядок каналов,
  автоматические действия ИИ и этапы — только предложения до согласования.
- Номер 0008 выбран, потому что ADR-0007 занят в Draft PR #77 (BMOS AI Control Layer).
- Связано: [аудит](../communication/COMMUNICATION_CENTER_AUDIT.md), [план](../communication/COMMUNICATION_CENTER_PLAN.md),
  PR #77 (ADR-0007, принципалы ИИ), PR #88 (контракт MAX inbound), PR #97 (решения MAX trust), Issue #75, PR #95 (D02/D03).
- Область: `local_kbacompany` (`communication_service` и смежные). Moodle Core, `theme_kba`, production — вне области.

## Принятая цель (ПРИНЯТО)

Коммуникационный центр обеспечивает общение сотрудников; ИИ-сотрудники (терминалы) участвуют в тех же рабочих
обсуждениях; обсуждаются задачи, боевые планы и другие сущности; подключаются MAX, Telegram и другие каналы; человек
общается через удобный канал, а рабочая история сохраняется в BMS24. Обсуждение объекта из его карточки и из центра —
**один разговор**.

## Контекст (ПРОВЕРЕНО кодом `main` d353509)

`communication_service` уже является единым журналом: треды `direct/group/object`, связь с объектом через
`contextkind/contextuuid`, участие как граница чтения, повторная проверка доступа к объекту, правка/отзыв автора с аудитом
(`commrev`), защищённые файлы, уведомления отдельно от сообщений. Обсуждение задачи в карточке читает тот же тред.
Нет: происхождения сообщения (канал), внешних ID, типа участника (человек/ИИ), производителей событий outbox для
коммуникаций, адаптеров каналов, `battleplan` в видах объектов.

## Решение (ПРЕДЛОЖЕНО)

### D1. Один журнал

BMS24 (`local_kbacompany_commmsg` и связанные таблицы) — **единственная каноническая история**. Внешний канал — транспорт.
Второй сервис сообщений, отдельная «лента MAX» с собственной историей или копия переписки в адаптере не создаются.
Адаптер может держать только технический буфер приёма (inbox) с ограниченным сроком, как в #88.

### D2. Обсуждение объекта

Один активный тред `object` на `(companyuuid, contextkind, contextuuid)` — сохраняется. Новые виды добавляются через
`communication_object_service::describe` (ACL-дескриптор вида объекта) — это **общий контракт для сущностей**.
Карточка сущности и центр — две проекции одного треда. Дальнейшие сущности (боевой план, приказы, дневной отчёт)
подключаются только дескриптором + правилом участников, без своего хранилища сообщений.

### D3. Идентичность и происхождение сообщения

Каждое сообщение сохраняет: `uuid` (канонический ID BMS24), автора (Moodle user **или** ИИ-терминал), происхождение
(`bms24 | max | telegram | ai | system`), время создания в BMS24, время в источнике и время приёма (для внешних),
ответ (`replytouuid`), вложения. Внешние ID (`provider`, `connection`, `external_chat_id`, `external_message_id`) хранятся
в **отдельной таблице сопоставления сообщений** с уникальным ключом — это ключ идемпотентности и маршрутизации ответов.
`extmap` переиспользуется для привязки внешнего **аккаунта** к сотруднику, но не для сообщений (другая кардинальность и объём).

### D4. Участники-ИИ

ИИ-терминал — **отдельный принципал** (`ai_agent` по ADR-0007/#77), не Moodle-пользователь с человеческой сессией и не
подмена автора-человека. Участие ИИ в треде — явная запись участника с типом `ai`, кто добавил и когда. Право читать/писать
сообщения **не равно** праву бизнес-действий: сообщение ИИ не меняет статус задачи, не создаёт задачу/решение, не
отправляет наружу от имени человека. Любое действие — через канонический сервис с отдельной авторизацией и (на первых
этапах) подтверждением человека.

### D5. Каналы

Общий контракт адаптера (`channel adapter`) с явным описанием возможностей канала (capabilities), а не «наименьший общий
знаменатель», который скрывает различия. Входящие события: проверка секрета/подписи → надёжный приём → идемпотентная
запись через канонический сервис с повторной проверкой прав → подтверждение источнику. Исходящие: запись в outbox
(`eventout` расширяется видом события коммуникаций) → доставка с повторами → фиксация внешнего ID и статуса доставки.
Наличие сообщения во внешнем чате **не даёт** прав в BMS24; отзыв доступа прекращает новые отправки, но уже отправленное
наружу не отзывается гарантированно.

### D6. Состояния, которые не смешиваются

Сообщение ≠ уведомление ≠ открытие объекта (`tasklog opened`) ≠ прочтение треда (`commread`) ≠ подтверждение ознакомления
(отдельное будущее явное действие) ≠ выполнение поручения (статус задачи). Статусы доставки во внешний канал
(`queued/sent/failed`) — отдельная сущность, «прочитано» в мессенджере не утверждается, если канал его не сообщает
(ни MAX, ни Telegram Bot API его не предоставляют — см. план, §4).

### D7. Правка и удаление

Политика BMS24 (автор, аудит, неизменяемость сообщений, ставших задачей/решением) — источник истины. Синхронизация во
внешний канал — «по возможности» в пределах ограничений API (окна правки/удаления), с явным статусом результата.
Правка/удаление во внешнем канале автором-человеком применяются к BMS24 только если канал присылает событие и автор
привязан; иначе фиксируются в аудите/на ревью, не переписывая историю молча.

## Миграции

Первый срез (единое обсуждение задачи, этап 1 плана) — **без миграций**. Каналы и ИИ — **с миграциями** (тип участника,
происхождение сообщения, таблица сопоставления внешних сообщений, подключения каналов, привязки аккаунтов, статус
доставки). Обоснование и черновой состав — в плане, §2. Все миграции: отдельный PR, расширенная приёмка
(MariaDB/Percona, install/upgrade, privacy provider), не FAST.

## Альтернативы

1. Отдельный «мессенджер-сервис» вне Moodle с собственной историей — отклонено: две истины, дублирование ACL.
2. Хранить внешние ID в `commmsg` — отклонено: одно сообщение может иметь несколько доставок (MAX и Telegram).
3. ИИ как обычный Moodle-пользователь — отклонено (ADR-0007): смешение принципалов, риск чужих прав и сессий.
4. Импорт истории внешних чатов — отклонено: синхронизация начинается с момента подключения конкретного чата к конкретному
   треду; прошлая и личная переписка не импортируется.

## Последствия

Плюсы: одна точка ACL, аудит и приватность; каналы и ИИ добавляются без переписывания центра.
Минусы: каналы требуют схемы и фоновой обработки (cron/adhoc tasks Moodle) и операционного мониторинга; публичный HTTPS
endpoint для webhook — новая поверхность атаки.

## Условия принятия

Владелец отвечает на вопросы плана (§8). До этого ADR остаётся ПРЕДЛОЖЕНО и не разрешает реализацию, миграции, ботов,
токены, merge или deployment.
