# ADR-0002 — RC30: единая база, идентичность релиза и порядок интеграции

- Дата: 2026-11-08.
- Статус: **Accepted by Product Owner, 2026-11-08**. Владелец явно утвердил базу и порядок ADR-0002 и поручил read-only inventory и отдельный repair PR.
- Внедрение: в review-ветках; main не изменён. Принятие не разрешает merge или deployment.
- Задача: [Issue #44](https://github.com/rimanfatykhov-arch/bms24/issues/44).
- Область: стабилизация общей платформы для четырёх продуктовых потоков.
- Не заменяет принятый владельцем [ADR-0001](https://github.com/rimanfatykhov-arch/bms24/blob/cd1cd314d74e7946354ba7ae6576cbef8636e56d/docs/adr/ADR-0001-bms24-decisions-and-release-governance.md). Его внедрение в main ещё ожидает review/merge.
- Связанный отчёт: [Issue44 baseline audit](../reconcile/ISSUE44_BASELINE.md).

## Контекст и факты

Main `740fce16db15bb3551071cc11fe584c680fd738d` содержит BMS build2026101645/RC29.
Импорт #8 `eccc1eb221df90675067b1011e986702d96a4985` содержит build2026101879/RC29,
но удаляет 2078 main-путей и ожидает acceptance1873. #42 сохраняет пути main
и включает исправление версии из #40. #46 `a36c5ab8ac129433eeddb0ae341717e35b614ac8`
добавляет Corporate API1.26 и исправления по результатам QA/security review.

Это состояние Git, не установленных серверов. У candidate обнаружены три
расхождения fresh/upgrade схемы: task.starttime, task.duetime,
deviation.executionstatus. CI PASS не делает эту базу готовой к установке.

## Предлагаемое решение

1. Единственный **кандидат для продолжения исходной разработки** — точный SHA #46
   `a36c5ab8ac129433eeddb0ae341717e35b614ac8`. Он не является принятой RC30 или
   разрешённым deployment. После утверждения создать `integration/rc30-baseline`
   от этого SHA; обязательные исправления миграций и контекста выполнять отдельными PR.
   Утверждение владельца получено08.11.2026. Ветка фиксирует исходную точку, не установленную среду. Main не меняется.
2. Документы #41 → #43 проверять и интегрировать в согласованной последовательности.
   Сохранить четыре потока, обязательное чтение ADR и фактический candidate1879.
   Не заменять AGENTS/MASTER/WORKFLOW целиком старой версией. Для изменения защищённого
   `docs/DEVELOPMENT_WORKFLOW.md` нужен точечный reviewed-update в preservation gate
   и deletion inventory, а не отключение защиты.
3. Кодовая последовательность review: #42 → #46 → исправление fresh/upgrade parity.
   #8/#40 уже учтены как источники; повторный полный импорт не нужен.
   После утверждения процедуры замещённые PR можно закрыть с трассируемой ссылкой;
   сейчас никакие PR не закрываются и не объединяются.
4. Role Intelligence переносить дельтами R1 #38 → R2 #39 после стабилизации базы.
   Сохранить candidate version/schema/CI и остальные языковые ключи.
   Отдельно проверить company A/B, non-admin, оба shell modes и нагрузку.
5. BMS остаётся `2026101879 / 1.1.0-rc29`, Corporate — patched source
   `2026102610 / 0.40.10 / API1.26`. До установки нужен новый согласованный
   монотонный build выше **фактически установленного** во всех целевых контурах.
   Нельзя выбирать 1880 только потому, что он следующий: в Git уже существуют
   ветки с такими номерами, а установленная версия неизвестна.
6. Новый build согласованно изменяет version.php, финальный savepoint,
   EXPECTED_PLUGIN_VERSION, source-preservation/version tests и packaging metadata.
   Сохраняем строгую проверку идентичности. Не подменять expected version текущей
   установленной версией и не ослаблять gate ради зелёного результата.
7. Идентичность RC: Git SHA + версии обоих плагинов + manifest + SHA256 каждого
   реально собранного ZIP + профиль Moodle/PHP/DB + протокол acceptance.
   Corporate опционален для BMS в целом, но обязателен с API1.26 для приёмки
   implementation-сценариев. Текущий CI ZIP содержит только kbacompany.
8. MySQL5.7 и MariaDB10.11 — разные строки acceptance. MariaDB не выдавать за
   MySQL5.7; текущий strict gate закономерно не принимает parity-профиль.
   Изменение поддерживаемого профиля требует отдельного решения, тестов и явной
   идентификации движка. Минимальный requires не равен сертификации окружения.
9. Issue #44 не закрывать до подтверждения владельцем порядка и закрытия
   обязательных критериев. Issue #45 получает этот входной контракт, но настройка
   эксплуатационного deployment ждёт #44. Production/staging не изменять.

## Исправление схемы — следующий ограниченный PR

После inventory и выделения нового build добавить достижимый checkpoint выше
старых установленных версий. Через Moodle XMLDB и field_exists добавить только
отсутствующие task.starttime/duetime (char5, NOT NULL, default пустая строка) и
deviation.executionstatus (char16, NOT NULL, default pending). Не переписывать
старый checkpoint1219: обновлённые установки его не выполнят. Не переписывать
значения уже существующих полей. При несовместимом существующем типе — отдельный
диагноз и план, а не молчаливая конверсия.

До merge: реальный fresh1645 → новый candidate, upgrade существующей1879,
fresh нового candidate, повторный вызов и сравнение полей/индексов/данных.
Проверить оба SQL-профиля раздельно, сохранность company UUID и бизнес-данных.
Этот ADR предлагает коррекцию; в текущем PR PHP/DDL не меняются.

## Альтернативы и последствия

- Остаться на1645: исключает значительный импорт и не решает заданную RC30-задачу.
- Слить #8 целиком: теряет компоненты/контекст main; отклонено как способ reconcile.
- Признать #46 релизом по CI: оставляет доказанный schema gap и неизвестную среду;
  отклонено. #46 пригоден только как исходная точка дальнейшего исправления.
- Переписать базу из R2: откатывает schema/version/CI; переносим только дельты.

В результате одна линия исходников снижает расхождение веток, но сама не заменяет
DB/ACL/UI/restore acceptance. AI Core, AI Studio и SaaS Control Plane остаются
отдельными архитектурными задачами; не добавляются в этот reconciliation.

## Обратимость и контроль

Текущий PR содержит только документы и source evidence; откат — revert его commit.
Для будущего deployment нужны согласованные backup кода/БД, проверенное восстановление
и отдельное разрешение на точный artifact/host. Изменение version records для
принудительного downgrade запрещено. Принятие ADR не является разрешением на deployment.
