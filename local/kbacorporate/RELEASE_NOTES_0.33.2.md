# KBA Corporate Dashboard v0.33.2 — Интеграция действий внедрения с Канбаном

- Moodle component: `local_kbacorporate`
- Numeric build: `2026090812`
- Minimum Moodle: 4.0
- Status: BETA / prepared for pilot runtime validation
- Upgrade path: in-place from `0.33.1`

## Назначение

Релиз превращает существующую доску задач в единое рабочее представление действий, созданных из подтверждённых разрывов аудита BMS. Отдельная сущность «карточка Канбана» не создаётся: одна карточка всегда является проекцией одной записи `local_kbacorp_impl_task`.

Целевая цепочка:

`подтверждённый аудит → критерий BMS → действие внедрения → Канбан → исполнитель → срок → доказательство → проверка → завершение`.

## Новые возможности

### Расширенная доска

На карточке отображаются:

- компания;
- исходный аудит;
- код и название критерия BMS;
- фактический и целевой уровни;
- величина разрыва;
- ответственный;
- приоритет;
- срок и просрочка;
- последняя версия доказательства и её статус;
- непрочитанные обсуждения;
- прогресс чек-листа.

### Фильтры

Добавлены фильтры по:

- компании;
- куратору;
- аудиту;
- ответственному, включая неназначенные задачи;
- статусу;
- приоритету;
- состоянию доказательства;
- просроченным задачам и задачам со сроком в ближайшие 7 дней;
- отчётному периоду;
- тексту карточки, компании, аудита, критерия и ответственного.

### Управляемое редактирование карточки

Уполномоченный куратор или менеджер может прямо на доске изменить:

- ответственного;
- срок;
- приоритет.

Каждое фактическое изменение:

- проверяет принадлежность нового ответственного компании;
- не допускается для завершённых и отменённых задач;
- сбрасывает цикл напоминаний при изменении срока;
- фиксируется в журнале задачи отдельным событием `kanban`;
- рассылает уведомления затронутым участникам;
- не меняет статус задачи скрыто.

Повторное сохранение тех же значений идемпотентно и не создаёт событие истории.

### Контролируемые статусы

Произвольное перетаскивание между колонками специально не добавлено. Статусы меняются только через существующий управляемый процесс:

- исполнитель запускает запланированную задачу;
- отправка доказательства переводит задачу на проверку;
- возврат доказательства возвращает задачу в работу;
- принятие доказательства завершает задачу;
- отмена и другие переходы выполняются через lifecycle задачи.

Так Канбан не обходит правила независимой проверки доказательств, добавленные в `v0.33.1`.

### Контекстные ссылки

Добавлены переходы в отфильтрованный Канбан из:

- подтверждённого аудита;
- страницы создания действий по аудиту;
- плана внедрения;
- списка задач;
- карточки действия.

Из Канбана доступны исходный аудит, действие и рабочее пространство доказательств.

## Изменение базы данных

В существующую таблицу `local_kbacorp_impl_tasklog` аддитивно добавляются поля:

- `eventtype` — тип события (`status` или `kanban`), для исторических строк значение по умолчанию `status`;
- `detailsjson` — JSON с предыдущими и новыми значениями ответственного, срока и приоритета.

Новые таблицы не создаются. Существующие задачи, статусы, доказательства и обсуждения не изменяются.

Перед обновлением production рекомендуется резервная копия базы данных, каталога плагина и `moodledata`. Полный rollback схемы требует восстановления базы либо осознанного сохранения добавленных полей с совместимым кодом.

## Права и безопасность

- Исполнитель видит только доступные ему действия и может запустить только собственную запланированную задачу.
- Быстрое редактирование доступно куратору программы либо пользователю с полным доступом к компании и capability управления аудитами внедрения.
- Новый ответственный обязан быть активным сотрудником той же компании.
- Все POST-операции требуют `sesskey`.
- URL возврата ограничен локальным URL Moodle.
- Данные и файлы доказательств продолжают проверяться существующим company scope и Moodle File API.
- При privacy deletion идентификаторы прежнего/нового ответственного в `detailsjson` анонимизируются без удаления самого события аудита.

## Известные ограничения

- В релизе нет drag-and-drop, массового изменения карточек и автоматической записи сотрудников на курсы.
- Изменение ответственного, срока и приоритета отправляет уведомления через Moodle messaging; фактическая доставка зависит от конфигурации каналов сайта.
- История Kanban-изменений начинается после установки `v0.33.2`; прежние изменения не реконструируются задним числом.
- Полная runtime-проверка upgrade, SQL, прав, сообщений, cron и evidence workflow должна быть выполнена на пилотном Moodle.
