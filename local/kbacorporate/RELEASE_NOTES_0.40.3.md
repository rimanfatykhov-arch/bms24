## Назначение

Подготовлен безопасный серверный контракт между `local_kbacorporate` и BMS24. Сами задачи, их статусы, обсуждения, доказательства и приёмка **по-прежнему принадлежат Corporate**. Новые методы предоставляют только read-only представления задач для дальнейшего подключения провайдера BMS24. **Кнопка «В Боевой план» и BMS24-провайдер ещё не реализованы.**

## Новый публичный PHP API (bridge 1.22)

```php
use local_kbacorporate\local\bridge;

$contract = bridge::contract();
$rows = bridge::list_implementation_task_projections(
    $corporatecompanyid, $actorid, $targetuserid, 'mine', 50, 0
);
$task = bridge::get_implementation_task_projection(
    $corporatecompanyid, $actorid, $taskid
);
```

`list_implementation_task_projections()` разрешает `scope = mine | employee | company`:

- `mine`: `actorid === targetuserid`; активный сотрудник явно указанной активной компании.
- `employee`: доступ к задачам активного сотрудника при наличии у actor прав управлять внедрением этой компании.
- `company`: `targetuserid === 0`; необходимы права управления внедрением компании.

Максимум 100 строк за запрос, offset 0..10000, упорядочивание по `timemodified DESC, id DESC`. Некорректные границы страницы отклоняются. Скрыты удалённые задачи и программы без `commercialstatus=paid` или со статусом вне `active|paused|completed`. В приостановленных/завершённых программах задачи просматриваются, но не помечаются как доступные для нового планирования.

`get_implementation_task_projection()` возвращает одну запись или `null` без раскрытия чужой задачи; доступ к ней ограничен действующим назначенным сотрудником или руководителем с правом управления внедрением в той же компании. Статусы остаются Corporate: `planned`, `inprogress`, `review`, `completed`, `cancelled` (неизвестное значение отображается как `unknown` без разрешения добавления в план).

### Состав ответа

`provider`, `external_id`, `company_id`, `program_id`, `program_title`, `program_status`, `source_kind`, `title`, `expected_result`, `assignee_id`, `reviewer_id`, `creator_id`, `status`, `priority`, `start_at`, `due_at`, `completed_at`, `time_modified`, `attachable`, `editable=false`, `source_url`.

- `external_id = impltask:<numeric_id>` — стабильный идентификатор исходной задачи.
- `source_url` — ссылка только на оригинальную защищённую карточку Corporate.
- `attachable` — рекомендация для будущего провайдера, **не авторизация**. BMS24 отдельно должен проверить UUID компании, сопоставление Corporate company id, права пользователя, владельца плана и возможность редактирования черновика.
- Комментарии, вложения, доказательства, личные данные участников в ответ **не включаются**.

## Безопасность и границы модулей

1. Все серверные запросы ограничены числовой Corporate company id и действующими правами пользователя.
2. API не предоставляет HTTP endpoint и не принимает URL назначения от пользователя.
3. Куратор, имеющий доступ к задачам нескольких клиентов в старом UI, **не получает через новый мост автоматический доступ к задачам клиентов в BMS24**. Ему нужна отдельная явная BMS-авторизация для будущего интерфейса.
4. Сопоставление компании UUID BMS24 ↔ числовой company id Corporate НЕ производится этим релизом. Следующий провайдер должен проводить проверенное сопоставление, запрещая привязки по названию.
5. Прямое редактирование/закрытие задач через новый API отсутствует.

## Установка

1. Создать backup файлов и БД Moodle. Проверить версию Corporate до установки: исходный архив имел 0.40.2 / 2026092111.
2. Установить `INSTALL_local_kbacorporate_0.40.3_build2026102512.zip` через штатный механизм обновления плагинов Moodle. Корневая папка в ZIP — `kbacorporate/`.
3. Дождаться обновления БД (savepoint версии, без миграции схемы), очистить кеши.
4. Проверить `local_kbacorporate` версию `2026102512`, что прежние страницы `implementation_my_tasks.php`, `implementation_curator.php`, `implementation_task.php` открываются и что история/обсуждения сохранены.
5. На тестовой базе с двумя компаниями проверить PHPUnit и E2E: владелец A видит только A; пользователь B не может получить задание A через ID; неоплаченные/удалённые задания не возвращаются; пагинация; роли управляющих; активность учётных записей; сценарии draft/paused/completed.
6. Проверить на целевом PHP 8.1, MySQL 5.7 и Moodle 4.1. Локальная проверка на PHP 8.4 не заменяет этот этап.
