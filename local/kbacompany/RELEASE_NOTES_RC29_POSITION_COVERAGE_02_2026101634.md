# BMS24 RC29 / build2026101634 — BMS-POS-COVERAGE-02 (первый безопасный срез)

**Основа:** полный `local_kbacompany` build2026101633. **Требуется:** сначала установить миграцию 1633 (или корректное последовательное обновление Moodle), затем 1634. **Статус:** код подготовлен, локальная статическая/SQL-семантическая проверка пройдена; реальный Moodle/MySQL/PHPUnit и пользовательская приёмка не проводились.

## Что сделано

1. В каноническую задачу `local_kbacompany_task` добавлено необязательное поле `dutypositionuuid` (по умолчанию пусто — **персональная задача**). Выполняются `db/install.xml` и идемпотентная XMLDB-миграция 2026101634. Старые задачи не переводятся массово.
2. У руководителя компании в карточке задачи появилось действие **«Закрепить ответственность за должностью»**, доступное только для открытой/выполняемой/возвращённой задачи. Разрешён выбор только среди действующих *основных* назначений исходного исполнителя в его компании. Операция проходит POST + sesskey + подтверждение + проверку актуальной ревизии задачи + lock и транзакцию. Изменение и снятие привязки фиксируются в `tasklog`.
3. Новые задания, сгенерированные из опубликованной **программы работы должности** (`sourcekind=positionwork`), явно получают `dutypositionuuid`; старые записи и другие генераторы не мигрируются задним числом.
4. `position_coverage_service` определяет **временного фактического исполнителя** только для привязанной должностной задачи, при совпадении компании, должности, первоначального исполнителя, активного назначения `primary`, `approved`-замещения со scope `position_work` и **текущей даты внутри включительного периода**. Для закрытых/переданных на проверку задач исходный исполнитель сохраняется как исторический.
5. `Task Center`: в «Моих задачах», ограниченных SQL выборках и счётчиках видны должностные задачи временного исполнителя. Основной сотрудник сохраняет право видеть историю, но не получает право выполнить переданную задачу. На карточке показываются «Тип ответственности», исходный и текущий исполнитель. У менеджера карточка замещения показывает **только явно привязанные должностные задачи**.
6. Выполнение (`start`/`submit`), контрольный список и доступ к самой задаче проверяют эффективного исполнителя на сервере. Завершение/согласование остается за первоначальными системными правилами и ролями проверяющего, не передаётся автоматически. При отправке результата с файлом допускается короткое продолжение загрузки подтверждающих материалов тем же замещающим, только после его собственного `submit`.
7. UUID, исходный `assigneeid`, автор, задачи и история Task Center, связь с утверждённым боевым планом и схема регулярных серий остаются без изменения.

## Архитектурные границы

- **Не выполняется массовое переназначение пользователей**, кадровых ставок, RBAC-ролей, прав согласования и личного календаря.
- **Не меняются старые «неразмеченные» задачи**: сначала менеджер должен явно закрепить их за должностью.
- **Не активируется автоматическая передача регулярных серий/экземпляров**: это следующий BMS-POS-COVERAGE-03 с отдельным контролем идемпотентности генератора. Программы работы должности маркируются только для *новых* экземпляров.
- Вступление замещения в силу происходит при чтении/операции по текущей **UTC-дате** (так же, как в 01), без полуночной записи в `task.assigneeid`.
- Обсуждения остаются под отдельным ACL Коммуникационного центра. Замещение само по себе **не делает замещающего участником старого конфиденциального обсуждения**. Задачи, содержащие приватные материалы, нельзя без отдельной оценки маркировать должностными.
- Даже при открытом замещении `creatorid` и `reviewerid` не меняются. Работа с отдельными чеклист-назначениями и аналитикой внешних task providers требует функциональной приёмки.
