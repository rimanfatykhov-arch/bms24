# BMS24 — сравнение результатов технической приёмки RC30 (build2026101867)

## Назначение

Новая команда `cli/rc30_compare_reports.php` **только читает два ранее полученных JSON-отчёта** команды `rc30_acceptance.php`. Сравнивает результат до и после обновления или исправления данных, не выполняя запросов к БД и не изменяя файлы.

Это средство регрессии; **даже PASS не разрешает RC30 автоматически**.

## 1. Снимок ДО обновления

На установленной версии 1866 (или новее) запустите из корня Moodle:

```sh
php local/kbacompany/cli/rc30_acceptance.php --all --format=json --strict > rc30_before.json
```

Обязательно зафиксируйте **код завершения**, например `echo $?` на Linux. `0` — без блокирующих нарушений, `1` — найдены, `2` — диагностика не выполнена. В любом случае файл должен содержать JSON; отчёт с `diagnostic_complete=false` непригоден для сравнения.

## 2. Снимок ПОСЛЕ обновления

На той же копии Moodle и с той же областью проверки:

```sh
php local/kbacompany/cli/rc30_acceptance.php --all --format=json --strict > rc30_after.json
```

## 3. Сравнение

```sh
php local/kbacompany/cli/rc30_compare_reports.php \
  --baseline=rc30_before.json --current=rc30_after.json --format=json --strict > rc30_diff.json
```

Для просмотра результата на экране можно убрать `--format=json` и перенаправление.

Проверяются: новые и устранённые коды ошибок/предупреждений, потеря/восстановление индексов, увеличение/уменьшение количества нарушений в каждой диагностике, изменение PHP/семейства и версии БД, состояние текущего технического допуска. Изменение общего числа задач `tasks_total` **не считается ошибкой**.

### Коды завершения сравнения

- `0` — не обнаружено блокирующих регрессий; в нестрогом режиме могут быть предупреждения.
- `1` — блокирующая регрессия или текущий технический допуск не пройден; с `--strict` новые предупреждения также блокируют.
- `2` — отчёты нельзя корректно сопоставить: повреждённый JSON, незавершённая диагностика, несовместимые области, отсутствующие проверки и т.п.

Ошибки в режиме JSON отдаются как объект с `comparison_complete=false`, без текста SQL, содержимого файлов и абсолютных путей.

## 4. Проверка одной компании

При запуске `rc30_acceptance.php --company=UUID` с версии **1867** каждый полный отчёт содержит `scope_digest` — SHA256 от UUID компании (сам UUID в отчёт не записывается). Команда сравнения требует совпадения отпечатков, чтобы не перепутать две компании.

У отчётов 1866 и ранее отпечатка нет. Для сравнения исторического отчёта одной компании предусмотрена **ручная ответственность администратора**:

```sh
php local/kbacompany/cli/rc30_compare_reports.php \
  --baseline=rc30_company_before.json \
  --current=rc30_company_after.json \
  --format=json --strict --confirm-same-company
```

Этот флаг разрешён только после того, как администратор независимо убедился, что оба отчёта относятся к **одной и той же компании на одной установке**. Если отпечатки есть в обоих отчётах, но не совпадают, сравнение отклоняется даже с флагом.

## 5. Ограничения

- Сравнивать нужно отчёты **одной и той же установки Moodle** и одной области проверки (кроме подтверждённых исторических отчётов компании). URL установки сейчас не сохраняется в JSON, поэтому его совпадение администратор проверяет самостоятельно.
- По умолчанию размер каждого входного файла ограничен **2 МиБ**.
- Отчёт диагностики `rc30_task_integrity.php` не является отчётом `rc30_acceptance.php` и не принимается к сравнению.
- Два отчёта без проблем **не заменяют** Moodle PHPUnit, тесты прав пользователей, работу UI, MySQL 5.7 EXPLAIN, резервное восстановление или ручное решение о выпуске RC30.
- Новые изменения БД и бизнес-записей в build1867 не вносятся.
