# RC30 — подготовка к серверной приёмке Task Center (build2026101860)

## Статус
Только локальная подготовка. Текущий расширенный набор — 18 диагностических проверок. Выпуск **не является RC30** до прохождения серверной приёмки.
Версия плагина: `local_kbacompany 1.1.0-rc29`, build `2026101860`.

## 1. Неизменность БД
- `db/install.xml` и `db/upgrade.php` не изменены в этом build.
- Диагностика только читает существующие таблицы. Никаких `UPDATE`, `INSERT`, `DELETE`, `ALTER` или фоновых задач.
- Данные пользователей и названия задач не печатаются в выводе; только количество нарушений по категориям.

## 2. Запуск (CLI Moodle, PHP 8.1.34)
Откройте терминал на сервере под пользователем PHP/Moodle, перейдите в корень Moodle.

Для **одной** компании (рекомендуется):

```bash
php local/kbacompany/cli/rc30_task_integrity.php --company=UUID_КОМПАНИИ
```

Для всех компаний (может занять больше времени на большой базе):

```bash
php local/kbacompany/cli/rc30_task_integrity.php --all
```

Справка:

```bash
php local/kbacompany/cli/rc30_task_integrity.php --help
```

Результат:
- **Код 0, PASSED** — все 18 выбранных контрольных запросов не обнаружили нарушений.
- **Код 0, WARNINGS** — есть предупреждения по историческим данным; выяснить причины.
- **Код 1, FAILED** — найдена категория критических проблем либо задан `--strict` при предупреждениях; продвижение RC30 отложить.
- **Код 2** — ошибка запуска, схемы или SQL; проверка не состоялась.

Внимание: код 0 **не означает**, что вся система прошла приёмку. Это только контроль целостности данных.

### Машиночитаемый отчёт (новое в build1860)

Отдельно для одной компании:

```bash
php local/kbacompany/cli/rc30_task_integrity.php --company=UUID_КОМПАНИИ --format=json > rc30_integrity.json
```

Строгий режим: предупреждения дают код выхода 1, что подходит для проверки готовности перед выпуском:

```bash
php local/kbacompany/cli/rc30_task_integrity.php --company=UUID_КОМПАНИИ --strict
```

Поля JSON: `schema_version`, `gate`, `scope`, `strict`, `summary`, `checks`, `read_only`. Ни UUID, ни ФИО, ни названия задач в отчёт не включаются.

## 4. Дополнительная ручная серверная приёмка — обязательна

### A. Разграничение компаний
- Пользователь компании А видит только задачи компании А.
- Пользователь компании Б видит только задачи компании Б.
- Прямое обращение к URL задачи другой компании отклоняется.
- Руководитель подразделения видит только управляемое подразделение; просмотр не подразумевает изменение.
- После отзыва роли исчезает разрешённый ей доступ.

### B. Список и массовые действия
- Фильтры, настройка столбцов и сортировка сохраняются отдельно для пользователя и компании.
- Пустая выборка оставляет навигацию и настройку столбцов, сброс фильтров работает.
- На широком списке прокручивается таблица, а не верхняя панель.
- Пакетные операции учитывают ревизию задачи и права.
- Повторная отправка формы не выполняет операцию второй раз.
- Переназначение связанной с Боевым планом/должностью задачи блокируется.

### C. Канбан
- Горизонтальные стрелки появляются при переполнении; работают по щелчку и наведению.
- Перетаскивание ведёт к штатной форме подтверждения, не меняет статус сразу.
- Группировки по исполнителю и проекту не показывают чужие задачи.
- Предельные значения WIP предупреждают, но не блокируют.
- Настройки Канбана восстанавливаются при повреждённых сохранённых значениях.

### D. Аналитика и временное замещение
- Сводка «Руководителю» совпадает со списком по тем же фильтрам.
- Временно замещающий сотрудник получает в нагрузку активные поручения.
- Завершённые поручения не меняют историческую принадлежность.
- Отбор по сотруднику не показывает задачи другой компании.

### E. Боевые планы
- BMS-задача связана с пунктом Боевого плана без создания копии.
- Правильно работают создание, просмотр, приёмка и закрытие задач.
- Нельзя обойти ограничения статуса плана через массовую операцию.

## 5. Условия допуска к RC30
- Сохранить резервную копию базы и кода до тестов.
- Запустить CLI-диагностику; расследовать все ERROR.
- Прогнать установленный PHPUnit на рабочей схеме Moodle/MySQL 5.7.
- Проверить веб-интерфейс на PHP 8.1.34, включая меню, права и прокрутку.
- Сохранить протокол с датой, версией, выборкой, замечаниями и решениями.

## 6. Ограничения
Диагностика не заменяет тесты прав доступа, не валидирует действующее членство пользователя в корпоративной системе, не проверяет зависимости от KBA Theme и не обеспечивает автоматическое исправление несогласованных данных.

## 7. Порядок устранения найденных проблем

Диагностический релиз **не выполняет ремонт данных автоматически**, так как исправление связей с Боевыми планами, истории и ролей без проверки первичных документов может привести к потере данных или расширению доступа. При появлении ERROR:

1. Сохранить резервную копию базы и кодов сборки; зафиксировать результат `--format=json`.
2. Установить компанию-источник нарушений через запуск `--company=UUID`, не используя массовые исправления вслепую.
3. Для дубликатов и потерянных связей проверить связанные события и текущие рабочие статусы.
4. Исправление оформлять отдельным согласованным скриптом с `--dry-run`, транзакцией и протоколом изменения.
5. Повторно выполнить диагностику и функциональный сценарий; только затем рассматривать RC30.

**Локальная проверка SQL:** `python3 local/kbacompany/cli/test_rc30_integrity_1860.py` (SQLite, две искусственные компании). **Проверка интерфейса CLI:** `python3 local/kbacompany/cli/test_rc30_cli_1860.py` (имитация окружения Moodle без реальной БД). Эти проверки не заменяют MySQL 5.7 и серверный Moodle.
