# BMS v0.5.3 — Состояния показателей и управленческие действия

## Назначение

v0.5.3 добавляет следующий аналитический слой после трендов и событий:

`Показатель → бизнес-привязка → история фактов → тренд → состояние → рекомендуемая формула действий`.

Состояние не является новой статистикой. Канонический факт по-прежнему хранится только в `local_kbacompany_statval`.

## Методологическая основа

При реализации использован предоставленный в базе знаний методический документ `1. МД-БА-01.1-19 ФОРМУЛЫ СОСТОЯНИЙ.docx`.

Из него в BMS перенесены только правила интерпретации, необходимые для программной модели:

- Чрезвычайное положение — отсутствие улучшения или ухудшение статистики;
- Нормальная деятельность — устойчивый регулярный постепенный рост;
- Изобилие — крутой рост;
- Могучество — новый необычно высокий уровень, на котором затем удерживается нормальный растущий тренд;
- Опасность может следовать из очень резкого ухудшения или слишком длительного Чрезвычайного положения;
- Несуществование связано с новым/разваленным постом и не выводится из одной статистики;
- Смена Власти связана с принятием успешно работающего поста/области и также не выводится из одной статистики.

Методика использует качественные понятия «круто вверх», «очень круто вниз» и «необычайно высокий уровень», но не задаёт универсальный процент для любой компании и показателя. Поэтому BMS не содержит скрытых процентов для этих границ.

## Контекст состояния

Состояние относится к конкретной `statbind`, а не только к `stat`.

Это необходимо, потому что один показатель может использоваться одновременно для компании, подразделения, должности и стратегической цели, а достаточный/высокий уровень и управленческий смысл в этих контекстах различаются.

## Версионная политика интерпретации

`local_kbacompany_statpolicy` хранит явную версионную политику одной привязки:

- `dangerdecline` — что в этом контексте считать очень резким ухудшением за период;
- `dangerperiods` — сколько последовательных периодов ЧП считается слишком долгим;
- `affluencegrowth` — что считать крутым ростом Изобилия;
- `powerlevel` — необычно высокий уровень как процент действующей целевой нормы;
- `powerperiods` — сколько периодов высокий уровень должен удерживаться;
- `effectivefrom/effectiveto` — период действия редакции.

Политика не содержит фактов и не заменяет `statnorm`. Новая редакция создаётся additive и не изменяет старую историю. Для уже настроенной привязки и нормы, и политика продолжают свой UUID новой revision, чтобы не появлялись параллельные определения.

## Read-model

`indicator_condition_service::analyze()` получает:

1. каноническую историю `statval`;
2. направление показателя;
3. историю норм конкретной привязки;
4. историю политик состояния;
5. UUID конкретной `statbind`.

Результат содержит рекомендуемое состояние, источник вывода, причину, последнюю direction-aware динамику, длительность ЧП, действующую норму/политику и вспомогательные значения.

### Автоматически определяемые состояния

При достаточных данных и настроенной политике автоматически могут определяться:

- Опасность;
- Чрезвычайное положение;
- Нормальная деятельность;
- Изобилие;
- Могучество.

### Контекстные состояния

`Несуществование` и `Смена Власти` намеренно не угадываются по графику. Для них нужен организационный контекст: новое назначение, передача работающего поста, провал поста и т.п. Последующая интеграция должна брать эти события из канонического организационного/кадрового контура, а не изобретать статистический суррогат.

## Управленческие действия

Сервис предоставляет рекомендуемые формулы действий для семи состояний. Это рекомендации, а не новые объекты задач.

Если рекомендация переводится в исполнение, BMS должен использовать существующий канонический объект `Task` и ссылку из Боевого плана. v0.5.3 не создаёт параллельную сущность Action/Task и не создаёт задачи автоматически без решения менеджера.

## Совместимость Боевого плана

До v0.5.3 Боевой план имел собственную квотную формулу 70/90/110/130 и порог динамики. Для уже опубликованных и закреплённых редакций Боевого плана поведение сохранено через compatibility adapter `indicator_condition_service::legacy_quota_condition()`.

Новая каноническая аналитика показателей не использует эти числа и не считает их общей методикой состояний.

## Историческая разрешимость

При чтении периода выбираются действовавшие тогда редакции нормы и политики. Архивная редакция рассматривается как tombstone с даты архивирования, поэтому архивирование не стирает интерпретацию предыдущих периодов.

## Почему состояние не хранится как вычисленный факт

Автоматическое состояние детерминированно восстанавливается из канонической истории, контекста, нормы и версии политики. Хранение вычисленного значения создало бы второй источник истины и потребовало бы сложной инвалидации при корректирующих append-only фактах или исторических редакциях норм.

Хранить в будущем имеет смысл отдельное управленческое подтверждение/решение, если оно становится самостоятельным юридически или процессно значимым событием. Это не должно быть копией вычисленного факта.

## Продолжение в v0.5.4

v0.5.4 реализует предусмотренную здесь границу: вычисленное состояние по-прежнему не хранится, но самостоятельное решение руководителя сохраняется как immutable governance event и при необходимости переводится в существующий canonical Task/Боевой план.
