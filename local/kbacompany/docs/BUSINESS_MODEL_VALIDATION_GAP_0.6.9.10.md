# BMS 0.6.9.10 — Проверка бизнес-модели и реестр разрывов

## Назначение

Релиз завершает следующий слой BMS Business Model Canvas 2.0 поверх BMS CRUD. Он не создаёт второй финансовый, KPI, проектный или задачный движок.

Каноническая пользовательская цепочка в русской локали:

**Требование собственника → Как есть → Факт / Требуются данные / Гипотеза / Открытый вопрос → Как должно быть → Проверка целевой модели → Разрыв → Способ изменения → Показатель результата.**

## Проверка целевой модели

Для точной редакции бизнес-модели хранятся пять версионируемых контуров проверки:

1. Рынок.
2. Клиент.
3. Экономика.
4. Ресурсы.
5. Требования собственника.

Результаты: `Подтверждено / Частично подтверждено / Гипотеза / Требуются данные / Открытый вопрос / Конфликт`.

Проверка не переписывает записи «Как должно быть». При конфликте создаётся новая редакция бизнес-модели.

### Экономика

Статус «Подтверждено» требует опубликованный `local_kbacompany_finscenario`, закреплённый за той же `Business Model UUID + revision`. Финансовые расчёты остаются в существующем Financial Model domain.

## Покрытие требований собственника

Покрытие считается только по записям «Как должно быть». Связь требования только с «Как есть» не означает реализацию требования в целевой модели.

Текущий Owner Requirement package не содержит отдельного machine-readable приоритета/criticality. Поэтому в 0.6.9.10 все закреплённые требования считаются обязательными для вычисляемого признака «целевая модель согласована». При появлении канонического приоритета правило можно уточнить без смены идентичности требований.

## Реестр разрывов

Разрыв — отдельная versioned BMS-запись со Stable Code `GAP-xxxx`.

Разрыв закрепляет:

- точную редакцию Business Model;
- конкретную запись «Как есть»;
- конкретную запись «Как должно быть» из того же блока;
- почему разница существенна;
- доказательство/основание;
- связанные закреплённые требования собственника;
- существующий BMS Indicator как необязательный показатель результата.

Правило:

**Разрыв = конкретное «Как есть» ↔ конкретное «Как должно быть» + значение этой разницы.**

Разрыв не равен причине, решению, проекту или задаче.

Жизненный цикл первого шага: `Кандидат → Подтверждён → Архивирован`. Следующий слой Change mechanism / GAP → Administrative Scale остаётся отдельным управленческим решением.

## Новые таблицы

- `local_kbacompany_bmcval` — versioned проверки точного BMC snapshot.
- `local_kbacompany_bmcgap` — versioned canonical GAP registry.
- `local_kbacompany_bmcgapreq` — pinned Owner Requirement links для редакции разрыва.

## Границы владения

- Business Model root/items остаются `local_kbacompany`.
- Financial Scenario переиспользуется из существующего Financial Model domain.
- Показатель результата переиспользует canonical BMS Indicator.
- Program / Project / Task / Battle Plan не создаются автоматически.
- GAP → Situation / Administrative Scale будет следующим execution-layer решением, а не побочным эффектом создания GAP.
