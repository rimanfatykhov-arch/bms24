# BMS v0.5.4 — Подтверждение состояния и каноническое исполнение

## 1. Назначение

v0.5.4 добавляет governance-слой между аналитикой показателя и исполнением:

`stat/statval → trend/events → condition read-model → manager confirmation/context event → canonical Task → Battle Plan reference`.

Основное правило: аналитика не должна автоматически превращаться в задачу без управленческого решения.

## 2. Что остаётся read-model

`indicator_condition_service` продолжает вычислять состояние on-read из:

- истории `statval`;
- направления показателя;
- конкретной `statbind`;
- исторически действующей `statnorm`;
- исторически действующей `statpolicy`.

Автоматическое состояние не записывается в БД. Изменение позднего append-only факта, нормы или политики может изменить аналитический вывод, но не переписывает уже состоявшееся управленческое решение.

## 3. Что хранится

Хранится только самостоятельное событие решения руководителя в `local_kbacompany_stateevt`.

Типы событий:

- `confirm` — руководитель подтверждает состояние, совпадающее с текущим аналитическим выводом;
- `context` — руководитель задаёт состояние с учётом контекста, отличающееся от аналитического вывода или не выводимое из статистики.

Для `context` комментарий обязателен.

Событие фиксирует snapshot ссылок и аналитического вывода на момент решения, но не копирует значение показателя.

## 4. Почему событие хранится, а состояние — нет

Автоматическое состояние детерминированно воспроизводимо из канонической истории и методологических редакций, поэтому хранить его вторым источником истины не нужно.

Подтверждение руководителя — самостоятельный факт управления: оно имеет автора, время, контекст и может породить исполнение. Его необходимо сохранить для аудита и исторической трассировки даже если аналитика позже изменится.

## 5. Переход в Task

`task_service::ensure_from_condition_event()` создаёт задачу в единственной канонической таблице `local_kbacompany_task`.

Provenance задачи:

- `sourcekind = condition`;
- `sourceuuid = state event UUID`;
- `sourcerevision = 1`;
- `periodkey = periodkey события`.

Существующий механизм generated-task deduplication не позволяет одному и тому же событию незаметно размножить одинаковое исполнение при повторной обработке того же источника.

## 6. Переход в Боевой план

После создания Task сервис может вызвать существующий `battle_plan_service::add_task()`.

Перед этим `validate_creation_plan_target()` проверяет:

- план существует;
- план доступен актору;
- план является допустимым черновиком для добавления;
- план принадлежит выбранному исполнителю задачи.

Боевой план хранит только ссылку `bplanitem → task`; отдельная копия задачи не создаётся.

## 7. Права

Право подтвердить/контекстуализировать состояние наследуется только из существующего контура управления показателями (`indicator_registry_service::can_manage`). Это сохраняет ограничение: дополнительные бизнес-роли, которым разрешены показатели, не получают автоматически все административные права BMS.

Создание/просмотр Task и доступ к Battle Plan остаются под существующими правилами соответствующих сервисов.

При отображении истории governance events сервис дополнительно проверяет `task_service::can_view_task()` и участие/управление в Battle Plan, чтобы не раскрывать название задачи или реквизиты плана через экран показателя пользователю без доступа.

## 8. Неизменяемость и история

`stateevt` append-only. Следующее подтверждение создаёт новую строку. Событие не содержит task UUID или plan UUID: эти связи разрешаются on-read по canonical Task provenance и существующим Battle Plan references.

Это позволяет не дублировать связь и корректно сохранять историю даже если задача будет завершена/удалена soft-delete или изменится состав Боевого плана.

## 9. Schema change

v0.5.4 добавляет одну таблицу additive migration:

`local_kbacompany_stateevt`.

Существующие таблицы показателей, задач и Боевого плана не перестраиваются и не получают разрушительных изменений.

## 10. Следующий слой

После появления подтверждённого состояния и канонического исполнения следующий аналитический слой — Management Exceptions: выборка отклонений, которые требуют внимания руководителя, без создания ещё одного реестра задач/событий.
