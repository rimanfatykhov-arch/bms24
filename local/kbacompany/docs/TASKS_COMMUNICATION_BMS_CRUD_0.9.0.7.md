# local_kbacompany 0.9.0.7 — Задачи и Коммуникационный центр: BMS UI / CRUD

Build: 2026092501. Статус: ALPHA, не production acceptance.
Target: Moodle 4.1.22; PHP 7.3+ по синтаксическому намерению, runtime 7.3 не проверен.
База: полный локально выданный 0.9.0.6 build2026092500. Последний опубликованный baseline в MASTER до этой работы — 0.9.0.5; промежуточный 0.9.0.6 сохранён в baseline/ Release Kit и не объявляется задним числом отдельно опубликованным.
Основание: согласование пользователя, FireShot Capture 094 (страница 1), BMS-UX-CRUD-001 v0.3 и BMS-MASTER-001 v1.5.4.

## Пользовательский путь

Рабочее пространство → Задачи → список → карточка. Кнопка «Создать задачу» открывает отдельную форму. После сохранения открывается карточка. Задача создаётся в существующем состоянии «Новая», а не в придуманном черновом lifecycle.

В карточке: «Обзор», «Чек-лист», «Результат», «Файлы», «Обсуждение», «История». Редактирование определения задачи — отдельный экран; остальные разрешённые действия — через «Действия» и подтверждение. Работа: создать → начать → указать результат/факт времени → передать на проверку (если назначен проверяющий) → принять либо вернуть с причиной. При отсутствии проверяющего прежнее правило самостоятельного завершения сохраняется.

## Разделение назначения экранов

- Пункт меню и верхняя кнопка «Задачи» ведут в canonical tasks.php. Внутри списка больше нет заголовка «Коммуникационный центр» и обязательного дополнительного перехода к настоящим задачам.
- Коммуникационный центр содержит «Входящие», «Сообщения», «Обсуждения», «Встречи», «Уведомления». Входящие содержат отдельные показатели внимания по каноническим задачам и собственные непрочитанные уведомления. Счётчики задач не выдают данные всех внешних учебных источников за единый факт.
- Встречи открывают существующий модуль встреч. Переписка открывает существующие коммуникационные потоки; внутренний редактор communications.php не перерабатывался.
- Учебные и прежние задачи открываются через «Инструменты → Задачи из других источников». Это read-only проекции с переходом к владельцу данных, не новые копии BMS Task. Их унаследованный объединённый список не заявляется постраничным.
- Подключение учебных источников вынесено в отдельный экран настроек источников для пользователей с действующим правом управления задачами. Для выбора курса сначала применяются Company-bound candidates: существующая явная связь с компанией или активное зачисление её активного сотрудника; затем прежние права и видимость курса. Каталог ограничен 100 кандидатами. Записи enrolment не создаются и не изменяются. Существующие явные связи сохраняются.

## BMS CRUD

Основной список: «Мои задачи», «Поставленные мной», «Мне на проверку», «Наблюдаю», «Просроченные» и «Все задачи» для управленческого доступа. Поиск по названию, фильтры состояния/потока/источника, server-side страницы по 25 записей. Список, доска и сводка используют одинаковые SQL-предикаты. Доска показывает только текущую страницу, что явно подписано. Сводка считает весь отфильтрованный доступный набор в SQL, не только текущую страницу.

Создание/редактирование: результат и описание, участники, сроки и время; связи, включение в Боевой план и вложение в «Дополнительно». Ошибки показываются у полей, текст сохраняется. Даты валидируются как реальные календарные даты. У администратора без membership исполнитель не назначается произвольно первым сотрудником.

Карточка содержит состояние, исполнителя, следующий шаг, данные задачи, связи и отдельные панели. Технический UUID раскрывается отдельно и не заменяется придуманным постоянным кодом: в существующем домене Task поля Stable Code нет. Содержание, комментарии и история разделены. Причина возврата/отмены выводится из существующей истории, а не скрывается в техническом JSON.

Выбор связанной задачи/записи Административной шкалы — ограниченный серверный поиск с Company scope и task ACL. Текущая связь сохраняется в форме, даже если не попала в первую порцию результатов. Доступные published administrative revisions закрепляются существующими UUID/revision. Ссылка в карточке ведёт к существующему редактору-владельцу; подпись отличает закреплённую редакцию от текущей карточки.

Компоненты используют существующий BMS Record Header/Action Bar/View Switcher, scoped CSS и presentation-only JavaScript. Общий переключатель представлений получил aria-current для активной страницы. Вкладки выделены текстом/цветом, переносятся на узких экранах; таблицы и доска прокручиваются внутри контейнера.

## Логика, права, совместимость

Канонические task_service, communication_service, task providers, Battle Plans и File API сохраняются. Новых task/meeting/KPI/knowledge/AI engines и persistent tables нет.

Task list, count, exact-record и parent-picker queries ограничиваются Company + разрешённым task scope до получения строк. Созданные мной и требующие моей проверки задачи не теряются из-за неправильного одновременного фильтра assignee=actor. Наблюдатель не получает право менять определение, выполнять либо принимать задачу только вследствие наблюдения; существующие разрешения на обсуждение/вложения/чек-лист не расширяются новым назначением.

Состав личных переписок ограничен активным участием пользователя. Управленческая роль сама по себе не открывает частные потоки. Уведомление не даёт доступ к прежней закрытой переписке. Список/обзор не отмечают сообщения прочитанными; открытие отдельного обсуждения использует штатный механизм прочтения. Повторное «Прочитано» сохраняет первое время прочтения.

Обычный App Shell использует SQL-счётчики вместо полной загрузки task providers/встреч/переписки ради значков навигации. Полный старый workspace projection остаётся совместимым для прежних специализированных экранов; весь проект не объявляется переведённым на пагинацию.

POST + sesskey + подтверждение + повторная доменная валидация. Session receipts ограничены 2 часами и 40 операциями; повтор той же формы в действующей сессии не повторяет мутацию. Это не durable exactly-once и не гарантия восстановления после потери сессии между commit и сохранением receipt. Повтор удаления уже недоступной задачи безопасно отклоняется.

Явное состояние пункта чек-листа вместо повторяемого toggle не переворачивает результат назад при повторной доставке. Устаревшая версия определения/перехода блокируется существующим revision guard. Создание/сохранение с вложением и опциональной связью Боевого плана оборачивается в общую делегированную транзакцию; физические blobs File API не объявляются транзакционными, возможна штатная уборка неиспользованных объектов.

Исправлен inherited delete defect: обращение к отсутствующей таблице local_kbacompany_bptask заменено существующей local_kbacompany_bplanitem. Удаление задачи остаётся soft delete с историей; ссылки чернового плана удаляются из существующего реестра. Удаление запрещено, если задача включена в нечерновой план, чтобы не ломать состав уже переданного/действующего/закрытого плана.

Прямые GET/HEAD-ссылки communication_center.php?tab=tasks перенаправляются в canonical tasks; для внешних providers — в источники. Старые POST-формы настройки источников не выполняются молча: пользователь получает ссылку на новый экран. Старые task UUID, режимы kanban/analytics и создание через legacy hash поддерживаются. Подмена Company, task UUID, plan UUID и чужих объектов не даёт доступа.

## Границы выпуска

Схема БД, upgrade.php, capabilities, service declarations, scheduled tasks и privacy provider побайтно сохранены из 0.9.0.6. Унаследованные migrations (в том числе doc.filemanifest) по-прежнему требуют штатного Moodle upgrade при переходе со старых версий. KBA Theme и AI companion не изменены. Документы/файлы/версии и Боевой план из предыдущих выпусков включены.

Не добавлены drag-and-drop перемещение статусов, новый мессенджер, AI-автодействия, новые интеграции, массовое удаление, новый task audit engine или Moodle instance per company. История — существующий ограниченный срез task log (последние 50 записей), не восстановление полного аудита задним числом.

## Проверка и установка

См. QA_REPORT. Live Moodle 4.1.22, PHP7.3 runtime, фактическая KBA Theme, реальные File API/uploads/course ACL/SQL drivers/lock contention/session backend, PHPUnit, Behat, production/staging и provider interoperability не запускались.

Резервная копия БД + moodledata + кода → тестовая копия → INSTALL_ME ZIP → штатное обновление Moodle → очистка кэшей. Сервер пользователя в этом шаге не обновлялся. Для установки используется только INSTALL ZIP, не Release Kit.
