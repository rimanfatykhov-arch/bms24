## Интерфейс

Список: один заголовок, кнопка «Создать сотрудника», компактное меню «Инструменты».
Панель старых вкладок ОФС/оргсхем убрана только с ежедневного раздела сотрудников;
сами организационные разделы и их маршруты не удалялись. Представления «Действующие»,
«Исключённые», «Все»; поиск имени/фамилии/email/телефона, фильтр «С назначением» /
«Без назначения». Колонки: сотрудник, должность/подразделение, контакты, состояние
связи с компанией, изменение. Имя открывает карточку; дублирующей кнопки «Открыть»
в каждой строке нет. Синхронизация больше не является повседневной колонкой.

Список выбирает один наиболее актуальный период связи на пользователя: действующий
приоритетнее завершённого, затем effectivefrom/id. Все периоды остаются в истории.
SQL-поиск/фильтры/count и страницы по 25 выполняются до получения результатов внутри
Company. Корпоративная compatibility-проекция тоже отбирается на сервере, read-only.
Завершённая canonical связь не возвращается в действующие через legacy fallback.
Текущая основная штатная должность приоритетнее совмещения; иначе берётся последнее
действующее назначение. Фильтр назначения относится к этой штатной проекции.
Свободная строка должности из учебного профиля не выдаётся за canonical назначение;
данные исходного профиля не меняются. Назначения с будущими/истёкшими датами исключены.

Карточка: имя, компания, отдельные состояния связи и учётной записи, следующий шаг,
основное «Редактировать профиль» и вторичные «Действия». Вкладки «Обзор»,
«Организация», «История связи», «Синхронизация». Последняя доступна только при
существующем праве управления организацией / site admin. Данные соответствующей
вкладки загружаются по её выбору, а не все сразу. История связи имеет страницы и
позволяет открыть конкретный прошлый период read-only. Это не полный журнал
редактирования глобального профиля и не снимок его прежних контактов/назначений.

Создание/редактирование: смысловые группы, подписи над полями, обязательность,
проверки длины/имён/email/телефона, сохранение текста при ошибке, ошибки около полей.
Сохранение возвращает в карточку, отмена — в карточку или список при создании.
Исключение: самостоятельный экран и явный checkbox; GET не выполняет исключение.
UUID, Moodle ID, внешний contact ID и последняя ошибка находятся в раскрываемых
технических сведениях вкладки синхронизации. Её статус — существующая локальная
проекция очереди, не текущая сетевая проверка Bitrix24.

Вёрстка локализована в .bms-ecu, общие Record Header / Field Groups / Action Menu
переиспользованы. На ширине до 700px таблицы перестраиваются в карточки; поля/вкладки
переносятся. Меню на узком экране раскрывается внутри ширины содержимого.
Пояснение об отсутствии автоматического зачисления перенесено в справочный блок
списка и формы, а не постоянно занимает верхний экран.

## Логика и безопасность

Используется существующий employee_service и Company/permission services.
Бизнес-роль не добавляет capability автоматически. Сотрудник с разрешением просмотра
компании видит её доступный реестр; личный-only режим не вводился. Управленческие
действия требуют прежних прав. Site admin сохраняет путь без membership.

Поля профиля принадлежат общему Moodle User, а не копии контакта в компании — форма
предупреждает об этом. Существующий domain service обновляет профиль и ставит команду
в существующую очередь KBA Connect. Должности, подразделения, задачи, планы,
компетенции и зачисления не редактируются через форму профиля.

Повторное создание по email действующего canonical сотрудника текущей компании
открывает его карточку без перезаписи имени/телефона и сброса ролей. Совпадение с
учётной записью вне этого набора даёт общее сообщение, не поиск/раскрытие другого
пользователя и не автоматическое присоединение. Это ограничение нового UI: прежние
integration/canonical методы сохранены. Exact-email uniqueness является системной
проверкой Moodle User, не глобальным справочником сотрудников. Новый UI передаёт
opt-in guard directory_newonly существующему create_employee, чтобы его повторная
проверка не превратила создание в присоединение чужого пользователя.

Редактирование и исключение используют optimistic fingerprint профиля/периода связи;
устаревшая форма отклоняется. Использован existing document_request_service для
Company/actor/object/action/membership-bound session receipts: 2 часа, 30 форм в общей
сессии; повтор с тем же содержимым возвращает сохранённую карточку, иной payload
отклоняется. Это не durable exactly-once; потеря сессии после commit остаётся пределом.

UI-команды имеют locks и делегированную транзакцию существующих DB-записей/очереди.
CRM и другие старые редакторы не обязаны брать эти UI-locks: защита не объявляется
гарантией против всех внешних concurrent writers. Core events/cache/preferences и
реальный Moodle transaction behaviour отдельно требуют live проверки.

Исключение мягко завершает существующие активные membership этой компании и
сохраняет историю, Moodle User и команду интеграции. Оно не удаляет пользователя,
не закрывает за него задачи/планы/штатные назначения и не обещает мгновенную
синхронизацию. Это не кадровое увольнение и не новое управление доступом в learning.
Старый email-like телефон не показывается второй почтой: отмечается необходимость
уточнения. Исходное значение хранится до явного редактирования, миграции данных нет.

## Сохранённое и исключённое из scope

install.xml, upgrade.php, upgradelib.php и hotfix norm_ix сохранены побайтно. Новых
DDL-шагов, capability/API/cron declarations, Privacy storage, Theme или AI изменений нет.
Все прежние разделы остаются в полном пакете. Legacy employees_context/employee_context
и диагностика остаются compatibility API; их полная пагинация не заявляется.
Новых фото-загрузок, приглашений, восстановления исключённого сотрудника, HR-договоров,
отдельного profile-audit, массовых операций, отдельного движка коммуникаций или ERP нет.
