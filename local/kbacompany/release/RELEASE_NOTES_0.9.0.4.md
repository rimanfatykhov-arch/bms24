## Работа в интерфейсе
Путь: Управление → Документы. Главная — ListView, а не форма создания.
Одна строка соответствует документу. Есть код, кликабельное название, тип,
должность-владелец, статус последней доступной редакции, отдельная действующая
редакция и время изменения. Поиск по коду/названию и фильтры типа, статуса и владельца
выполняются в SQL текущей компании. 25 строк на странице. Содержание документов
в список не загружается. Полностью архивные документы скрыты по умолчанию;
архив последнего отменённого черновика не скрывает более раннюю действующую редакцию.

«Создать документ» открывает отдельную форму с понятными секциями и подписями над
полями. Сохранение создаёт черновик и открывает его карточку. «Редактировать»
отдельно открывает только последний черновик. Ошибки связаны с полями и сохраняют
введённые значения. Отмена создания возвращает в список; отмена редактирования —
в карточку. Действующая редакция не редактируется в обход нового выпуска.

Карточка содержит код, название, статус, номер редакции и владельца, следующий шаг,
содержание и связанные записи. Вкладки: Обзор, Согласование, Ознакомление,
Редакции, История; для управляемых форм — Записи по форме.
История управления видна управляющим, рассмотрение — управляющим либо назначенному
согласующему в текущем состоянии review. Обычный сотрудник видит только свои
ознакомления и заполненные записи. Недоступные вкладки не изображаются как нулевой
объём данных. Технические UUID, хеши и source pins скрыты в раскрываемом блоке.

Операции над карточкой находятся в «Действия» и открывают отдельный экран подтверждения:
назначить согласующего, направить на рассмотрение, согласовать/отклонить, вернуть
на доработку, утвердить, опубликовать, ввести в действие, создать новую редакцию,
отменить, архивировать, назначить/подтвердить ознакомление, создать запись по форме.
Показываются только допустимые операции по существующим правам и статусу.
Все изменения — POST + sesskey. Действия требуют явного подтверждения.

## Сохранённая логика документов
Цепочка прежняя: черновик → рассмотрение → согласован → утверждён → опубликован → действует.
Итоговое утверждение не подменяется решением согласующего. Публикация не активирует
документ автоматически. Вместо Unix timestamp пользователь вводит календарную дату
в часовом поясе Moodle; после наступления даты требуется отдельное «Ввести в действие».
Действующая редакция сохраняется до явной активации замены. Предыдущая тогда получает
статус superseded, её содержание, ознакомления и история не переписываются.

Коды новых ручных документов генерируются как DOC-xxxx существующим stable_code_service.
Существующие коды и UUID не перенумеровываются; новый черновик редакции сохраняет их.
UI не принимает пользовательский code. Явные коды остаются поддержаны для прежних
внутренних service callers, но изменение уже присвоенного кода запрещено.
Счётчик может содержать пропуски после неуспешной записи; номера не переиспользуются.

Для СТП сохранён прежний код и точный снимок опубликованной модели процесса.
Ссылка source=stp открывает просмотр снимка и подтверждение. Изменившийся после
просмотра источник отклоняется. Содержание СТП нельзя подменить ручной формой;
новая редакция явно принимает свежий опубликованный снимок. Это не редактирование
канонической модели процесса. Полная информация старого снимка доступна в его
раскрываемом блоке; данные не пересоздаются из текущего источника при просмотре.

Ознакомление всегда привязано к точной действующей редакции и самому сотруднику;
оно не означает подтверждения компетенции. Заполненная запись по форме неизменяема
и не меняет исходную форму. Отмена/архивирование не удаляют бизнес-данные физически.
Владелец документа — ответственность по должности, не автоматическое назначение прав.
Исторический неактивный владелец сохраняется при неизменённой связи; новый выбор
неактивной/чужой должности отклоняется.

## Защита и история
Используются существующие document_service, doc/docreview/docack/record/aclog и codecounter.
Schema, upgrade.php, ACL, services, scheduled tasks и privacy provider byte-identical 0.9.0.3.
Переходы, рассмотрение, ознакомления и записи по формам защищены блокировкой
Company + Document и транзакцией, включая запись в прежний audit log.
Черновик и действия сравнивают серверный снимок формы с актуальной записью под блокировкой.
Старый текст не перезаписывает более новое изменение. Пустой документ не уходит на
рассмотрение; отклонение требует комментария. Назначения принимают только активное
членство и не удалённый/не заблокированный Moodle account.

Формы дополнительно используют ограниченные квитанции текущей Moodle-сессии:
Company/actor/document/revision/action, 2 часа, до 30 форм, без текста документов.
Точный повтор успешно отправленной формы возвращает результат без повторной записи;
другой payload с тем же ключом отвергается. Это session-level replay protection,
НЕ гарантированная durable idempotency между сессиями и НЕ доказательство восстановления
при сбое между DB commit и сохранением Moodle session. Реальное конкурентное
поведение Moodle lock/session backend требует отдельной live-проверки.

История показывает существующие события aclog с действием, автором и временем,
без раскрытия raw oldvalue/newvalue в UI. Старые события не восстанавливаются задним числом.
