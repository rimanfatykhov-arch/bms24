# BMS24 RC29 — build2026101622

Тема этапа: **Боевой план → Метрики: управленческий план и сопоставимое промежуточное выполнение**.

## Что реализовано

1. В ячейке **«План периода»** каждой метрики появилась раскрываемая форма **«Задать план»**, видимая только пользователям с каноническим правом `indicator_registry_service::can_manage`. Для обычного сотрудника сохраняется только «Внести факт» и просмотр результатов.
2. Для **дневных метрик** руководитель задаёт значения по конкретным датам семидневного боевого плана (одна форма с семью днями). Для **недельных метрик** единственная допустимая дата плана — понедельник плана. Пустое поле НЕ удаляет ранее записанное значение; сумма дневных планов в заголовке вычисляется из общего реестра.
3. План записывается через `product_service::record_value(..., 'plan', ...)` в каноническую append-only `local_kbacompany_statval` с тем же UUID метрики, что используется в её паспорте, по календарной дате. Не вводятся дублирующие объекты или таблицы.
4. **Корректировки планов:** повторное значение, равное предыдущему, игнорируется; изменение существующего значения требует причины и создаёт ревизию с автором. Все изменения недели подтверждаются одной транзакцией: при отказе одного дня остальные не должны фиксироваться частично.
5. **Доступ и целостность:** на сервере проверяются компания, доступ к боевому плану, открытый статус, привязка к должностной метрике, менеджерское право управлять метриками, количество и конкретные даты вводимых целей, формат числа и причина исправления. В обработчике POST: `sesskey` и whitelist действий. Изменение факта остаётся под отдельным узким разрешением владельца боевого плана; настройка цели не наследует его права.
6. **План — факт — отклонение:** для дневных показателей полный план недели и накопленный факт показываются независимо, но **промежуточная оценка** (статус, сумма и процент отклонения) вычисляется по *одним и тем же датам с фактом и с планом*. План будущих дней не приравнивается к фактическому нулю; если хотя бы для одного дня с фактом нет плана, оценка не создаётся. Возле сравнения и статуса указано, что это промежуточная оценка, а не результат всей недели.
7. Сохранены уже введённые факты (например, 42 000 ₽ + 20 000 ₽), UUID, правила критичности и статусов, история, существующие маршруты и служебные модели задач. `theme_kba` и `local_kbaai` не менялись. Схема БД без изменений.

## Установка

1. Сохранить резервную копию БД и `/local/kbacompany`.
2. Установить `INSTALL_ME_local_kbacompany_v1.1.0-rc29_build2026101622.zip`, корневой каталог архива — `kbacompany`; целевой путь `/local/kbacompany`.
3. Выполнить стандартный upgrade Moodle и очистку кэша.
4. Запустить сценарии из `ACCEPTANCE_BMS24_RC29_build2026101622.md`.
5. Не откатывать файловую версию до 2026101621 без согласованного пониженного контроля версий, иначе Moodle может вернуть `cannotdowngrade`.
