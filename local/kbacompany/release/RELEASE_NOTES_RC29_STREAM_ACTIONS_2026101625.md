# BMS24 1.1.0-rc29 — build2026101625
## Battle Plan Stream Actions / Recurring CRUD Entry
Дата: 16.10.2026. Основа: проверенный SOURCE build2026101624.

### Реализовано
1. В заголовках всех пяти потоков боевого плана появились контекстные действия «+ Создать задачу»: **Изменения — программы и проекты** (`change`), **Регулярная работа** (`run`), **Текущая работа по посту** (`operate`), **Обучение / развитие** (`develop`) и **Вне плана** (`unplanned`). Каждая кнопка использует фактический key потока, передаваемый с сервера. Никаких дополнительных хранилищ задач.
2. Для контекстного создания зафиксирован поток в форме в видимом read-only поле и hidden-параметре. Название и ожидаемый продукт обязательны; исполнитель — владелец боевого плана, срок — обязательный; остальные поля по BMS-UX-CRUD-001 находятся в блоке «Дополнительные параметры». Проверки серверной допустимости потока сохранены. После сохранения — возврат к выбранному разделу таблицы.
3. Для **действующего, ранее согласованного** боевого плана введён узкий сценарий добавления **только новой ручной задачи**, с теми же ACL, company UUID, каноническим `task_service::create()`, транзакцией и блокировкой плана. Сведения о согласовании не переписываются. Поздняя задача распознаётся по времени привязки к плану (`bplanitem.timecreated > bplan.approvedat`) и помечается в веб-таблице и DOCX как «Добавлено после согласования». Импорт существующей задачи, библиотека, шаблоны и синхронизация регулярных задач в активный план **по-прежнему запрещены**; `submitted` и `closed` нельзя изменять этим способом.
4. В разделе, который в действующей модели именуется «Регулярная работа», рядом с «Создать задачу» появилось «Настроить повторение». Это ведёт на каноническую `recurring_tasks.php?view=create&plan=...&stream=...`, отображающую одну форму новой серии вместо перегруженного списка + редактирования + создания. Содержимое серии по-прежнему сохраняется как **черновик**, затем активируется отдельно. Переход проставляет назначение владельца плана только если он есть среди доступных исполнителей. Генерация экземпляров остаётся канонической, синхронизация плана — только для черновиков.
5. Для формы серии дополнены `id` у элементов, чтобы подписи над полями имели корректные связи `label/for`.

### Важное различие: разовая задача и повторение
Разовая задача в потоке `run` — один канонический task UUID. Регулярная серия — одна запись определения с расписанием (cadence, weekdaymask, интервалы, назначение), которая затем порождает отдельные канонические задачи-исполнения. Создание определения **не добавляет** автоматически экземпляры в уже одобренный план. UI предупреждает об этом.

### Анализ BMS CRUD регулярных задач
Текущий `recurring_tasks.php` исторически совмещает **реестр, карточку/редактирование выбранной серии и большую форму создания** на одной странице. Это не соответствует утверждённой модели `ListView → DetailView → EditView`. Ввиду риска сломать редактирование и переходы, релиз вводит отдельный чистый `view=create` только для нового пути из боевого плана и сохраняет старые URL.

**Следующий UX этап**: отделить полноценные List/Detail/Edit для `RecurringTaskDefinition`; отразить частоту в человекочитаемом preview «Пн–Пт, ежедневно», показать ближайшие 3–5 срабатываний, статус серии, «Активировать/Пауза/Архив» в DetailView, создание/редактирование с явными обязательными полями (название, продукт, исполнитель, периодичность, дата начала), адекватным показом зависимых настроек (неделя месяца только при monthly), отдельным управлением шаблонами и историей ревизий. Реализацию этих изменений делать после установки и приёмки RC29 build2026101625.

### Безопасность и миграции
- Входы `GET`/`POST` валидируются, любые изменения — POST + sesskey, контролируется company UUID и права на конкретный боевой план.
- `create_manual_task` выполняется транзакционно; ссылка в `local_kbacompany_bplanitem` и задача создаются в одной транзакции без параллельной БД. Классический `add_task` остаётся ограничен черновиком.
- Внешние провайдеры задач и синхронизация серий не получают возможность изменять утверждённый план.
- `version.php=2026101625`; новый уникальный монотонный no-DDL savepoint, данные/UUID/схема БД сохраняются.

### Установка
Сделайте резервную копию БД и `/local/kbacompany`, распакуйте INSTALL_ME ZIP в `/local/kbacompany`, выполните Moodle upgrade и очистите кэши. Откройте боевой план в состоянии «Согласован / в работе» → «Задачи»; убедитесь, что в каждом разделе есть «+ Создать задачу». Проверьте разовую задачу и метку после согласования, затем «Настроить повторение». Для черновика проверьте стандартный выбор существующей задачи/синхронизацию серии.
