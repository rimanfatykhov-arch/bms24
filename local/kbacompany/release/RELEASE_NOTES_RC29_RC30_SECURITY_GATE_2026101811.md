# BMS24 — 1.1.0-rc29 build2026101811

## Область релиза
Начальный **этап стабилизации к RC30**: исправление недостоверной проверки межкомпанейного доступа, усиление внутренней диагностики управленческих ссылок, матрица живой приёмки. Это **не выпуск стабильной RC30**.

## Исправленные дефекты

1. Ранее `cli/qa_management_cycle.php` проверял `$deniedactor` на доступ к `$deniedcompany`; если этот пользователь законно состоял во второй компании, диагностика завершалась `HOLD`, а исходный пользователь компании A против B не проверялся. Теперь проверяются четыре пары: A→A, B→B (позитивные контроли), A→B, B→A (отрицательные контроли), и результат без обеих пар **никогда не называется PASS**.
2. `management_cycle_acceptance_service` ранее принимал абсолютный URL внешнего домена, если путь и `uuid` выглядели внутренними. Теперь проверяет совпадение host/scheme/port с Moodle `$CFG->wwwroot`, отбрасывает path traversal и внешние protocol-relative URL. Это **контроль диагностического read-model**; он не заменяет обработку разрешений на самом endpoint.
3. Проверка прежней версии 1810 переписана на допустимое «версия не ниже 1810», чтобы продолжить регрессию в новых сборках; проверки безопасности не отключены.

- `cli/test_rc30_company_isolation.php`: проверки успешной изоляции, легитимной двойной членской роли, сломанного контрольного кейса, совпадающих идентификаторов и исключения резолвера.

## Технические ограничения
- Проверки выполняются на PHP CLI среды сборки; Moodle 4.1/PHP 8.1 на целевом сервере **не исполнялись**.
- `qa_management_cycle` — read-only и не тестирует транзакционные CRUD-сценарии, веб-сессии, PHP-FPM и многопользовательскую нагрузку.
- Вход в локальный `qa_management_cycle` должен быть только из защищённого CLI, не из HTTP.
- Наличие двойного членства или `viewallcompanies` в тестовых аккаунтах даёт `HOLD`, а не безосновательное обвинение в уязвимости.
- Исправление не добавляет таблиц, не меняет сущности/права и не создаёт дополнительную нагрузку на страницы.

## Установка и приёмка
1. Сделать резервную копию БД и плагина. На стенде выполнить штатное обновление Moodle до `2026101811`, очистить кэш.
2. Проверить основные страницы рабочего пространства, задач, Боевых планов, управленческого обзора.
3. Протестировать управленческий цикл и матрицу RBAC согласно `docs/RC30_STABILIZATION_ACCEPTANCE_2026101811.md`.
4. Запустить `php local/kbacompany/cli/qa_management_cycle.php --company=<UUID_A> --actor=<USER_ID_A> --week=2026-10-19 --denied-company=<UUID_B> --denied-actor=<USER_ID_B>` с непривилегированными, корректно разграниченными тестовыми пользователями.
5. Зафиксировать фактический результат, браузер, активные версии Moodle/PHP/БД, p50/p95 и логи PHP/Moodle. Любой непрошедший блокирующий сценарий оставляет RC30 со статусом HOLD.
