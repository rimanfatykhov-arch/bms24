# BMS24 — local_kbacompany 1.1.0-rc29 — build2026101839

## Цель
Этап A / стабилизация задач: единая календарная дата для вычисления просрочки и окна «Ближайшие 7 дней» в списке, сводке и подзадачах. Накопительный релиз поверх `build2026101838` (полный плагин).

## Проблема
До build1839 `task_service.php` и `task_ui_service.php` проверяли срок через UTC (`gmdate('Y-m-d')`), тогда как `tasks.php`, Боевые планы и часть общего BMS24 workspace используют дату текущего пользователя Moodle (`userdate`). На границе локальных суток возникала возможная рассинхронизация: одна задача считалась просроченной в одном разделе и непросроченной в другом; окно «7 дней» тоже начиналось не с локального дня пользователя.

## Исправления
1. **`task_service::reporting_dates(?int $timestamp = null)`** возвращает `today` и `until`, даты формата `YYYY-MM-DD` в текущем часовом поясе Moodle. Окно включает сегодня и 6 следующих календарных дат; прибавление дней выполнено календарно, независимо от летнего/зимнего времени.
2. Единая дата применена в списке, аналитике, KPI просрочки, фильтрах `overdue`, `soon`, `subtaskoverdue`, проекциях задач по сотрудникам, статусе подзадач и связанных представлениях.
3. `task_ui_service` сравнивает срок с той же датой, что SQL-предикаты, во вкладках «Список», «Доска» и «Подзадачи».
4. Обновлён устаревший тест `task_service_test.php`: он больше не требует версии контракта 0.5.6, когда текущий исходный контракт уже имеет 0.5.7; сравнение использует константу сервиса.
5. Добавлен PHPUnit `tests/task_reporting_dates_test.php`, проверяющий разные часовые пояса и границы DST; расширен `task_execution_analytics_test.php` на совпадение «Ближайшие 7 дней» и фильтров по календарному интервалу.
6. Обновлены `version.php`, штатный savepoint `db/upgrade.php`, реестр и метаданные релиза. **Таблицы и данные не изменяются.**

## Совместимость и границы
- Moodle 4.x, API `userdate()` уже используется в существующем BMS24.
- Бизнес-права, компании, основные запросы и состояние задач не изменялись; изменяются только даты сравнения для отображения и фильтрации.
- Нет изменений `db/install.xml`, языковых файлов, схемы ролей, новых прав и CSS/JS.
- Если пользователи из разных часовых поясов смотрят одну компанию на границе календарного дня, вывод о просрочке может различаться по локальной дате каждого; это ожидаемая семантика после изменения.
- Точные временные значения `duetime` этим релизом не перерабатывались; срок оценивается по календарной дате, как и прежде.

## Установка
1. **Если build1838 ещё не проверен на сервере, сначала зафиксируйте статус его приёмки.** build1839 включает изменения 1838 и может устанавливаться поверх 1837/1838, но не заменяет тестирование исправленного TypeError.
2. Сохраните резервную копию БД и текущего `local/kbacompany`.
3. Установите полный `INSTALL_local_kbacompany_1.1.0-rc29_build2026101839.zip` (верхний каталог `kbacompany/`).
4. Выполните `https://edu.kzn.mba/admin/index.php`; очистите кэши Moodle и, при необходимости, OPcache.
5. Проверьте «Задачи → Список / Доска / Сводка» и переходы по метрикам; «Ближайшие 7 дней», «Просроченные», «Просроченные подзадачи», фильтр по исполнителю и проекту.
6. Для пограничного случая проверьте задачу со сроком **сегодня** в локальном часовом поясе пользователя: она не должна считаться просроченной до наступления следующего локального календарного дня. На границе суток сопоставьте все три представления.
7. Проверяйте сотрудников с разными правами и компании по отдельности. Зафиксируйте серверные PHP Warning / TypeError.
