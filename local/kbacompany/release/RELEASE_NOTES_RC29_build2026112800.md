Upgrade step 2026112800 creates six additive tables from install.xml — `local_kbacompany_wprincipal` (work principals; A1.1 registers only `ai_agent`, which never has a Moodle user, login, token, session, role or capability), `local_kbacompany_wpaudit` (immutable principal journal), `local_kbacompany_wpgrant` (grants in RBAC 2.0 form, deny by default, scopes `own`/`position`/`explicit_object`, risk R0–R3, expiry at most 90 days, renewal only by a human as a new revision), `local_kbacompany_wpdeleg` (schema reserved, unused until A3), `local_kbacompany_posoccup` (non-human position occupancy, two persons for agent mode) and `local_kbacompany_posoccuplog` (immutable occupancy journal). Services: `principal_registry_service`, `principal_grant_service`, `position_occupancy_service` (with a read-only OccupancyView that keeps human vacancy and agent functional coverage apart), `principal_context_service` parallel to `company_context_service`, and `principal_permission::can`. Only the logged-in human with `can_manage_organization` in the company writes the registries; issuing and renewing grants additionally needs the separate grant authority, which until the owner decides (OD-A11-1) is the site administrator only, while an organisation manager may still revoke; changes run under the principal lock and one transaction that increments `authzrevision`. Field names differ from the A0 draft only where SQL reserves the word: `occupancymode` (A0 `mode`), `constraintjson` (`constraint`), `eventname` (`event`). Existing tables and rows (`posassign`, `plannedcount`, `poscover`, tasks, history) are untouched; no backfill. Behind `local_kbacompany/bmos_enabled` (default off): with the switch off nothing reads or writes the registries. No Command Gateway, agent commands, runtime, registry UI, models, keys or network calls. Pairs with Corporate 2026111100.
