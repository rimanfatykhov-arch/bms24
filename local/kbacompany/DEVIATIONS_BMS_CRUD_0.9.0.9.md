## Пользовательская регистрация без числовой нормы
Активный сотрудник текущей компании с существующим правом viewowncompany может
отправить сообщение. Обязательны название, описание наблюдаемого факта, место /
контекст и дата обнаружения. Автор определяется сервером. Известное требование,
текстовое подтверждение и ссылка на точную действующую редакцию управляемого
документа необязательны. Отсутствующее требование не подменяется выдуманной нормой.
Сообщение получает DEV-xxxx и состояние «Ожидает разбора» (reported), а не
автоматическое признание несоответствия. Числовой факт, UUID нормы и утверждения
для ручного сообщения хранятся как NULL, не как ноль или фиктивные UUID.

Сотрудник видит только свои ручные сообщения, в том числе результат рассмотрения;
не видит чужие сообщения и количественные отклонения. До рассмотрения автор
может уточнить своё сообщение; после рассмотрения исходный текст не переписывается.
Управленческий доступ остаётся за существующей проверкой владельца/руководителя
и capability. Назначение ответственной должности не добавляет прав; сайт-администратор
сохраняет административный путь без собственного membership. Новых capabilities нет.

## Разбор и исправление
Руководитель отдельно подтверждает несоответствие либо отклоняет сообщение с
причиной. Подтверждение требует указать подтверждённое требование и критерий
проверки результата; можно сразу назначить ответственную должность и срок.
В этой версии ответственность и срок назначаются при рассмотрении; отдельное
переназначение уже подтверждённого случая не добавлено.

Последующий путь: разбор причины → связь с существующей задачей BMS → выполнение
и приёмка в каноническом центре задач → повторная проверка результата → явное
закрытие руководителем. Гипотеза причины обязательна перед связью/проверкой.
Для проверки должны быть приняты все активные связанные задачи и хотя бы одна
задача должна быть связана. Для BMS Task принимается done с непустым результатом;
legacy workflow-задача использует прежнее accepted.

Для ручного несоответствия руководитель указывает дату, доказательства и результат
«Соответствие подтверждено» / «Не подтверждено». Успешная проверка даёт verified,
но не закрывает случай автоматически. Изменение причины, состава или редакции
задач после проверки делает прежнее подтверждение недостаточным для закрытия.
Неуспешная проверка возвращает случай к корректирующим действиям.
Закрытие, отклонение и отмена сохраняют запись и историю; физического удаления нет.
Состояния: reported/open/analyzed/correcting/verified/closed/rejected/cancelled.
Отклонение сообщения и отмена подтверждённого случая — разные операции.

Причина остаётся обоснованной гипотезой; завершённая задача не доказывает устранение
причины. Наблюдения/повторные проверки не записываются в факт статистики,
не повышают компетенции и не меняют зрелость BMS24 автоматически.

## BMS UI / CRUD
Главный экран — реестр без встроенной большой формы: поиск по коду/названию,
фильтры по состоянию и способу регистрации, представления «Все доступные»,
«Мои сообщения», «Ожидают разбора», «Просроченные» и страницы по 25 записей.
Поиск, count и страницы ограничиваются Company и правами до получения строк.
Пустой реестр предлагает регистрацию, а не блокирующую информационную страницу.

Создание и редактирование отдельны; поля сгруппированы; ошибки рядом с полями,
введённые данные сохраняются; Save возвращает в карточку. Карточка содержит код,
состояние, автора, ответственность, следующий шаг и вкладки Обзор / Разбор /
Корректирующие задачи / Проверка результата / История. Редактирование исходного
сообщения — отдельная primary action только у его автора до рассмотрения.
Другие разрешённые операции находятся в «Действиях» с явным подтверждением.
История — существующие бизнес-события с автором, временем и причиной, с пагинацией;
не новый движок версий и не восстановление отсутствовавших старых событий.
Технические UUID и методические ограничения скрыты в раскрываемом блоке.
Узкие экраны: таблицы преобразуются в карточки, формы и вкладки переносятся.

Справочники документов, должностей и задач ограничены на сервере 40 строками
на страницу и поддерживают поиск; утверждённые пакеты норм — 25 на страницу.
Поиск сохраняет выбранное значение. Ошибка загрузки не стирает форму.
Связанные канонические задачи, проверки и история имеют страницы по 25 записей;
legacy workflow-задачи имеют отдельную пагинацию и доступны только руководителю.
Просмотр не меняет данные, не завершает задачи и не отмечает их принятыми.

## Сохранение старого сценария
Отклонение по утверждённой числовой норме остаётся доступным руководителю.
Сохраняются точные снимки нормы, сравнение десятичных чисел, отсутствие границ
как unbounded, проверки периода и запрет выдавать изменение нормативного порога
за улучшение. Нулевой факт остаётся валидным числом; отсутствие факта не равно нулю.
Старые связи с wfwork и структура старого fingerprint сохраняются. Новые связи
используют canonical BMS Task через существующий devlink с taskengine=bms;
legacy taskengine по умолчанию workflow. Задачи не копируются.
Старые GET ссылки с deviation=UUID открывают карточку. Legacy POST без нового
защитного ключа отвергаются; пользователь должен открыть новую форму.
Существующий manager-scoped compatibility API context() сохранён; его полный
company-scoped список НЕ объявляется новым пагинированным UI/API. Ежедневная
страница использует новый ограниченный browse().

## Хранение и безопасность
Нет новых таблиц. В deviation добавлены 11 полей сообщения/критерия/ответственности,
в devlink — taskengine; у шести полей deviation/devcheck снят NOT NULL для ручных
сообщений. Добавлены три company-scoped индекса, включая уникальность Company+code.
Старые записи получают quantitative/workflow по умолчанию; их UUID, статусы,
факты, связи и история не переписываются, старые коды не назначаются задним числом.

Операции используют POST+sesskey, существующие session receipts, проверку текущей
редакции, повторную доменную валидацию, Company lock и согласованные с Task service
task locks, транзакцию с audit. Повтор той же формы в действующей сессии не создаёт
дубликат, изменённый повтор отвергается. Ограничение receipts: 2 часа / 30 форм;
это не durable exactly-once и не гарантия повторного использования после потери
сессии между DB commit и сохранением receipt.
Company UUID нормализуется существующим сервисом перед SQL/записью/блокировкой.
Task service получает только reusable SQL visibility helper; Task lifecycle не меняется.
Расширены metadata, поиск субъектов, export predicate и очистка персональных данных
существующего privacy provider. Авторизованное удаление персональных данных —
отдельное исключение из обычного сохранения истории. Полный Moodle Privacy API
не проверялся. Новые таблицы, ACL/API/cron, AI plugin и изменения KBA Theme отсутствуют.

## Граница выпуска
Непосредственная загрузка новых файлов в несоответствие не добавлена: доказательства
текстовые, можно выбрать существующий управляемый документ точной редакции.
Вложения самих задач и документов остаются в их существующих разделах. Ссылка
на документ не создаёт его копию; после изменения доступа прежний reference
сохраняется, но недоступная редакция не раскрывается пользователю.
Новых автоматических уведомлений, анонимных жалоб, обязательного SLA, авто-детектора,
нового анализа повторяемости и AI-рекомендаций нет. Odoo/Bitrix/learning ownership
сохраняется. Это устанавливаемый ALPHA-пакет, не deployment или production acceptance.
