# Политики и директивы — BMS CRUD 0.9.0.8

## Основание и границы

BMS-UX-CRUD-001 v0.3; MASTER v1.5.5; точная база INSTALL0.9.0.7 build2026092501.
Домен остаётся в policy_service и local_kbacompany_policy; action audit — existing
aclog. Новых сущностей, второго document/knowledge/task engine нет.
KBA Theme не меняется. UI-рендерер не выполняет записи; domain service
определяет права, состояние и повторно валидирует ввод.

## Пользовательский путь

Управление → Политики и директивы → список → Создать → Сохранить черновик →
карточка. Для публикации: заполнить дату начала и ссылку на документ →
Действия → Опубликовать → причина и подтверждение.

List: поиск по коду/названию, фильтры типа/статуса, 25 записей на страницу.
Одна строка на UUID; тела и все редакции ради списка не загружаются.
Detail: код, название, тип, состояние, редакция, ответственный, следующий шаг.
Вкладки: Обзор / Связи / Редакции / История. Related data загружается только
для выбранной вкладки, история и связи имеют собственную пагинацию.
Edit/Create: наименование/тип/назначение; владелец и область применения;
период и ссылка; основание и комментарий. Пары label/control, ошибки возле
полей, сохранение введённого текста. Cancel/Save возвращают в карточку;
при отмене создания — в список. Технические UUID находятся в «Дополнительно».

## Canonical identity

POL-xxxx для политики, DIR-xxxx для директивы, существующий company-scoped
stable_code_service и codecounter. Allocator учитывает максимальный исторический
suffix соответствующего префикса в компании; зарезервированные коды не
перенумеровываются. В UI код не вводится. Legacy internal callers могут при
первом создании передать явный код. Код и тип существующего UUID неизменяемы.

## Редакции и состояния

Сохраняется существующий append-only lifecycle draft / published / withdrawn.
Каждое Save и каждое действие создают новую строку редакции: номера не
обязательно соответствуют только опубликованным версиям. Причины и авторы
сохраняются на существующих строках; прошлые записи не переписываются.
Изменить опубликованный текст можно через New revision и новый черновик.
Публикация и отмена требуют основания и подтверждения. Отмена доступна только
когда последняя редакция опубликована. Отдельного действия отмены черновика
или возврата на согласование в этом выпуске нет. Утверждение/согласование
с документным lifecycle не смешиваются.

При новом черновике reader получает последнюю опубликованную редакцию;
manager — последнюю рабочую с переходом к опубликованной. Reader не получает
черновые тексты и комментарии даже в истории/API. Явная отмена закрывает
читателю доступ к отозванной политике и её прошлым публикациям; manager
сохраняет историю. Даты — только индикатор периода: ещё не наступил,
действует по датам, истёк. Они не запускают скрытое действие или cron, не
доказывают фактическое исполнение политики, не удаляют опубликованную запись.

## Ответственность и связи

Существующие node/position owner и company/branch/node/position scope сохранены.
Новые назначения выбираются из активных объектов той же компании.
Тип и UUID выбираются вместе, например position|UUID, не несогласованной парой
полей. Поиск — серверный, максимум40 вариантов каждого разрешённого типа.
Текущая историческая/неактивная ссылка отображается явно; новая публикация
требует актуальных допустимых ссылок. Область применения описывает действие
правила, но не является ACL: доступ по прежнему Company/capability gate.
Назначение владельцем само по себе не даёт права чтения или управления.

В «Связях» — существующие записи Административной шкалы, ссылающиеся на
policy/directive через sourceuuid и точную sourcerevision. Ничего не создаётся,
не перепривязывается к последней версии и не копируется. Показаны только
доступные исходные записи в Company scope. История не восстанавливается
задним числом и не объявляется отдельным новым аудитом.

## Документ

Сохраняется существующая ссылка documenturl. Только HTTP/S без встроенных
учётных данных; небезопасные legacy URL не превращаются в активную ссылку.
Внешний адрес не запрашивается сервером и не проверяет утверждение документа.
В этом срезе нет загрузки файла политики, snapshot внешнего URL или связи с
точной редакцией управляемого документа. Файлы/версии раздела «Документы»
сохранены, но автоматически не переносятся в политики. Нет электронной подписи,
назначения обучения, автоматических задач или изменения показателей.

## Защита и совместимость

Company/capability до SQL; явные условия scope на все запросы. Менеджерское
право — existing cascade_service::can_manage, не новая role/ACL. Site-admin path
сохраняется по действующим сервисам. GET/HEAD не меняет business data.
POST: sesskey, company/actor/object/revision/operation-bound receipt, подтверждение
lifecycle actions, повторная server validation, существующий company lock,
делегированная транзакция policy+aclog. Устаревшая версия не записывается.
Session receipts переиспользуют document_request_service: 2 часа/30 записей,
не durable exactly-once; потеря сессии между commit и receipt не закрыта.
Старые object URL открывают карточку. Старые POST без новой proof не выполняются;
пользователь получает сообщение открыть актуальную форму. Compatibility
context API сохраняет ключи и не заявляется пагинированным, но visibility
перенесена в SQL. Ужесточение readonly history и сохранение опубликованной
версии при новом черновике являются явными исправлениями текущего домена.

## Приёмка

PHP8.4 lint, SQLite/Moodle doubles, controller fixtures и Chromium components
не заменяют Moodle4.1.22, фактическую KBA Theme, PHP7.3 runtime, настоящую
Company ACL, MySQL/PostgreSQL, locks/sessions concurrency, PHPUnit и Behat.
Для live gate: две компании, роли reader/manager/site-admin, создание→редакция→
публикация→новый черновик→публикация/отмена, доступ по старым URL, код legacy,
неактивные ссылки, ошибки, повторы, 26+записей/редакций, desktop/mobile.
