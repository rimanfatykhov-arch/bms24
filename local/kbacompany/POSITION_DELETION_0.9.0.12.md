# local_kbacompany 0.9.0.12 build2026092508
## Должности — безопасное удаление из действующих и восстановление

Полное обновление на основе точного INSTALL 0.9.0.11 build2026092507.
Статус ALPHA. Сервер пользователя в рамках выпуска не изменялся.

### Рабочий путь

Люди → Должности и роли → Справочник должностей → нужная карточка →
Действия → Удалить должность. На отдельном экране проверьте код, название
и подразделение, выберите причину, установите флажок подтверждения и нажмите
«Удалить должность». Отмена возвращает в карточку без изменения данных.

Это мягкое удаление: active становится 0; строка, UUID, код, название и история
не стираются. Должность перестаёт отображаться в «Действующих» и в стандартных
выборках активных должностей. Руководитель видит её в «Неактивных» / «Все».
Восстановление: Неактивные → карточка → Действия → Восстановить должность →
явное подтверждение. Сохраняются прежние UUID и код.

Удаляется только неиспользуемая должность. Существующие ссылки из штатных
назначений/строк/ставок, функций, процессов, продуктов/показателей, документов,
политик, управления, финансов, компетенций/развития, структуры и интеграций
блокируют действие. Исторические связи также считаются использованием.
Поиск UUID внутри перечисленных frozen payloads консервативен: упоминание
в снимке может заблокировать удаление, даже если связь уже не действующая.
На экране блокировки показаны категории, без содержимого частных объектов.
Нельзя «освободить» должность автоматическим удалением истории; для выведения
используемой должности требуется отдельный сценарий организационного изменения.

Одинаковые имена не объединяются. Ни одна из двух должностей на скриншоте
не удаляется установкой пакета. Пользователь выбирает запись по коду и UUID.

### Границы изменения

Меняются только active и timemodified выбранной строки Position плюс metadata
событие штатного Moodle logging. Причина сохраняется как код из фиксированного
списка; произвольные персональные тексты в событие не добавляются.
Ставки, назначения, пользователи, функции, задачи, показатели, обучение, права
и внешние сопоставления не изменяются и не восстанавливаются автоматически.
Повторная отправка формы использует существующий session receipt (срок 2 часа);
это не распределённый постоянный механизм exactly-once.

Записи извлекаются с ограничением Company до получения данных. Команда требует
имеющегося права управления организацией, повторной авторизации, POST/sesskey,
подтверждения и проверки актуальности формы. Транзакция повторно проверяет
зависимости; запись сериализована с обычным редактированием справочника.
Другие домены не все используют этот же lock: глобальная сериализация
конкурентных междоменных записей не заявляется. Перед production нужна проверка
на staging, включая конкурентное назначение/добавление ссылок. Физического
удаления нет, поэтому даже при конкурентной ссылке UUID-строка не исчезает.

### Установка

Резервная копия БД, moodledata и кода → тестовая копия Moodle 4.1.22 →
INSTALL_ME ZIP как обновление local_kbacompany → штатные Уведомления / upgrade →
очистка кэшей. Не удалять плагин и не сбрасывать его версию.
При ручном размещении содержимое kbacompany/ копируется в local/kbacompany/,
без второй вложенной папки kbacompany.

Новых миграций нет: install.xml, upgrade.php, upgradelib.php, norm_ix hotfix,
ACL/API/cron/privacy declarations побайтно сохранены. Обновление с более ранней
версии всё равно должно завершить унаследованные миграции.
KBA Theme и AI companion не менялись.

Проверки и ограничения описаны в QA_REPORT release kit. Live Moodle/MySQL,
PHP7.3 runtime, PHPUnit, Behat и production acceptance не выполнялись.
